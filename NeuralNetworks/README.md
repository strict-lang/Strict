# Strict.NeuralNetworks
A multilayer perceptron written in Strict, the use case for measuring parallel loops on all CPU cores, SIMD and the GPU. `Layer` is a fully connected layer (sigmoid, one weight row per neuron), `Network` trains any number of layers with backpropagation (softmax and cross entropy for several outputs, momentum 0.5), `Csv` and `Dataset` read samples, scale them to 0..1, one-hot encode the classes and hold every fifth sample back for testing.

Start with `Xor.strict` (2-3-1 neurons learn XOR in 11 ms natively), then `Iris.strict`: `strict build NeuralNetworks/Iris.strict` (from the repository root) trains 4-8-3 neurons for 200 epochs and reaches 97% test accuracy in 25 ms natively, 2.4 s on the Strict VM. `Diabetes.strict` learns a quarter of the UCI Diabetic Retinopathy Debrecen data (288 rows, 19 features), 60-64% in 80 ms.

`LogicGates.strict` starts even simpler, with single neurons (`Perceptron`, a step output like the saturated sigmoid of AiInvest): Or, And, Nor and Nand are learned from zero weights in 3 to 5 epochs, Xor needs a hidden layer and is built from an Or and a Nand neuron feeding an And neuron. `LinearRegression.strict` fits a line to 10 points by gradient descent on the mean squared error and lands on the exact least squares line (y = 2.0006 x + 1.0273).

`Activation` gives a layer Sigmoid (the default), Tanh, Relu, LeakyRelu or Softplus with the derivative backpropagation needs: `Network.Random((4, 8, 3), Activation.Tanh)` uses it for the hidden layers. `ActivationComparison.strict` trains Iris with each of them: 97-100% test accuracy in about 25 ms natively, except plain Relu (33-67%, its neurons die at learning rate 0.25, which LeakyRelu avoids).

`Optimizer` trains a network with Adam (`Moments` keeps the running averages of the gradients and their squares per layer) or RMSprop (Adam without the first moment) instead of plain gradient descent with momentum. `OptimizerComparison.strict` starts all three from the same random XOR network: after 2000 steps momentum is still at an error of about 1, RMSprop and Adam are below 0.01.

`Recurrent` is the first network with memory: an Elman network (input, hidden-to-hidden and output `Layer`s) trained with backpropagation through time. `BinaryAddition.strict` (a BrightWire sample) feeds it two numbers below 128 bit by bit and it learns to output their sum: 100 of 100 new sums right after 10000 random examples, 0.29 s natively. `Gru` adds update and reset gates (a gated recurrent unit, its gradients checked against finite differences), which keep what an Elman network forgets. `ReberPrediction.strict` (a BrightWire sample) predicts the allowed next symbols of strings from the Reber grammar (`Reber`): both networks get 100 of 100 new strings right after 2000 strings, but in the embedded Reber grammar the second symbol (T or P) must be remembered until the end, the Elman network stays at chance (44-54 of 100 even after 20000 strings), the GRU gets 100 of 100 after 2000 strings in 0.34 s natively. It needs its gradients clipped to plus minus 1 and its update gates to start at -2 (keeping the state), otherwise some random starts explode or never learn the dependency.

Evolution instead of gradients: `Weasel.strict` (the weasel program of Richard Dawkins) evolves a random text into "METHINKS IT IS LIKE A WEASEL" with mutation and selection in about 70 generations, a few milliseconds natively. `Neuroevolution.strict` evolves the weights of the XOR network (tournament selection, mutation, the best network always survives) and reaches an error around 1e-13 in 46 ms natively. `ArmEvolution.strict` is a genetic algorithm with real valued genes (`Reach`: crossover, mutation within the joint limits, tournament selection, the best survives) that finds the joint angles of an `Arm` reaching a target. An `Arm` is a chain of joints in modified Denavit-Hartenberg rows (a, alpha, d), its forward kinematics multiply 3x3 rotations: the planar arm with 2 links gets within 0.2 mm, the 7 joints of a Franka Emika Panda (its published parameters and limits) within 0.2-1.1 mm of (0.01, 0.7, 0.28), 200 generations of 40 arms each in 55 and 136 ms natively (AiInvest evolved 6 Franka joints with a simplified chain that only adds up angles around x and z).

GPT-2 inference: `Safetensors` reads the JSON header and the float32 tensors of a `.safetensors` file (through `TensorFile`, a few lines of C in `native/`), `Gpt2Block` is one transformer block (layer norm, 12 attention heads with a key and value cache, GELU), `Gpt2` stacks them and picks the most likely next token, `Gpt2Tokens` is the byte pair tokenizer of `vocab.json` and `merges.txt`. `strict build NeuralNetworks/Gpt2Text.strict` downloads the 124M parameter model (548 MB, into `gpt2/`, ignored by git) and continues "Alan Turing theorized that computers would one day become" with " the most powerful machines on the planet.\n\nThe computer is a machine that can perform complex calculations", token for token what PyTorch gives with 32 bit weights (`Gpt2.Loaded(path, 32)`, 35 ms per token on one core). `Gpt2Text` loads the weights as 16 bit halves (`Gpt2.Loaded(path, 16)`, 1.3 s loading, 26 ms per token), which changes one word ("The computer is a computer that can perform"). `Gpt2.Loaded(path, 8)` quantizes every matrix to 8 bits (a signed byte per weight and a scale per 32 weights, Q8_0 of llama.cpp, 0.8 s loading) and continues with " the ultimate computer.", the same text as PyTorch with the same quantization. Doubles took 102-107 ms per token, the numpy picoGPT (no cache, 0.25 s loading) needs 476 ms per token, PyTorch with Hugging Face transformers (float32, cache) 24.6 ms on one thread and 22.1 ms on 24 threads. The matrix products run on all cores (11.7 ms per token with 16 bit weights, 8.6 ms with 8 bit weights on an i9-13900KF) or on an NVIDIA GPU (see the main README). The cache keeps the values of the attention heads per dimension, so the weighted sum over the positions is one vectorized loop per dimension. The tests use the tiny `tinygpt2.safetensors` (one block, vocabulary of 5), the Strict VM is too slow for the real model.

Qwen3: `Gguf` reads llama.cpp's GGUF files (the metadata and F32, F16, BF16, Q8_0, Q4_K and Q6_K tensors through `GgufFile`, a few lines of C, blocks decode to floats exactly like ggml), `Qwen3Block` is one Qwen3 block (RMS norm, grouped query attention with normalized and rotated queries and keys, SwiGLU), `Qwen3` stacks them, `Gpt2Tokens.Listed` builds the byte pair tokenizer from the vocabulary in the GGUF file (`TokenSplitter` splits the words like Qwen does: single digits, a punctuation mark before a word, line breaks), and `Generation` continues a prompt with either model. `strict build NeuralNetworks/Qwen3Text.strict` downloads Qwen3 0.6B with 8 bit weights (805 MB, `ggml-org/Qwen3-0.6B-GGUF`, into `qwen3/`) and continues "Alan Turing theorized that computers would one day become" with " able to solve the problem of finding the prime numbers. He was wrong, but he was right in", token for token what PyTorch gives with the same weights. The 4 bit weights of `unsloth/Qwen3-0.6B-GGUF` (`Q4_K_M`, 397 MB, Q4_K and Q6_K blocks) loaded as 32 bit floats give " a part of the human brain, but he was wrong. Why? Because of the following reasons:", also token for token like PyTorch. `Gguf(path, 4)` keeps those blocks as they are, as rows of 4 bits (Q4_K, 4.5 bits per number) and 6 bits (Q6_K, 6.56 bits): the same tokens in about 25 ms per step with less than half the memory of 8 bits (32.5 ms). Mixtures of experts (`qwen3moe`) work too: `Experts` routes a vector to the most likely `used` of its experts (softmax over the router rows, the chosen weights scaled to sum to 1, each expert a SwiGLU like a dense block, which is one expert), the stacked expert matrices come from `Gguf.Rows` of 3 dimensional tensors. `tinyqwen3moe.gguf` (4 experts, 2 used) gives the logits and tokens of the transformers library, `strict NeuralNetworks/Qwen3CoderText.strict D:/Models` downloads Qwen3-Coder-30B-A3B (Q4_K_M, 18.6 GB, into the given folder) and completes `def fibonacci(n):` with a correct recursive body, loaded in 31 s, 145 ms per step on the CPU (about 3 billion weights per token). On the GPU `Routing` ranks the experts by their router scores (a sum of comparisons per expert, ties go to the lower index) and picks the `used` best, `Experts.Expanded` and `Contracted` run all chosen experts as one loop each over the stacked rows of all experts (`gateUps(expert * size + row)`, a list of rows indexed on the GPU), `Mixed` weighs them by a softmax over the chosen scores, so a step needs no download: 5.0 ms per token (200 tokens/s, llama.cpp b11658 4.78 ms), it was 202 ms while the expert matrices did not fit the GPU cache of 4096 lists. On an NVIDIA GPU the whole step runs there: `Qwen3Block` keeps the queries, keys and values as flat lists, normalizes (each head by its own root mean square, a block of 128 threads adds up its head) and rotates every query and key head in one loop (`Rotated`, 2.8 instead of 4.3 us), the attention and feed forward norms are one kernel each too (2.5 us, the root mean square and the scaling were two kernels of 2.2 and 1.5 us) and does the attention with `Scores` and `Merged` (`Softmax.Weighted` takes the largest score of a row, then adds up the shares and the shared values in one loop on the warp), all loops that become kernels, only the logits come back to the CPU. `Qwen3.Prefilled` sends all prompt tokens through each block at once: `Batch` multiplies a matrix with the vectors of several tokens in one loop over rows times tokens, `Scores` hides the positions after each token, 4.3 ms per prompt token for the 8B (7.1 ms as single steps), 0.82 ms for the 0.6B, on the CPU 18 ms (0.6B) and 190 ms (8B), where each token still decodes every row again. `Qwen3Benchmark.strict` measures it (`strict build NeuralNetworks/Qwen3Benchmark.strict`, then `NeuralNetworks/Qwen3Benchmark.exe <gguf> 4 30`: the generated text, prefill and decode per token, median after a warmup): on an RTX 4090 Qwen3-8B Q4_K_M decodes in 7.0-7.1 ms per token (141-143 tokens/s, mean 7.2 ms over 128 tokens, llama.cpp 7.25 ms, 138 tokens/s on the same day, 180 ms on the CPU) and prefills 10 tokens in 2.9 ms per token, Qwen3 0.6B Q4_K_M in 2.2-3.1 ms (llama.cpp 2.2 ms), with the same tokens as on the CPU. How: loops over packed numbers calculate in 32 bit floats (`Compiler/MlirSingle`) and their results stay on the GPU, launches do not wait and are captured into CUDA graphs of 96 that run again with updated arguments, the inputs of the matrix products become 8 bit numbers with a scale per 32 (a quantize kernel each, like q8_1 of llama.cpp) that `dp4a` multiplies with 4 numbers of a row at once (`STRICT_DP4A=0` keeps 32 bit inputs, 7.4 ms per token), Q4_K and Q6_K rows keep the blocks of ggml (a lane decodes 32 numbers of a Q4_K row per step with one header load and its 6 bit scales in registers, 8.3 instead of 17 instructions per weight, or 16 numbers of a Q6_K row), small host lists move to the GPU on their second use, the argmax is one kernel of (maximum, position) pairs per 128 logits and one download (`Qwen3.Best`), a loop keeping a maximum or minimum runs on the 32 lanes of a warp (`MlirDeviceChoice`). Per 8B token (nsys): 6.3 ms of kernels, the matrix products 5.0 ms (per layer QKV 19.9, output 12.2, gate and up 64.5 (880 GB/s), down 46.9 us, with 32 bit inputs 23.6, 12.7, 66.6 and 51 us, 144 quantize kernels take 0.14 ms, llama.cpp 20.7 as three kernels, 11.4, 63 as one fused kernel and 46), the logits 0.55 ms (both), the other kernels 0.8 ms against 0.65 ms, the GPU idles about 0.5 ms (llama.cpp 1.1 ms). A synchronous download waits 60-100 us for the copy engine under WDDM even when the GPU is idle, a graph launch 50-70 us until its first kernel, under WDDM a launched graph waits in the driver until something submits it (a stream query after every graph launch does, before the first graph after a download started 500 us late), a fresh 64 MB device chunk stalls the GPU 3.2 ms (the young generation of the collector reuses blocks instead). Measured and not kept: 128 lanes per row adding through shared memory (QKV 21.1 us, but output 14.8, gate and up 68 and the attention kernels twice as slow), two Q4_K units per lane step, synchronizing before a download, 512 MB device chunks, at most 40 registers per thread (QKV in one wave, 20.3 us, but gate and up 69 us). Greedy decoding of the benchmark prompt gives the same 80 tokens as llama.cpp (b11658, CUDA), then a near tie flips: llama.cpp continues "serving as a model" with 49.5% against 47.6% for " mathematical" (a logit gap of 0.04), Strict picks " mathematical" (32 bit sums and llama.cpp's 8 bit activations round differently). The tests use `tinyqwen3.gguf` (random weights, one block, 6 tokens) and compare with the logits and tokens of the transformers library.

Bigger data does not belong into this repository: the MNIST digits are in [Mnist](https://github.com/strict-lang/Mnist), larger datasets should be downloaded when they are needed.
