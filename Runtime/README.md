# Strict.Runtime
The Strict VM: `strict <file>` and `strict test` run the instructions of `Bytecode` here without building an executable. `Execute` loads the types, `Resolver` numbers the locals and registers of every method into slots, resolves jumps and decodes constants, `Routes` decides where a call goes (a method, a VM native or a hosted call; a placeholder body of a hosted method runs its native), `Machine` calls methods and binds members and arguments, `Frame` runs one call in its own list of slots (a call of a method that only returns a member, like `Vector2.X`, reads it through `Accessor` without a call), `Looping`, `Operations` and `Storage` carry out the instructions, `Natives` the methods of the base types the VM implements itself.

## Test budgets
Automatic test runs select unmarked methods and enforce 100 ms per test (the goal is under 10 ms), including leading local setup; source checking and compilation are outside the budget. `TestBudget` gives the VM and native test runner the same clock and watchdog hooks, a test that does not return is stopped. Methods of the internal packages (Compiler, Runtime, Bytecode, Expressions, `TypeSource.IsSlow`) count as Slow. Explicit file or method runs include Slow tests. Only automatic passing results are cached. `Execute.Run` runs the requested tests before loading the program's Run graph.

VM constants are cached per `Machine`: a getter runs on first use and its result is stored, recursive access reports `RecursiveConstant`. Unused Slow fixtures are never initialized.

`python Runtime/check_tests.py` checks deadlines, Slow selection and fixture exclusion, `python Runtime/check_frames.py` frame initialization speed.

## Coordinator
One process per OS user (`strict coordinator`) admits GPU and memory jobs. Its port is in `%LOCALAPPDATA%/Strict/coordinator` on Windows and `~/.cache/strict/coordinator` elsewhere, and it also listens on `Peers.Port` when that port is free. A program sends `need`, `holding`, `progress` and `done`; the coordinator answers `go`, `wait`, `free`, `exit` or `refused`. `fit` asks the same admission without taking the machine. `run` executes a command in the same folder and returns its exit code. `STRICT_MACHINE_RAM` and `STRICT_MACHINE_VRAM` replace the measured totals. `strict status` prints the running job. If the coordinator is not there, programs keep the `MachineUse` check and the GPU lock. `Admission` is the decision, with no sockets.

`cancel <job>` and `lost <job>` drop that job and answer `free`, which tells its backend to yield the GPU. A different job id is left running. A failed send, from Ctrl+C or a dropped client, is the same cancel for that connection. `--remote <name>` runs the same arguments, with that flag removed, on one peer. The names are `Ben-Home-PC`, `Ben-Work-PC` and `AiServer` (`Peers.Named`, hosts in `Peers.Hosts`). Nothing is copied; every machine already has the same folders. `--remote any` (also `Any`) stays here when this machine can start now, otherwise the first peer whose `fit` answer is `go` runs the job. If none can, the local `wait` or `refused` answer stands. Ben asks with `Remote.Ben`, which is `any`, when it does not pass a name. H3Video and MossImage stay local unless `--remote` is present. `Placement` is that choice, with no sockets.
