# Strict.Validators
The rules behind `strict check`: `Limits` (120 characters per line, 13 lines per method with header and tests, 16 methods and 15 members, `0 - x` where the 0 starts an operand must be written `-x`: `ZeroMinusMustBeNegation` (a leading minus applies to its first operand before `*`, `/`, `^` and `to`, so `0 - a ^ b` becomes `-(a ^ b)`), ...), `Names` (keywords, list prefixes, constant names), `UsageRules` and `TypeValidator` (unused or never changed variables and members), `ConstantCollapser` (folds constant expressions), `Recursions` (a constant calling a method that uses the constant again, a method whose only line calls itself), `DroppedResults` (a line that only calls a method whose body is one plain expression without calls, so its result is dropped for nothing: `DroppedResultMustBeUsed`; a method of the same file as `Area(2)`, any other as `shape.Area(2)` on a variable or member when every method of that name in the folder and the base types is plain), run by `ValidateCheck` for every file of a folder. Every issue prints as `<File>.strict:line <N>: <Rule>: <detail>`, `strict check <folder>` reports 0 issues before a commit.

`strict suggest <file> <method>` (`Suggestions`, `SuggestionCalls`, `SuggestionTests`) compiles candidate bodies for a method, links their combined dependencies once and keeps each body that passes the method's tests on fresh VM state, at most 32 candidates from the own, parameter and member types; a method name or its header line number selects an overload, `-` reads unsaved source from standard input. Passing tests never create a validation issue. `python Validators/verify-suggestions.py .` checks it end to end.
