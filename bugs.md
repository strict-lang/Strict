# Bugs

- GC race: a young collection inside a pool job (more than 2 threads) frees or misses an object a job thread still uses. Repro: the -O3 seed compiler (`Compiler\Bootstrap.cmd` with -O3) building Strict.strict after strict.exe stamped the .strictbinary files, with STRICT_GC_LOG=1, crashes 4 of 4 right after a "young, pool job" collection (AccessViolation at changing places: KnownTypes.Index, TypeEntry.ShortName, CallTarget.Holding). STRICT_THREADS=1 or 2, STRICT_YOUNG=0, -O2 or no vectorizer hide it. Bootstrap.cmd links with -O2 until it is fixed; release builds use -O3.
- `strict check` hangs on a member default that reaches the own type through another type's constant: in a type Split, `has place = Split.Folder` makes `Split.X` resolve as `place.Split` and the check loops before any test; with a literal default it reports `place.Split hides the type Split` at once (from Ben).
- `Logger.Captured(true)` inside a running capture overwrites the one saved output of the thread, so the outer `Captured(false)` keeps capturing and every later log line is lost (TrialRun evaluates its warm-up before it captures for that reason).
- A child that strict waits for ends with its parent on Windows (job with kill on close) and on Linux for `Process.RunTool` (PR_SET_PDEATHSIG), not yet on macOS (no parent death signal) and not for Linux `Process.Started`, which runs through `system()`.
- A default argument that is a constant list breaks the split native build: `Ran(arguments Text, variables = EightThreads)` in `Runtime/CheckTests.strict` gave `mlir-opt failed: llvm.mlir.addressof op must reference a global` (`@cCheckTests_CheckPolicyRun_1_1_0`, defined in another module part); passing the constant explicitly builds.
- A default argument of another package's method is linked under `Strict/`: `Strict.Testing(rest)` called from `Runtime/Trial.strict` fails with `UnresolvedLink: Strict/InferenceCache.None` (the default `inferred = InferenceCache.None` lives in `Runtime/`).
- A test run inside a test (`Trial.Tested` on the VM) leaves the outer test with a negative time (`-2.3e8 ms`): both runs share the test clock of `TestBudget`.

`strict check` lets a second way of writing the same thing through (from the review of all DeltaEngine files, 2026-11-11, counts are DeltaEngine sites then):
- `ErrorCheckCannotFail` misses callees of other types that turn every Error into a literal themselves (same-type callees are covered since 2026-11-21: a Boolean method of only `let` lines and `x is Error then <Boolean> else <Boolean>`, without `Error(`); other types need the records `SureMethods` only builds for base types.
- `StatusNumberMustNotBeReturned` misses a huge constant for nothing found (`-1` is `NotFoundMustBeNamed` since 2026-11-21) and Number results only compared with `is 1` (Window.IsDebug, WebPage.Picture). A 0/1 result or bit sum of an Is/Has/Can/Should method is `BooleanMustNotBeNumber` since 2026-11-21.
- Three ways to build a list: `mutable list = List(T)` + `for` + `list = list + item`, `List(Mutable(T))` + `.Add`, and the plain `for` expression. `AccumulatingLoopMustBeForExpression` is written (`Validators/AccumulatedLoops.strict`, not in `Issues`): a pure map or filter of one element per step, joined lists left out by the element type, 69 sites in Strict and 45 in DeltaEngine (2026-11-21), moved with the other large rules. `List(Number) + x` and `(x)` both build a one element list.
- A leading test line that does not mention the method it sits in (`TestMustCallItsOwnMethod`, 2377 test lines in Strict) and a method with a branch and no test that does no IO (`MethodWithBranchMustHaveTestOrBeIO`): written in `Validators/TestChecks.strict` (`Placed`), not in `Issues` until the lines are moved; instance and constant checks go to a `from` method with tests and `value` (works on the VM and natively).
- The same call with arguments twice in a method outside the tests (`SameCallTwiceMustBeLet`): written in `Validators/RepeatedCalls.strict` (not wired, calls on `mutable` values are skipped), 874 sites in Strict and 182 in DeltaEngine (2026-11-21), moved with the other large rules.

- mlir-opt crashes now and then (0xC0000005, stack in `std::__basic_future<void>::wait` of its parallel verifier) in the GPU kernels step of big native test builds (`strict test H3Video.strict native` in StrictComfy): `GPU kernels failed: mlir-opt failed`, then `NoProgramEmitted`; the unchanged retry passes. Since 2026-11-22 the kernel lowering runs mlir-opt with `--mlir-disable-threading` (no slower: 7.6 to 10.5 s either way on the 30 MB Qwen3Benchmark kernels), and the failure names the exit code; remove this line once big native test builds stay clean.
