# Ideas
Large features, difficult or long work and far fetched things, kept here until someone wants them. Not a to do list, lines may get deleted any time. Bugs go into `bugs.md`, speed work for soon into `performance.md`, while there are any.

## Features and long work
- Reusing results of unchanged calls: values are immutable and every result is consumed, so a call whose inputs (instance, arguments and what it reads) did not change since its last run can hand back the kept result instead of computing again, from `numbers.Sum` up to a pathfinding query on a big unchanged map. Needs purity per method (MlirPurity has a start), cheap change detection of the inputs (versions or hashes of lists instead of comparing them), a cache size limit and eviction, and only pays for expensive calls.
- A one line edit of H3Video (StrictComfy) takes 6.5 s without kernel work: MLIR emission 2.4 s, of it 1.7 s emitting GPU kernels that then turn out unchanged, linking 1.4 s, GPU preparation 1.2 s, lowering 0.5 s. Skip emitting kernels when their types did not change. A change in any kernel rebuilds all of them (mlir-opt 7.6 s, PTX 8.8 s, cubins 12.7 s of 34 s). No cache per program: a shared cache of all programs would fit, 602 of the 722 functions of MossImage have the same text in H3Video, 3443 functions of 11 programs have 1652 distinct bodies. It needs kernels compiled one by one, and kernels will rarely change, so only worth it if updates hurt.
- Plain `strict test` mutates every passing file, about 110 ms per verified Ben candidate (309-330 instead of 200-209 ms); `unit` skips that but a cached unit run prints no per-test lines, which Ben counts: a mode for tool callers that always runs, prints every test and never mutates.
- A small page reused after a collection is cleared before its objects are handed out (strict_gc_small_page), also for texts the collector never reads: skipping it for texts made 20 million small texts 31.5 -> 29 ns each, but packed rows, gathered rows and other GPU blocks share the unscanned classes and may rely on zero padding; texts need classes of their own first.
- A strict build of Strict.strict makes about 168 million allocations (STRICT_ALLOC_PROFILE=1009 with STRICT_SERVER=0 at the start): TypeEntry.ShortName 10% (MlirFunction.TypeOf, TypeEntry.Wrapped, MlirKinds.MembersKind), LoadReuse.Reads 4.5% (RegisterCount, MlirPacking.Kind), Tokenizer.Tokens 4.2%, Text.Split 2.2%, TypeEntry.Unconstant 2% (Changing). Not time: all of MLIR emission is 3.4 of the 11 s of a build with no cached objects, none of these reaches 5 %.
- Two packages with a type of the same name in one executable (Left/Point and Right/Point): natively the symbols, register kinds and helpers use the short type name, a folder build stops with SameNamedTypes; qualify the symbols of a type whose short name is taken.
- On the web dead values can stay roots: Asyncify saves every local that is live at any unwind point of a function with whatever it held last, and the collector scans them (strict_registers_spilled). The old value of an owned local is freed when it is replaced (strict_rc_dead), so `moss = Loaded(model)` releases the old Moss; a value that is not provably owned (passed to a method returning it, aliased) can still be kept by such a copy until the local is reused. Precise roots (reference locals in a shadow stack frame the collector scans instead of the Asyncify locals) would cover all of them.
- Requests in threads of one server (the decided design, after several servers came first): a `for` runs in parallel when every effect of its body only touches resources the iteration owns (its accepted socket, its own output, files it creates), checked by MlirPurity; the pool takes jobs of several threads (one busy flag today, inner loops of a second request run serially); blocking natives (accept, receive, waiting for a process) count as stopped for collections; full collections inside long jobs; Process.FilesRead and claims per request. Served timeouts: a test over its time inside one long native call is reported but not counted, a gone caller is only noticed while VM work runs.
- Mutation testing (Ben): fix the surviving mutants package by package (strict test <file> reports each with its method source, a folder run skips files whose .strictbinary is current, results are kept in obj/Name.mutations until the source changes). Math done, base package types are not mutated (the runtime and compiler replace most of them). Left: Json 26 (Parts, ValueEnd, StringEnd, Slashes loop conditions; its get, Keys, Elements and Values were hosted so their tests never ran the source), Runtime (Machine 35, Mutation 53, MutationKinds 36, Mutants 31, Execute 39, Frame 85), Validators (Limits 45, UsageRules 56, Recursions 55, TypeValidator 48, TestChecks 36, Duplicates 26, DroppedResults 18, RoundTrip 15, Names 8, ValidateCheck 4, LoopBodies 1), ImageProcessing about 230, Compression 61, MachineLearning 34, Xml 30, Binary 27, Networking 20, Bytecode, Expressions, Compiler, NeuralNetworks and Examples not surveyed. Open: the 1 s (0.1 s in folder runs) baseline limit and the folder run skip of files whose tests take 0.1 s are wall clock based (should be step based); obj/Name.mutations is keyed on the file source only, a changed fixture or dependency replays stale survivors; Json.strict takes minutes (its tests read files, a JsonMock would help). Methods whose tests pass with a failing body (native, hosted, Text searches) are not mutated, mutation runs cannot write, delete or run tools. MutationKinds.IsText stops at a non-writer (Print, Store) whose payload(0) equals the register instead of going on to the real writer. Constants of other types are still pasted into mutation compiles (their linked binaries have no constant methods, generating all of them for every dependency blew up the compile), so mutants inside pasted foreign constants (like Layer.Halves in Gru.States) still show up as equivalent "removed the call Add" survivors.
- Compiler/MlirCarried.strict has 43 surviving mutants (61 before its rejection fixtures): mostly the depth limits and the and/or of IsSafeUse, IsKeptValue and IsHeld. Perf shortcuts give equivalent mutants (MlirLayout.Represented for base names, Instantiation.Arguments without "("): a shortcut skipped gives the same result.
- OutOfMemory, crash reports and STRICT_ALLOC_PROFILE name the Strict methods on the stack on Windows and Linux; macOS uses the same unwinder calls (untested), strict_stack_starts on the web returns no frames yet.
- `ImageCodec.SaveJpeg` only works on Windows and the web (`JpegRequiresWindowsOrWeb` on Linux, macOS, Android, iOS): a baseline JPEG encoder in Strict next to ImageSaver's PNG would cover every platform.
- Qwen3-Coder-30B decoding is host bound (about 1000 kernel launches captured per token) and swings between 200-217 and 133-160 tokens/s from run to run, the 11-05 build too: in slow runs every driver call and the code between them take 1.6 times as long, the core of the main thread runs at 64-71 % performance instead of 99 % (Balanced plan); the High performance plan makes every run slow (133-149), pinning the process to one CCX keeps the swing, to one core gives 97. Fewer launches per token (larger fused expert kernels, graphs without recapture) would make it independent of the boost.
- Batch.Sums of 8 to 32 tokens (strict_device_blockss, 128 registers since the launch bounds) is latency bound at 33 % occupancy (DRAM 30-46 % busy): Qwen3-8B with 8, 16 and 32 sequences decodes 801, 1446 and 2098 tokens/s against 953, 1655 and 2357 on 2026-10-17. Not from the token kernels changed since 10-29 (84fdfec7's NativeRuntimeTokens.mlir gives 677, 1107 and 1607), tokens_sums and tokens_tile not inlined (3 % slower), 3 blocks per SM (15 % slower) or PTX with the SLP vectorizer (same); next: bisect 10-17 to 10-29 with the Bootstrap.cmd of each commit (LLVM 23 came on 10-22).
- Nightly CI: build and run every program's Run once a day (games and long running apps for a few frames); work too slow for a Slow test (rebuilding all content, big models) belongs in a Run, not in tests.
- Networking: `Http.Send`, `Http.Started`/`Received` and `Hmac.Sha256` are in (Windows, Linux and the web checked, macOS untested), DeltaEngine's Google sign-in and sheet downloads use them: switch Rebalancing's `NativeIO.Http`/`Hmac` (with the user, it trades live); client certificates when a program needs them, TLS for multiplayer sockets later.
- GPU sidecars: every program still keeps obj/Name.kernels.mlir (the PTX cache key) and its PTX in obj/ next to the source, move them into Tools/PtxCache once it evicts old entries (up to 25 MB each, never cleaned today).
- f32 kernels: a GPU loop reading a `value.Bits is 32` member computes in f32 (WGSL on WebGPU, the 32 bit CUDA kernel natively); WGSL lacks Float8 `from` calls, Bytes results and rows.
- Release builds: platform builds into Release/<Platform> are optimized without debug checks, logging or per-call checks (the web runtime already is), plain `strict build`, test executables and the VM keep them; native needs a release flag on `strict build` for local benchmarks.
- Named iterators over counts (`for row, column in rows, width`) as one flat loop of rows * width with the names from the index (parallel, GPU kernel), then the `(index / n).Floor` and `index % n` loops of NeuralNetworks, Math/Matrix and the image decoders can name their iterators without losing their kernels.
- Parallel dedup by key (Ben): a `for` that keeps the first element per computed key (Dictionary or distinct by key) in parallel; Ben's program search keeps 2 of 128 cores busy because its observational equivalence dedup is a sequential loop over a mutable Dictionary.
- NeuralNetworks on the GPU (Ben): a program using NeuralNetworks (models, image and video generation) should get GPU kernels for every loop that can run there, also those the size heuristics keep on the CPU today.
- Loop conditions in the compiler (Ben): split loops on conditions that do not change in them (`range is 0` guards, mode flags like `isGray`) the way LoopPeeling splits first and last iterations; `strict check` only reports guards in inner loops.
- Branch probing in `strict check` (Ben): for a branch in an inner loop run the method's tests with only the then side and only the else side (SuggestionTests on the changed body); when one passes the branch is not needed or not tested, the issue says which side and how to fix it.
- Cleanups shown by equivalent mutants, what is left after the redundant conditions were deleted (2026-11-12): f32 stores write the exact parts twice (MlirDeviceRows.Called, MlirDevice.Entry and MlirGrouped.Remembered call function.Store and then MlirExact.Set overwrites the same slots, a MlirDeviceRows fixture pins the doubled stores); MlirWholeNative line 135 passes the kind "c" where "i" is probably meant (both map to i64); the unguarded `instructions(writer < 0 then ... else writer)` selects in MlirWholeFlat 80, MlirWholeKernel 86, MlirWholeSpan 120 and MlirDestined.IsSafe; not looked at: Mentions.Unknown adding own constants, LoopPeeling.Folded `isChoice`, Specialization.Completed `method is not ""`, SpectralFit.Linear `coords.Length < 2`, the TypeInference fallbacks `2 - "a"` typed Number and `Mutable(a, b)` typed Mutable. - 32 bit loops (Ben): a vectorizable CPU loop (+ - * / over lists, not on the GPU, not a small constant count) over f64 Numbers fails the build with `VectorLoopMustUse32BitNumbers` (MlirNarrowing) until its lists say `with value.Bits is 32` (or 64 to keep them exact, a hard stop for narrowing); packed lists (Float32s, BFloat16s) compute in f32 with f64 sums (MlirSums: a 10 million dot takes 3.6 ms, 2.7 with f32 sums, 5.5 in f64); `value.Bits is 32` list members are stored packed natively (`strict_list_single`, format 32, 10 million sum of squares 4.3 -> 3.55 ms). ## Performance
- Resident builds forward to the server but reuse nothing between requests except what the process already caches (a one line edit: Xor 1.04 -> 0.91 s, a big program 8.65 -> 8.5 s, no change 0.37 -> 0.03 s). What repeats per build of a big program: MLIR emission 1.45 s, splitting the module 0.8 s, link passes 0.9 s. Linker.Known does not help (it keys exact method lists, each link pass extends them) and skipping homes changes the output order, keep decoded homes or per function MLIR text instead, and compare with a server-less build (byte identical MLIR).
- One edit regenerates every ThinLTO module importing from its part, and parts mix types by hash: an edit in strict's top type regenerates 32 of 64 modules because it shares a part with MethodEntry. One module per type needs each part to declare only what it mentions (256 parts: cold build 30 s instead of 18 s, mostly parsing all declarations per part).
- A web rebuild is now mostly whole program work after the parts: emcc link with Closure 2.3 s and wasm-opt 1.6 s for Xor, also when only one string changed.
- Build speed: under 10 s hard limit, 2-3 s target (LogoApp, Blocks and Breakout 3.6-4 s): a build with tests runs the frontend twice (test gate, then native), lowering and the thin LTO link are the largest phases left.
- The VM is about 100 times slower than native on compiler code (boxed numbers, dispatch, allocation): the reason internal package tests count as Slow.
- VM calls dominate game logic (a member read through a method like `Vector2.X` is two calls): DeltaEngine's multi tick simulation and content loading tests are Slow for it.
- Cold GPU builds spend most time on the shared runtime PTX for both sm_75 and sm_80.
- Trees as pools with 32 bit backward offsets ([Goose](https://github.com/aardappel/goose)): count SyntaxNode allocations of `strict build Strict.strict` first.
- Reachability, safety and globals/text assembly of MLIR emission run serially.
- ParticleStress at 1 million particles (Unity's particle system 9.5 ms per tick): 5.5 ms per tick over 100 ticks, 4.8 at 600 ticks (7.8 and 5.9 before 2026-11-06, 14.2 at first) and no collections: dying locals free their old values (MlirDying), a long list whose last count goes is freed at the next large allocation unless a stack slot points into it, and the next list reuses its pages. Pool threads take their own pieces of a job first (strict_pool_run) and prefer one core each (SetThreadIdealProcessorEx), so every tick a thread writes and reads the same items in its own L3; before, the list two ticks old was still dirty in other CCXs' L3 and every line moved between them. Next: 32 bit members (72 -> 44 bytes per particle), writing in place over the list being read.
- A `for` that drops items collects objects in parallel, but numbers and flat elements stay on one thread (any bit pattern is a number, so no hole marker): keep a bitmap of the kept slots instead.
- `strict test RealTimeStrategy native` (DeltaEngine, 73 files) takes 47 s when anything changed: every file is linked again, 11 s of dependency linking (link rounds only scan new entries now, `Completed`, `Forwarded`, `Linkable` and the round lists remain), the thin LTO link takes 8 s (about 2 s on one thread at the end), name validation reads every linked source again per file. A run without changes of a .strict file takes 0.1 s.
- Decode attention (`strict_device_attention_decode`) is latency bound: about 8 us per call even for a few positions (4 blocks of 8 warps, 255 registers, warps waiting at the merge barriers) and 24 us after 2000 positions for Qwen3-Coder 30B, 48 calls a token.
- Generated CPU loops: parallel chunks whose checks are all on numbers run once without early exits (a failed check or index read gives 0 and a flag, the chunk then runs again with all checks) and vectorize when their reads are of hoisted parameter or member lists; still per element: reads of other lists (`strict_list_read`), checks on instances, chunks with inner loops (their fast path copies would be duplicated), serial loops, and f64 numbers and indices.
- Fast path loops (MlirFastLoop) below `MlirCost.Threshold` elements run on one thread, longer ones in parallel chunks (10 million numbers: 30 ms on one thread, 12 ms on 64, the rest is page faults of the fresh 80 MB result, pool big results); a chunk reads an iterated list of 32 or 16 bit floats (Float32s, BFloat16s, halves) in place (`MlirDeferred.Packed`), a chunk with inner loops reads each item where it is (`strict_steady_item`) instead of unpacking the list first.
- Reading a packed list through `strict_list_items` (chunks without inner loops over Float8, byte, lane or quantized lists, quantized formats read by index, Float8 and quantized arguments of native library calls) replaces it with an f64 copy for good (`strict_list_unpacked`), it then takes twice the memory and loses the f32 loop variants; serial loops, chunks with inner loops and index reads read 32, 16, 17 and 7 bit formats in place (`strict_steady_item`, `strict_list_get`).
- A call with whole number arguments dispatches per element between its i64 (`_whole`) and f64 versions: a vectorized loop computes both and blends, one thread over 10 million numbers takes 55 ms against 14 ms for the same math inline.
- Tool children get a fixed share of the threads (strict_tool_share): Ben's 24 searches started together get 5 threads each and the few long ones then run alone on 5 while the 3990X idles (codewars6 113 s, STRICT_THREADS=32 46.5 s; nine stages 5m54s, 3m13s): a share that grows when siblings exit, or the full pool for every child.
- Collections inside pool jobs: 1.6 s of a 30 s MlirLibrary mutation run (21 young, up to 236 ms), 2 % of a full Strict.strict build, Ben Operations on 64 threads no slower than on 8; not measured again on 128 threads (297-685 ms there before e6efb260). Sleeping parked threads in strict_gc_resume made the compiler crash in ResolveCheck, a race not found.
- The first big numeric loop of a process takes ~330 ms extra, that is its first GPU use (STRICT_GPU=0 saved ~0.45 s of an 8 seed run, only cold runs pay it).
- Attention: `strict_device_dense_attention` keeps the 8 bit tensor pipe 53 % busy (Moss on the 3080, 1.26 ms per layer, 253 registers leave one block per SM; comfy_kitchen's `int8_attention` was ~20 % faster on the 4090 before warps 4 to 7 ran half a step behind): fewer softmax instructions (part of the exponentials as a polynomial on the fma pipe), or two blocks per SM
- Attention: the row maximum on the integer sums (IMNMX) needs one key scale per lane and step instead of one per position
- Attention: the 2 tile copies of a routed step sit in conditional blocks (long scoreboard stalls after them): branch-free copies like `strict_device_dense_issued`
- Attention: the routing planner reads all pooled keys of a head in every block: moments once per head, the scores as a small product kernel (2026-11-08: fusing the moments and score passes, or only storing the centroid before the moments loop, made the routed kernel run 2.25x the instructions and L2 bytes at 480x832, so plans got longer although the data flow reads as equivalent: dump plan lengths before trying again)
- Attention: the Hadamard on Q and K
- Attention: routing plans at most 1024 key blocks (65536 positions), longer prompts attend densely: plans in global memory
- Attention: head size 64 (H3 VAE decode) has no tensor core attention kernel
- Attention: routed strict_device_bytes_attentions is L2 bound on the 4090 (L2 81 %, DRAM 4.5 %, compute 40 %, 238 registers): every 64 query block loads its own tiles, kernel time is ~0.7 ms plus ~3.2 ms per plan at 384x640 (half the entries: 3.88 -> 2.29 ms); neighbouring query blocks of a head share 46-118 of their 78-134 exact tiles, so two query blocks per block of 8 warps loading the union once (each half computing only its own plan, pooled chunks are per half) would load 27-46 % less: ~25-30 % kernel, ~10-12 % of an H3 step at 480x832, ~4 % at 384x640
- 16 bit lists: bf16 QK attention beyond the 128 wide QKV path
- 16 bit lists: attention, product and Hadamard results are 32 bit
- 16 bit lists: compiled loops index in 64 bits: 32 bit index math where the counts fit
- GPU memory: streamed weights are not overlapped with compute (H3 idles ~230 ms per step, ComfyUI 60): uploads ahead in a ring need a cheaper refill than walking the chain
- GPU memory: without spilled rows the trim before an own block runs at every block
- GPU memory: GPU-only lists can't be spilled, activations kept across streamed blocks take every byte from the weights
- GPU memory: a reference in a local stays alive after its last use in a callee-saved register or spill slot (conservative stack scan)
- GPU memory: NVFP4 matrices (`TensorFile_Fours`) load as 8 bit rows (27 instead of 15.7 GB): e2m1 rows with their block scales on the GPU
- Loading: 8 bit rows gathered straight from the mapped file (the 21 GB H3 DiT loads in 10-12 s, ComfyUI 4-7)
- WebGPU: strict_convolution runs at ~6 TFLOPS on a 3080 (30 peak): not limited by workgroup bank conflicts, index divisions, register prefetch or the rolled inner loop (unrolled it was 6 % faster in a decode, products slower, shaders compiled longer)
- a `for` over candidates times examples whose body calls a method with an inner counted `for` and a mutable accumulator (a small opcode interpreter, Ben's candidate evaluation) gets no kernel and stays a CPU parallel loop (800000 evaluations in 3 ms there): kernels for such bodies, then batches big enough for the GPU
- bounds, reduction and tail checks remain: extend the four wide loads (`MlirBatched`) and fuse memory passes
- an index divided by a power of two (`size / 2`) divides in 64 bits at every read: shift

- Uniform branches still in GPU loops, measure their share first (none showed up in Qwen3-Coder): `tokens_blocks` switches on the row bits per block, `products_run` runs bits chains per element, `strict_device_dots` has no bfloat16 arm, prompt attention masks every tile.
- small number types as kernel values: values, parameters and members of types with 2-4 Number members (Complex) and lists of them read by index work (StructLanes, LaneCalls, MlirDeviceRecords), still on the CPU: a `for` over a List(Complex) (a list member with `value.Bits is 32` fails the build, index it instead), a List(Complex) result, a method returning a Complex that has a loop or an early return, the 32 bit types (Vector2, Vector3, Size); a flattened list goes up again for every launch; a `to Text` reached only through text conversion is not emitted unless something calls it (why lane inlining skips `to`)

## Validator rules from the DeltaEngine review (2026-11-11)
All 440 DeltaEngine files were read for what `strict check` lets through (it reports 0 issues there). Most hits first, counts are DeltaEngine sites, each is a second way of writing the same thing:
- `ErrorMustNotBecomeAValue`: `x is Error then <number, true, false, value>` and `if x is Error` followed by `return <literal or value>`: the Error is swallowed and the frame goes on (`next.Drawn(screen) is Error then value else next` in every game Frame, `Cast(casters) is Error then 0 else ...`), about 90. The branch of an Error check should return that Error or another Error; leaving the check out already propagates it. StatusNumberMustNotBeReturned made 45 of these visible, the fix was always to drop the return type and the check.
- `ErrorCheckCannotFail` misses callees that turn every Error into a literal themselves: `current.Drawn(screen) is Error` where Drawn is Boolean and returns false on failure (Games/WebWars/WebWars.strict:61-72), ArenaHud.Draw, FractalPage.Published.
- StatusNumberMustNotBeReturned misses: `condition then 1 else 0` as the result (RealTimeStrategy/NetworkChecks.strict:18, ServerChecks.strict:30, about 30, also `(a then 1 else 0) + (b then 2 else 0)` bit sums), a literal after only tests (`Failures Number` ending in `0`, `10` or `7` in every *Checks type), `-1` or a huge constant for nothing found (about 10), and Number results only ever compared with `is 1` (Window.IsDebug, WebPage.Picture).
- `NumberStateMustBeEnum`: a Number member or parameter compared with `is <integer literal>` against two or more different literals in a type and never used in arithmetic (`page is 3`, `choice is 6`, `stage is 4`, `phase is 1`, `kind < 3`, `Gpu.State(3, 1)`, `NativeDraw.Quads(texture, 1, 0, ...)`), about 300. Types often define the constants (UnitCommand.MoveOrder, GhostMatch.Neutral) and then compare literals.
- `NumbersMustNotBeARecord`: one Numbers value indexed with three or more different integer literals in a method, or `x(index * N + k)` strides (`value(0)`..`value(8)` poses, `grade(8)`, `metrics(4)`), about 350; `ListIndexMustBeNamed` for handle lists (`images(9)`, `clips(7)`, `sounds(6 + kind)`), about 100. Both want a type with members.
- `TestMustCallItsOwnMethod`: a leading test line that does not mention the method it sits in (tests parked under a neighbour to get around the method length, about 170 lines), with `MethodWithBranchMustHaveTest` for the methods left without one (about 50).
- `MethodMustUseItsInstance`: a method that reads no member and no `value` but is called through a constant or a made up instance (`Boost.None.Cast(...)`, `PlayPage.Sample.Described`, `GameApplication(0, 0, 0, 0, "", false).Images`, `RaceTrack.Empty.Loaded`), about 70; the other way round `OwnTypeParameterMustBeInstanceMethod` (`Accepted(room Room)` in Multiplayer/Room.strict, 13).
- One way to build a list: `mutable list = List(T)` + `for` + `list = list + item` + `list`, `List(Mutable(T))` + `.Add`, and the plain `for` expression all occur, about 65 loops are pure maps or filters (`AccumulatingLoopMustBeForExpression`); `List(Number) + x` and `(x)` both build a one element list.
- `MixedAndOrMustBeParenthesized`: `and` and `or` at one depth, or an `is`/`<` operand of them without parentheses (`a is false or b is 0` parses differently than it reads), about 60 lines against several hundred parenthesized ones.
- `ConstantValueMustBeDefinedOnce`: the same constant name and value in several types of a package (tick step 0.0625 and `16` 25 times in RealTimeStrategy, Tiles 15, ImpactScale 0.6), a literal equal to an existing constant, the same text literal three times (`"Content.xml"` 6, `"Google sign-in failed, please try again"` 5).
- Hand written base methods: `a > b then a else b`, `x < low then low else ...`, `a + (b - a) * t`, `text.Substring(n, text.Length - n)`, `(x / 2 ^ n).Floor % 2 is 1`, `x < a or x > a`, `.Round(0)`, `2 ^ 0.5`, about 60 (needs Maximum, Clamp, Lerp, a substring to the end and a bit test to point to).
- `BooleanParameterMustNotSelectBehaviour` and Number parameters used as one (`test is 0`, `motion > 0`), about 45.
- `CopyConstructorMustBeUsed`: `Type(a, b, c, changed)` repeating own members where `Type(value, member = changed)` exists (12); `NamedArgumentMustDifferFromCurrent` (`mines = mines`); `MethodMustNotOnlyReturnMember` (12); `MemberMustBeReadSomewhere` for members only ever copied (Attack.managedExternally).
- `ConstructorCallMustNameArguments`: more than four positional literals or two bare `true`/`false`/`0` next to each other (`UnitCommand(k, id, v, 0, false)`, `Attack(2, 0, 0, 1, false, false)`, 12 argument SpecialAbilityState), about 120.
- `TestMustNotTouchFiles`: tests and constants that write or list real files (`ArenaProfile.Empty.Saved` writes Profiles/Player.profile on every run, `constant Loaded = ArenaReplays(Directory.Files(...))`), about 15; engine packages whose tests load game content (Graphics3D/Scenery.strict, Weapon.strict).
- `SameCallTwiceMustBeLet`: the token equal call with arguments twice in a method outside the tests (about 30).
- `Up to date` could also say whether the program is running: a pid stamp written by each running program (like `obj/strict.server*`) makes that a file read instead of a 0.55 s process query.
- `GarbageCollectionExceedsLimit` and `GarbageCollectionAboveTarget` could also name the largest allocating call sites of the window.
