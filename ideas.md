# Ideas
Large features, difficult or long work and far fetched things, kept here until someone wants them. Not a to do list, lines may get deleted any time. Bugs go into `bugs.md`, speed work for soon into `performance.md`, while there are any.

## Features and long work
- VM frames without per-slot reference counting: a Vector2 call (about 20 us for `position + Vector2(1, 2) * 0.75`) spends 19 % in `Machine.Bound`, most of it counting the references of each frame slot (6 header slots, members, 8 constants, parameters); lazy constants, a copied frame template and indexed frame writes were each measured under 3 % (2026-11-26). Frames that borrow the values of their caller and only count what outlives the call would remove it.
- Owned list concatenation: `left + right` appends in place when `left` has room but still allocates a new 16 byte list view per call and counts the shared holder (`strict_list_concat_host` 22 % inclusive of a `Matrix.Inverse` probe, 2026-11-26). When `left` is owned and never read again, also across loop back edges (`MlirOwned.IsReread` only scans forward), the view itself could be reused like `strict_list_push` does.
- `GarbageCollectionExceedsLimit` and `GarbageCollectionAboveTarget` could name the largest allocating call sites of the window.
- Build speed measured (2026-11-24, `BuildSpeedAnalysis.md`, `STRICT_BUILD_PROFILE=1` on scratch copies): a one-line change in a small program takes 1.45 s of which link is 0.90 s; the Math folder cold takes 31-37 s of which emission is 22-27 s; the same folder all cached takes 4.6-7.1 s, spent re-reading and re-parsing `obj/Math.emitted` and redoing reachability, safety and GPU selection; Runtime tests cold take 66 s (frontend 14.8, emission 11.4, lowering 13.1, link 15.6); the warm VM stays 60-220 ms and is not the problem. Emission scales with loop bodies, not functions: Vector2 31 functions 0.17 s, Mandelbrot 30 functions 10.2 s, Matrix 50 functions 19.0 s, about 0.36 s per loop-heavy function, because every variant of a loop (CPU body, parallel fork, GPU kernel, fast loop) regenerates the whole loop text and `MlirDefaults.ParameterName` rebuilds the parameter list per copy. Parts already link incrementally (warm ThinLTO 0.37 s for an 11.9 MB exe), so per-method objects and a custom linker are not worth it yet.
- A dev build that skips ThinLTO (2026-11-24, option 7 of `BuildSpeedAnalysis.md`): the 0.90 s one-line-change link is ThinLTO re-optimizing the parts that import the change, so `strict build --fast` / `STRICT_FAST_BUILD=1` compiles parts to objects and links without it, taking a small edit from 1.45 s to about 0.6 s and the big link from 15.6 s to about 1 s; semantics unchanged, only speed and size differ, so keep it off by default (every dev run of a game or model 2-10x slower is a build nobody uses) and never in `Release/`. The same idea applied to emission is not available: the variants of a loop (CPU, parallel fork, GPU kernel, fast loop) are different programs, not optional optimizations, and the cost is regenerating text per variant, so option 5 (emit once, reuse) is the version that keeps the fast executable.
- Profiler results visualized (2026-11-24): the profile lines and stage times drawn live in the app instead of only in the console, for a web UI or a DeltaEngine game, and the console stays the default for everything else; only outside a release build and only when `STRICT_BUILD_PROFILE` or a new `STRICT_RUNTIME_PROFILE` is on, so no drawing, layout or upload code runs in a release or a plain build.
- A child that strict waits for ends with its parent on macOS too: Windows puts every Process.RunTool and Process.Started child in a kill-on-close job, Linux and Android give both PR_SET_PDEATHSIG (Process.Started forks instead of `system()` since 2026-11-23, checked in WSL), macOS has no parent death signal and still runs both through `system()`/fork without it; a fix (a kqueue EVFILT_PROC NOTE_EXIT watcher on the parent, or a pipe whose end closes with the parent) needs a Mac to test, `Runtime/CheckTests.strict` (CheckDeadline) is the check.
- Agent scratch runs, and only then agents drop Python for them (2026-11-14). A warm `strict serve` already holds the VM and the types, and native code that needs no linking and no GPU kernels is cheap, so a small program on top should be sub-millisecond and way faster than `python -c` on the same jobs (a file read, a numeric loop, a regex over text), not 10 ms against 100 ms. Missing first, taken from the 16 scripts agents wrote for the text-length work (`align`, `append`, `audit`, `emitter2`, `emitter_tests`, `fn`, `headers`, `helpers`, `lists`, `makers`, `makers2`, `makers3`, `readers`, `seal`, `twins`, `unseal`): `Text` regex with groups (every match, the captured pieces, a substitute, a whole-line match; the patterns are names, optional braces, escaped quotes and hex pairs). Read one file as one `Text` and write it back with the same `\n` or `\r\n` and no added blank line (`TextReader.ReadLines` and `TextWriter.Write` split and rejoin, which those scripts avoid with `newline=''`). Count of a piece of text, not one character (`text.count(anchor) == 1` before a replace; `Text.Count` counts a character). Repeat a text (`"\\00" * 17`). Root bytes, not `Compiler/MetalValue.Hex`: UTF-8 bytes of a text, a byte's value, a little-endian integer (`to_bytes`, `struct.pack('<qq')`), hex of one byte (`%02X`), and a scan of `\HH` escapes. The words after `strict run -c code` are the script arguments (`sys.argv` in every script). `strict run <Type>` and `strict run -c code` run on the VM, the default, and `-c` leaves no file behind. `strict <Type>` stays the native route. Already in the language, so not this work: `Split`, `Lines`, `Replace`, `IndexOf`, `StartsWith`, `EndsWith`, `Trim`, `Substring`, `is in`, `Directory.Files` with a pattern, `Path.FileName`, `Dictionary`. A Boolean line in a program is a test and does not run, so "exactly once" is an `Error`, not `is`. Measure every case against `python -c` before switching. Windows `cmd` and `.ps1` fail for rounds, `.py` less often and still often; Strict should fail less because code that does not build does not run, and a miss is cheap to retry. Until those features exist and the times hold, agents keep Python for throwaway glue.
- Faster LLM decoding on the RTX 4090 (2026-11-13): plain Qwen3.5-9B decoding spends 5.85 of 6.9 ms per token in products at about 900 GB/s, the rest are about 760 small kernels per token (norms, `DeltaBlock.Read`, quantizing the inputs) that a fusing GPU emitter could merge; MTP (5.5 ms per token, 2.67 of 3 drafts) would gain from tree drafts (runner-up tokens, a tree mask in attention, per branch DeltaNet states) and a DeltaNet replay with one thread per state column carrying its 128 numbers through the accepted tokens (0.5 ms per step), which a Strict loop can not express yet; the 4 token verify products read at 653 GB/s, 16 or 32 rows per block and longer chains were slower. Measured 2026-11-28: Qwen3-8B Q4_K_M batch 1 6.53 ms (153 tok/s), batch 4 7.15 ms (560 tok/s); Qwen3.5-9B Q4_K_M batch 1 7.17 ms (140 tok/s), batch 4 8.94 ms (447 tok/s); folding `HeadScales` into `Qwen3Block.Rotate` gave 6.53-6.58 ms (batch 1) and 8.06 ms (batch 4, reverted), and fusing `Normalize`+`quantize` alone saves at most ~1.2% (under 3%).
- Reusing results of unchanged calls: values are immutable and every result is consumed, so a call whose inputs (instance, arguments and what it reads) did not change since its last run can hand back the kept result instead of computing again, from `numbers.Sum` up to a pathfinding query on a big unchanged map. Needs purity per method (MlirPurity has a start), cheap change detection of the inputs (versions or hashes of lists instead of comparing them), a cache size limit and eviction, and only pays for expensive calls.
- A small page reused after a collection is cleared before its objects are handed out (strict_gc_small_page), also for texts the collector never reads: skipping it for texts made 20 million small texts 31.5 -> 29 ns each, but packed rows, gathered rows and other GPU blocks share the unscanned classes and may rely on zero padding; texts need classes of their own first.
- Two packages with a type of the same name in one executable (Left/Point and Right/Point): natively the symbols, register kinds and helpers use the short type name, a folder build stops with SameNamedTypes; qualify the symbols of a type whose short name is taken.
- On the web dead values can stay roots: Asyncify saves every local that is live at any unwind point of a function with whatever it held last, and the collector scans them (strict_registers_spilled). The old value of an owned local is freed when it is replaced (strict_rc_dead), so `moss = Loaded(model)` releases the old Moss; a value that is not provably owned (passed to a method returning it, aliased) can still be kept by such a copy until the local is reused. Precise roots (reference locals in a shadow stack frame the collector scans instead of the Asyncify locals) would cover all of them.
- Requests in threads of one server (the decided design, after several servers came first): a `for` runs in parallel when every effect of its body only touches resources the iteration owns (its accepted socket, its own output, files it creates), checked by MlirPurity; the pool takes jobs of several threads (one busy flag today, inner loops of a second request run serially); blocking natives (accept, receive, waiting for a process) count as stopped for collections; full collections inside long jobs; Process.FilesRead and claims per request. Served timeouts: a test over its time inside one long native call is reported but not counted, a gone caller is only noticed while VM work runs.
- OutOfMemory, crash reports and STRICT_ALLOC_PROFILE name the Strict methods on the stack on Windows and Linux; macOS uses the same unwinder calls (untested), strict_stack_starts on the web returns no frames yet.
- Nightly CI: build and run every program's Run once a day (games and long running apps for a few frames); work too slow for a Slow test (rebuilding all content, big models) belongs in a Run, not in tests.
- Networking: `Http.Send`, `Http.Started`/`Received` and `Hmac.Sha256` are in (Windows, Linux and the web checked, macOS untested), DeltaEngine's Google sign-in and sheet downloads use them: switch Rebalancing's `NativeIO.Http`/`Hmac` (with the user, it trades live); client certificates when a program needs them, TLS for multiplayer sockets later.
- f32 kernels: a GPU loop reading a `value.Bits is 32` member computes in f32 (WGSL on WebGPU, the 32 bit CUDA kernel natively); WGSL lacks rows.
- MossWeb WebGPU experiments (RTX 4090, headless Chrome, 2026-11-28): `strict_eights` 64x128 tile (1779 vs 1354 ms, lower occupancy, reverted) and 128x128 tile (>24 s DXC compile, reverted); `strict_products_f16` (48.0 vs 48.3 ms, changed JPEG output, reverted); `WebRuntime.js` zero-alloc dispatch + batch 128 (1883 vs 1908 ms warm, ~1.3%, reverted).
- A plain `strict build` of a program that opens a window or has a `.shell.html` (StrictGen) also refreshes Release/<Platform> (`Release.Package`, 2026-11-23): a dev build with debug checks overwrites the release executables the owner commits; only a platform build (`windows`, `linux`, ...) should write there, a plain build stays next to the source.
- Release builds: platform builds into Release/<Platform> are optimized without debug checks, logging or per-call checks (the web runtime already is), plain `strict build`, test executables and the VM keep them; native needs a release flag on `strict build` for local benchmarks.
- Named iterators over counts (`for row, column in rows, width`) as one flat loop of rows * width with the names from the index (parallel, GPU kernel), then the `(index / n).Floor` and `index % n` loops of NeuralNetworks, Math/Matrix and the image decoders can name their iterators without losing their kernels.

- `strict check Compiler` logs 44 `PackageDependenciesMustNotCycle` edges between Compiler and its sub-folders (Checks, Gpu, Mlir, MlirDevice, MlirLoops, MlirStructs, MlirValues), only a warning (exit 0): Packages.md layering breaks them.
- 32 bit member layout (memory model step 3, designed 2026-11-26, not built, not measured): A type made only of numbers (directly or through such member types) gets a layout table (offset and width per member): members constrained with `value.Bits is 32` take 4 bytes, others 8. Its blocks are leaves (allocation kind 32, never scanned), so two floats in one word are never read as a reference by the collector or by `strict_rc_release`. Construction already rounds with `strict_single`, reads widen exactly, so results do not change. Every reader of member slots goes through the layout: FieldLoad, unpacking of `value`, the inline blocks of record lists (slot bytes instead of slot count), equality, `to Text`, `strict_records_flat` for GPU loops. Types with any reference member keep 8 byte words.
- Incremental marking for bounded pauses (memory model step 4, designed 2026-11-26, not built): the longest pause of ParticleStress 1M is its one full collection while it spawns (87 MB marked): 38-58 ms since a full collection of a heap over 64 MB starts the pool before the first parallel loop and its workers help the marking (median 91 ms on one thread before, 9 runs each, 2026-11-26); young collections take 10-25 ms, the 100 ticks have none since lane recycling. , incremental marking for framed programs (`strict_frame_ended`). A full collection becomes a cycle: start (roots pushed, a few 100 us), slices at frame ends that drain the mark stack for a time budget (1 ms), finish (stacks and dirty cards scanned again until the stack is empty, then the lazy sweep that exists). Invariant: a marked object never holds an unmarked one without its card being dirty; all stores already mark their card (`strict_gc_written`, `strict_gc_card`, `strict_rc_put`), objects allocated during a cycle are born marked, stacks count as unscanned until the finish. A block freed by its count during a cycle loses its mark, a stale entry on the mark stack then scans cleared memory or a link (not a reference). No slice runs inside a pool job; a young collection due during a cycle finishes the cycle first (logged as one pause). Programs without frames keep the stop-the-world collection.

## Model: Ternary Bonsai 27B
the Bonsai GGUF, 12.7-18 ms per token on the RTX 4090 (Prism's llama.cpp ~11); per token (ncu) the products take ~8.7 ms, the quantize kernels ~0.6. Left:
- 5 to 8 tokens in one kernel (like Kindi's) so `LookupDecoding` verifies cheaper: 1 to 4 tokens take `strict_device_tokens` since 2026-11-28 (two 3 bit rows per warp read each token once, the 4 token kernel was L1 bound at 18 % DRAM), 1, 2, 3, 4, 8 tokens 11.1, 14.1, 16.0, 18.1, 32.4 ms per step (3 and 4 were 25.4 and 26.4 on `blocks`); 8 tokens as two 4 token chunks were 37.8 ms, one lane decoding a whole PTQ1_0 block instead of half was slower (12.0 and 30.6 ms for 1 and 4)
- CPU loops unpack 3 bit rows to doubles (`MlirWidths` decodes only 4 and 6 bit blocks per use)
- per decode token (nsys, `STRICT_GRAPHS=0`, 2026-11-28, after 3a42cf19 moved the norm scales into their loops): 1741 kernels, 11.0 ms of GPU time, decode median 10.9-11.2 ms with graphs; products (`strict_device_token1s`, 305) 7.8 ms at about 765 GB/s of the ~1 TB/s card, the rest 3.2 ms in small kernels: `Sylvester` 258 x 2.4 us 0.63 ms (each feeds the next product, the per token quantize scale needs the whole rotated vector, so it does not fuse into one block), `DeltaBlock.Read` 96 x 4.8 us 0.46 ms (the step reads the state twice; one pass over the old state could give both reads, the output is d * S^T q + (q.k) * beta * (v - d * S^T k); 2026-11-28: `ReadBoth` + `SteppedReads` tested on Qwen3.5-9B batch 1 gave 7.21 ms / 139 tok/s vs 7.17 ms / 140 tok/s baseline, reverted; Bonsai 27B GGUF not on disk), `Qwen3Block.Normalize` 129 x 3.6 us 0.46 ms, quantize 305 x 1.07 us 0.33 ms, `DeltaBlock.Update` 0.26 ms
- 10 GB budget: a holder process does not simulate it on Windows (the budget never saw the holder), capping the driver's free memory at 10 GB in `strict_gpu_free_memory` does (budget 8.5 GB, peak 10.0 GB in use, the same in cold and warm runs). Then 64 tokens decode in a median of 22-24 instead of 12-14 ms: per token 3-4 of the 12 CUDA graphs are instantiated anew (5 ms, 1 ms destroying, 9 instead of 12 updates), 3-4 cuMemAlloc/cuMemFree (2 ms), the result download waits 7 instead of 3 ms; 2 tokens per run take ~290 ms freeing and allocating ~100 buffers (one uploads 298 MB)
