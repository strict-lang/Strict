# Improvements
In priority order. Remove what is done, add what is found. Every item gets done before the bigger image processing and neural network examples, parallel loops and GPU (decided 2026-10-12).

1. **Neural networks** (the use case): `NeuralNetworks/` has a multilayer perceptron written in Strict (see its README): `Layer` (fully connected, sigmoid, one weight row per neuron), `Network` (backpropagation over any number of layers, softmax with cross entropy for several outputs, momentum 0.5, weights start in plus minus 1 / square root of the inputs), `Csv` and `Dataset` (features scaled to 0..1, one-hot classes, every fifth sample held out, a new random order every epoch). Natively XOR (2-3-1) trains in 11 ms, Iris (4-8-3) in 25 ms with 97% test accuracy, Diabetes (19-10-2 on a quarter of the UCI Diabetic Retinopathy Debrecen data, 288 rows) in 80 ms with 60-64%. The MNIST digits moved into their own repository (github.com/strict-lang/Mnist, `../Mnist`): 256-32-4 neurons reach 100% on 32 held out 16x16 images in 0.49 s natively (58 s on the Strict VM), 784-64-6 neurons 68-82% on 28x28 images in 2.8 s. Every step still builds new lists for the activations, deltas and weights, and a method call with loop-invariant arguments runs on every iteration natively (the compiler could hoist it). A `for` over a list or a count whose body only loads variables, calculates numbers, reads lists at `index` and collects one value per element runs twice compiled (`Compiler/MlirKernel`, `MlirFastLoop`): when every list read at `index` is at least as long as the loop, a copy with an integer counter, direct loads and direct stores into the presized result runs (LLVM vectorizes it), otherwise the checked loop, where a too short list stops the method with the index Error. Measured 2026-10-14: an element-wise update of 784 numbers 3.15 to 0.75 ns per element, a dot product 1.12 to 0.35 ns, MNIST 256-32-4 0.48 to 0.12 s, 784-64-6 2.74 to 0.86 s, Iris 27 to 20 ms. Now about 38% of the 784-64-6 training is allocating and collecting (`strict_gc_allocate`, `next_span`, `memset`, mark): every step builds new weight rows, the previous weights are kept for the momentum and the ones before become garbage. Native code is built with `-march=native` and the add of a sum in such a loop (`sum = sum + ...`) may be reordered (README), so LLVM vectorizes sums (AVX2 with 4 or 16 partial sums). Loops with calls (`activation.Output(...)`, `Row(...)` per row) still take the checked path. On the Strict VM every number is a `VmValue` with four members, each arithmetic result allocates one. Next: bigger networks to measure parallel `for` on all CPU cores, SIMD, GPU and CUDA through MLIR, compared with the C# version. Data over 1 MB is downloaded when needed instead of being checked in. The old C# code in `C:\code\AiInvest\AiInvest.NeuralNetworks` is only a guide, it has bugs (MatrixNetwork backprop drops the hidden gradient, the Tanh, Swish and Logistic derivatives, CrossEntropy ignores the target). Long term a more abstract language uses Strict like DNA: long chains of simple instructions that are easy to copy, change, merge and test, which the higher level rewrites, tests and evolves to reach its goals.
2. **Evolutionary algorithms and more neural networks** (asked 2026-10-13): `NeuralNetworks/Weasel.strict` evolves a random text into "METHINKS IT IS LIKE A WEASEL" by mutation and selection (45-95 generations of 100 children, 2-5 ms natively), `Neuroevolution.strict` evolves the weights of the 2-3-1 XOR network instead of backpropagating them (tournament selection, uniform mutation, the best network survives: error 1e-13 after 300 generations of 50 networks in 46 ms). `LogicGates.strict` learns Or, And, Nor and Nand with single neurons (`Perceptron`, from AiInvest's LogicTests) and builds Xor from three, `Optimizer` adds Adam and RMSprop (`OptimizerComparison.strict`: below 0.01 XOR error after 2000 steps where momentum is still at 1), `Recurrent` with `BinaryAddition.strict` learns to add 7 bit numbers (100 of 100 new sums after 10000 examples in 0.29 s), `MachineLearning/` has k-means, k nearest neighbors, Gaussian naive Bayes, a Gini decision tree, a random forest (Iris: 88.7% cluster purity, 96.7% test accuracy for each classifier) and an order 5 Markov chain over downloaded Shakespeare, `ArmEvolution.strict` evolves the joint angles of an `Arm` (modified Denavit-Hartenberg rows) to a target, the 7 joints of a Franka Panda within 0.2-1.1 mm in 136 ms natively (the AiInvest version only added up angles), `LinearRegression.strict` reaches the least squares line by gradient descent, `Activation` adds Tanh, Relu, LeakyRelu and Softplus with correct derivatives (`ActivationComparison.strict` on Iris: all 97-100% except plain Relu). Next, simplest first, from AiInvest (`X:\AiInvest`, deleted projects are in its history) and BrightWire (github.com/jdermody/brightwire, 18 samples in `ExampleCode/Program.cs`, `ReberPrediction.strict` with a GRU learns the embedded Reber grammar where an Elman network stays at chance): swish (its derivative needs the weighted sums, which `Network` does not keep: recomputing them costs another matrix product per layer in every step, AiInvest's Tanh, Logistic and Swish derivatives and its CrossEntropy are wrong). Only small inline data, bigger samples get their own repository like Mnist.
3. **DeltaEngine performance** (measured 2026-10-14): natively 1224 sprites interpolating a `Vector2` and building their 13 instance numbers take 0.12 ms per frame (3.5 ms on the Strict VM), 1M `position = position + Vector2(0, 1)` 21.7 ms (1.3 µs each on the VM), 1M replacement constructors `Unit(unit, health = unit.health - 1)` 5.7 ms (1 µs on the VM), element writes into a 9216 number grid 1.1 ns each (225 ns on the VM, in place on both). Natively an allocation is cheap, the VM spends its time in calls. The VM reads members like `X` (`numbers.X`, `elements(0)`) without calls: `Runtime/Accessor` finds the member path of methods that only return a member or a constant element of one and `Frame` follows it, anything else (out of range, an Error) takes the normal call (sprites 2.6x faster than with three frames per `X`). Open: `+`, `Lerp` and constructors are still full calls on the VM (`Bound` fills every member slot, `Constructed` checks `IsStruct` by name every time), assigning a replacement or `position + offset` back to the same mutable variable could write the instance in place, types made only of numbers (Vector2, Size, ColorValue) could be stored flat (a `List(Vector2)` as one array of doubles).
4. **Tooling**: `.github/workflows/ci.yml` bootstraps from the seed on Linux with the LLVM 22 release archive, self builds until the fixpoint and runs every test on the Strict VM and natively (validated in a fresh WSL clone). A Windows job builds the same way with `mlir-opt` and `mlir-translate` from MSYS2 and clang from the LLVM 22.1.0 release (validated with a fresh clone and the local tools). The LanguageServer in Strict (the C# one is on the `dotnet` branch) waits until after the parallel loops and GPU (decided 2026-10-13, it needs console input and a JSON package), the VS Code client calls `strict` meanwhile: it reads the method headers itself for completion, hover, go to definition and signature help, suggests implementations from the tests of a method and reports methods that already exist (`MethodAlreadyExists`), both by running `strict test` on a temporary copy per candidate call (40 ms each). `strict check` reports a method whose implementation (without its tests, at least 40 characters, not calling methods of its own type) copies another method of the folder or the base types as `MethodAlreadyExists`, a method whose tests a method of a type it uses passes is not found yet (exactly one way to solve each problem). Also not reported yet: an argument of the wrong type for a constructor (`MlirLines(value)` inside a `for` over instructions built an `MlirLines` from an `InstructionEntry`, the VM ran it, natively it crashed). `1e-5` is three tokens (`1e`, `-`, `5`), only exponents without a sign like `1.99e9` are number literals. Later the search for implementations belongs into Strict too (`strict suggest <file> <method>` with real type inference, all candidates verified in one process instead of one each). `strict test <file> lines` builds the tests natively with a counter per source line (`Compiler/MlirLines`) and prints `Line <file>:<n> executed N times in X ms (self Y ms)` for every line of the compiled methods and of the untested methods of the file (0 times), X includes the callees (recursion counts twice), Y does not. For the VS Code client, in this order: several files or a folder in one native build (`strict test . lines`, one build per file takes minutes for a folder); a trace of one test printing the value of every implementation line (shown inline), later the Debug Adapter Protocol in the VM (breakpoints by line, stepping, frames and variables from the `Frame` slots). A method named like a type hides the type in its file: `AdjustBrightness.Process` makes the test runner's `Process.Elapsed` call the method, the VM logs `Unsupported native call Strict/ImageProcessing/Image.Elapsed` and every test of the file prints `(() ms)` (`strict check` should report such a method or `Process.Elapsed` should mean the type when the method result has no `Elapsed`, which needs `TypeInference.ArithmeticType` to keep the type of its first operand instead of inferring it again). A `.strictbinary` stores a type whose own `.strictbinary` in the same folder has the same methods as a `Name.reference` (the indexes of the methods it uses), DeltaEngine/WebWars went from 2.58 to 1.20 MB of bytecode (a cold `strict test Compiler` takes 3 s longer for the repacking). Copies of types from other packages and of base types are still inlined (22% of WebWars): their names differ by package (`Strict/RealTimeStrategy/Unit` there, `Unit` in its own file), so referencing them needs the names mapped on load. The `sources` entry of every file lists all source paths again (10 KB per file in WebWars). Errors are handled where they show up (README "Rules worth knowing", `Examples/ErrorHandling.strict`): the compiler emits a `CheckError` instruction (`Bytecode/ErrorCodegen`, `ErrorScope`) before every other use of a value that may be an Error, the VM (`Runtime/ErrorCheck`) and native code (`Compiler/MlirChecks`, a tag test and an early return) stop the method there. It made `strict.exe` 7% and the bootstrap seed 28% bigger and the Strict VM tests about 10% slower: a method that can never return an Error (no Error constant, no failing native, no index or key access) could skip the check of its results. Still open: README says every expression statement must evaluate to true, but a dropped Boolean or other non-Error value is not reported yet. The runtime keeps `strict_list_*_number` and `_text` only for compilers built before the equality functions were passed, they can go once no older compiler builds stage 1.
5. **Reflection** (later, only as use cases need it): `"Number" to Type` builds `Type("Number", "Strict")`, `5 to Type` (any other value) is its static type and `value is Number` is decided at compile time from the static type, on both backends. `value.Members` lists the stored members of an instance as `Variable`s (name, static type, value) and `HashCode` of an instance combines the hashes of its members: the compiler writes `Members` and `to HashCode` for every type that uses them (`Bytecode/Automatic`). Not supported yet: `to Type` of a Text that is not a literal (needs the type names at runtime), natively the value of such a `Variable` is a `Generic` without its type, it can not be printed or compared yet, the `Method` of a `Stacktrace` is its `Type.Method` text on both backends (a `Method` value needs the methods at runtime).

## Member defaults (2026-10-14)

Literals, constants, empty `List(...)` and `Dictionary(...)` and one-member types with literal arguments (`has start Vector2 = Vector2(0, 0)`) are member defaults on both backends, any other default (`= Size(1, 2)`, `= Created(data)`) is an `UnsupportedDefault` error before anything runs (it was dropped silently). Text and text list defaults (`has label Text = "Names"`, `has names Texts = ("a", "b")`) build natively too: their texts are module globals per type and member (`@dLabeled_label`, `Compiler/MlirDefaults`, `Examples/Labeled`), a constructor anywhere references them.

## Constant aliases of chained constants
`constant Labeled = TypeCodegen(...).Entry` in `Compiler/MlirDefaults` works there, but `constant Labeled = MlirDefaults.Labeled` in another type is typed as `TypeCodegen` instead of `TypeEntry`, so `Labeled.members` gives `Unsupported native call Strict/Bytecode/TypeCodegen.members` on the VM (ResolveCheck.ChainType seems to give up on that expression and the plain constructor type stays).

## Loading and using safetensors (2026-10-14)

Allow to load safetensors files and do some basic operations on the data in them with the long term goal to use llm models and utilize stable diffusion. Something like https://github.com/syoyo/safetensors-cpp no need to reinvent the wheel, if there is something working and usable, we should be using it. Important thing here is to get it into a working mode so we can do some actual tests on the loaded data, convert it into a GPU efficient format, execute parallel operations on it, etc. Use something like GPT2 to test parsing a medium big model (528MB) and where performance difference would be noticable: https://huggingface.co/openai-community/gpt2/resolve/main/model.safetensors obviously we are not going to run something that won't fit on our hardware, so we will keep things in consumer hardware range (24-32gb gpu vram max, 128gb ram, 128 hyperthreads cpu threadripper, maybe using multiple consumer pcs together, but this is usually very hard to sync)

Working (see `NeuralNetworks/README.md`): `Safetensors` parses the header in Strict, `native/TensorFile.c` reads float32 tensors as doubles (`Values`) or as rows of 32 bit floats or 16 bit halves (`Rows`, `Columns` transposed, `Safetensors(path, 16)`), `Gpt2Text.strict` runs GPT-2 124M natively token for token like PyTorch. Measured 2026-10-14 on one core of an i9-13900KF: doubles 102-107 ms per token, vectorized sums 61-75 ms, packed 32 bit rows 35 ms (load 0.65 s, same text as PyTorch), 16 bit rows 26 ms (load 1.3 s, the 15th generated token differs: "computer" instead of "machine"); PyTorch 24.6 ms (one thread) and 22.1 ms (24 threads), numpy picoGPT 476 ms. Packed rows come from C (`strict_packed_result`), a `for` adding them up reads them directly (`Compiler/MlirPacked`: one loop copy per packed source and width, chosen by `strict_list_packed`), anything else unpacks a row into doubles once. Parallel rows (`Compiler/MlirParallel`, `MlirPurity`, a worker pool in the runtime) bring it to 12.6-13.5 ms per token with 8 threads (PyTorch 22.1 ms on 24 threads): 64% of a token is in the parallel loops at about 31 GB/s (DRAM gives about 70 GB/s), 4.6 ms is serial (attention per head, layer norms, small lists, collections), 31 worker threads were slower (spinning workers slow the main thread). Per row a `Summed` call still checks its lists and the rows of a matrix are separate allocations. Next: GPU kernels generated from the same Strict loops (MLIR nvvm, verified: a vector add from MLIR runs on the RTX 3080 at 670 GB/s), then 8 bit weights (Q8_0) and GGUF models (Qwen3 MoE). GPU plan (2026-10-14): pure collecting loops whose bodies are simple numeric code after inlining pure calls (`MlirParallel.IsParallel`, `MlirKernel` instructions) become nvvm kernels in a device module (`mlir-translate`, `clang --target=nvptx64`, PTX embedded in the executable), an inner reduction (`Layer.Summed`) runs one warp per row; the runtime loads `nvcuda.dll`/`libcuda.so.1` itself (no CUDA toolkit needed to run), keeps a device copy of every list a kernel read (keyed by list block, length and items, released after a garbage collection finds the list unreachable), uploads the rest and falls back to the CPU without a GPU. Measured with a throwaway CUDA kernel (all 49 GPT-2 matrix products per token, 248 MB of F16 weights, RTX 3080): 1.89 ms per token accumulating in f64 like Strict's Number (131 GB/s, the 3080 does f64 at 1/64 speed), 0.59 ms in f32 (424 GB/s), the CPU spends about 8.5 ms per token there. Whether 16 bit weights may accumulate in 32 bit is a decision for later. Done so far (2026-10-14): loops become kernels (`Compiler/MlirGpu`, `MlirGpuCheck`, `MlirDevice*`), `Layer.Sums` runs one warp per row with f64 sums, device copies of lists of at least 64 KB (pinned, least recently used of 128 freed), rows unpacked by the CPU are narrowed back exactly. GPT-2 over 100 tokens on the RTX 3080: 12.8 ms per token with only the output layer (77 MB) on the GPU, 13.4 ms with every matrix product there, 15.1 ms on the CPU alone (20 tokens include the CUDA startup). A launch costs about 150 us of copies and synchronization (Nsight: kernels 35 us average for the 768 to 3072 row products), so the next step is keeping results on the device between loops (a list whose data lives on the GPU until the CPU reads it) and fewer copies per launch, then 32 bit sums for packed weights if wanted. Only F32 tensors are read (others are `OnlyFloat32TensorsAreSupported`). The Strict VM can not hold the real model.

## Optional deflate for bytecode ZIP caches
Bytecode/ZipWriter writes stored entries and ZipReader does not inflate compressed content or reject unsupported compression methods. DeltaEngine LogoApp cache is roughly 42 KB and compresses much smaller. Optional native deflate support could reduce distribution/network IO; measure read-plus-inflate latency before enabling for local cache performance. Keep cache integrity and freshness checks; do not add copies of engine sources.
