## Next
1. **CI complete and fast**: `.github/workflows/ci.yml` runs the bootstrap, one self build and the VM tests of the fast folders (Linux about 5 minutes with `Examples`, Windows only the quickest folders, 10 at most). Add `Validators`, `Runtime`, `Expressions` and native builds back while it stays under 10 minutes; a failing native build prints the file and exit code. CI, `Toolchain.LinuxRelease`, `bootstrap.sh` and `MacOSTools` still use LLVM 22, move them to 23.1.3 like Windows (msys2 LLVM 23 needs cc-libs and gcc-libs 16, clang 23 too: LLVM 23 writes float literals as `f0x...`, which clang 22 can not read).
2. **Faster builds**: a gated program builds twice (`Name.test.exe`, then `Name.exe`, each compiling the bytecode from source), one bytecode load for both would save the second generation; native gates write no `.strictbinary`; generation is single threaded (10.8 s of `MlirModule.Declared` for `strict.exe`); the host build waits for the PTX; `--mlir-disable-threading` was needed for a threading race in 21.1.7, with 23.1.3 threaded runs give identical output (mlir-opt of `strict.exe` 4.2-4.7 -> 3.55 s, mlir-translate 2.5 -> 2.3 s): drop it once every platform uses 23.
3. **16 bit lists on the GPU**: bfloat16 lists (format 17: the high half of a float, same range, 8 bits of precision; Moss residuals reach 41472, f16 could overflow) are read everywhere (strict_device_elements, host unpacking, the guarded body, the int8 products epilogue, attention, quantize, hadamard, products and convolution) and written when strict_gpu_run gets format 17, but no generated loop asks for it anymore: when every loop of 2^20 numbers and more stored bfloat16, Qwen3.8 prompts of 1366 tokens and more decoded NaN (the pair matrices of `DeltaChunks`, even elementwise ones like `Unit`, feed the triangular inverse, which amplifies their rounding) and MossImage mix720 took 583-592 instead of 540-550 ms per step. Next: a rule for which loops may store 16 bits (activations that only 16 bit or int8 tensor core kernels read, not inputs of sums or inverses), measured on MossImage mix720 for speed and error. Lists joined with another format go through the host.
4. **Qwen3.8 for the robot arm**: MTP drafting 15.3-15.6 ms per token over 150 tokens (3 drafts, 2.78 tokens per step, Ollama's text), Ollama 13.3; plain decode 22 ms, prefill 1.38 ms per token at 460 tokens, 2.17 at 1370 and 2.95 at 2000 (Qwen3-8B stays at 0.15-0.17 ms up to 3720 tokens: find what grows). Hardware accelerated GPU scheduling (HwSchMode 2) changes nothing: MTP 16.3-18.2 ms, plain decode 21.7 ms. A step is about 43 ms, the GPU busy 62 % of it (about 1800 launches per step, 59000 in 1.5 s): the host feeds 15-20 us per launch, so the DeltaNet replay of `Truncated` (per token `Updated` and `Read`) and the first segment after every download run the GPU dry (gaps of 1.7-2.9 ms each, `cuGraphExecUpdate` 0.15-0.5 ms and `cuGraphLaunch` 0.4-0.9 ms per segment under WDDM, 31 % of the busy host samples); restarting segments at 8 after host waits moved the gaps instead of removing them. Collections are 9 % (162 young and 6 full of 24 ms per 150 tokens), a live tokenizer makes a full one 107 ms (its million objects: keep the vocabulary in one text with offsets). Next: fewer launches per layer (quantize 185 and Scales 185 per step: Scales fused into Normalized, 8 bit inputs written by the producing kernels), one kernel per DeltaNet layer for the replay (a thread per state column loops over the kept tokens, the columns are independent), cheaper segments; speech to text, a small Strict endpoint the arm calls, the time from question to first sound. A loop calling `Length(start)` in `Corrected` stays on the CPU (find the rule in `MlirGpuCheck`).
4b. **Qwen3.8-Flash-Next (qwen4exp, `C:/code/Models/FlashNext`, 111 GB, Strata approach)**: spec in the session scratchpad (`flashnext_spec.md`, from llama.cpp `src/models/qwen4exp.cpp` at 3cf03257). Done: `HyperStreams` (4 streams, Mix/Combine), `Ngrams` (n-gram rows with exact 64 bit hashes in 32 bit halves, gate, dilated conv taps), `DeltaBlock.sigmoidGate`, Q5_1/Q5_K/IQ4_NL decoding in GgufFile.c. Left: split shards, shared expert with its sigmoid gate, the rest of `build_ple`, the layer schedule (attention every 4th layer, no output norm), experts in RAM computed on the CPU with a GPU expert cache, the QSA indexer (exact dense attention up to 2051 tokens).
5. **GPU memory at the edge of the WDDM budget**: lists on the GPU are freed by their counts at a missing block (strict_rc_reclaim, device flag 64), so MossImage at 720x1280 runs without full collections per step (95 % GPU busy, 470 ms); with ~0.9 GB used by other programs the pool sits at its 256 MB headroom and still has 1-8 full collections, 2-5 cuMemAlloc/cuMemFree/cuCtxSynchronize and ~100 young collections per step (462-499 ms, was 1.5 s): a sub-allocating pool (any free block serves any size) would end that; the arena wrap synchronizes every second step; MossImage's per-step reference list (7 MB) is only freed by a later collection.
