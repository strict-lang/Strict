## Next
1. **CI complete and fast**: `.github/workflows/ci.yml` now tests every folder on the VM, a process per file on all cores of each runner: Linux base (the quick folders, Runtime, Expressions, Networking, Json, Xml, Binary, native builds of the small packages), neural (NeuralNetworks, `Layer` natively), Compiler in two halves, Windows the quick folders. Estimated 5.5-7 minutes per job from the local CPU times (Compiler 1581 s, NeuralNetworks 764 s, Bytecode 298 s); check the times and failures of the first push (Compiler and NeuralNetworks never ran on a runner), then more native builds while each job stays under 10 minutes.
2. **INT8 attention like ComfyUI's comfy_kitchen** (../StrictComfy/Performance.md, 2026-10-25): ComfyUI's `int8_attention` (Q and K rotated by a Hadamard of 128 before int8, int8 V, uint8 shares) runs H3's step in 2.06 instead of 3.22 s, Sol-Attn on top (each 64 token block attends the key blocks whose pooled proxy score clears tau sigma exactly, one pooled term for every other block) in 1.57 s. `Attention.quantized` (H3 sets it) quantizes the keys once per launch with a scale per position and head and multiplies them with per row quantized queries in m16n8k32 (`strict_device_attention_scores_eights`): one H3 launch 40.8 -> 31.1 ms under ncu, steps 0.34-0.43 s faster, errors against ComfyUI unchanged (video 0.236, audio 0.084). Quantizing the keys in the kernel instead was slower (every block of a head quantized all its keys again). Next, from ncu: the tensor pipe is 53 % busy, 35 of that the f16 PV products, so uint8 shares times int8 values (sums converted on the FMA pipe, not I2F); tiles of 64 positions (the per tile fold, barrier and softmax bookkeeping are amortized over 32 keys); the Hadamard on Q and K; then Sol's routing.
3. **16 bit lists on the GPU**: the rule is explicit, a GPU loop of a method returning `BFloat16s` stores bfloat16 (MossBlock.Modulated and Activated, which only int8 products read), never by size alone (bfloat16 in every loop made Qwen3.8 prompts of 1366+ tokens decode NaN, `DeltaChunks` feeds a triangular inverse). Open: (a) bf16 QK attention beyond the 128 wide QKV path; (b) attention, product and hadamard results are 32 bit; (c) joining lists of different formats goes through the host; (d) LLVM 23 PTX of strict_device_whole(s) is ~3 % slower than LLVM 22's.
4. **Ternary Bonsai 27B** (`C:/code/Models/Bonsai`, NeuralNetworks/README.md): 12.7-16.4 ms per token on the RTX 4090 (Prism's llama.cpp ~11); per token (ncu) the products take ~8.7 ms, the 257 `Sylvester` kernels ~1.4 ms, the quantize kernels ~0.6. Next: (a) a `Sylvester` kernel takes ~5.5 us for 50-170 blocks, latency bound by its 10 radix-2 stages with a barrier each: radix-4 or radix-8 stages in registers (fusing it into the quantize was slower); (b) on 10 GB cards steps stall (median 20, mean 313 ms): check StrictComfy's 256 MB own reserve (6c) there; (c) the dot products decode every PTQ1_0 block twice, the two lanes of a block should split the codes; (d) one kernel for 1 to 8 tokens (like Kindi's) so `LookupDecoding` verifies cheaper (2, 4, 8 tokens 27.7, 37.3, 47.2 ms against 16.8 for one) and keeps the tokens of plain decoding; (e) CPU loops unpack 3 bit rows to doubles (MlirWidths decodes only 4 and 6 bit blocks per use).
5. **Qwen3.8-Flash-Next** (qwen4exp, `C:/code/Models/FlashNext`, NeuralNetworks/README.md): ~280 ms per token, 325 with MTP drafts. Next: (a) the draft acceptance on a chat prompt with a longer answer and with 3 drafts (llama.cpp reports 89 %, here 7 and 12 of 24); (b) the 3 token `Steps` costs ~1.5 plain steps; (c) the QSA indexer past 2051 tokens.
6. **GPU memory at the edge of the WDDM budget**: H3 DiT steps (21.7 GB of weights, 37 of 50 blocks resident, the rest streamed) take 3.6-3.8 s against ComfyUI's 3.3 s, about 230 ms of that idle; ComfyUI streams too (47 GB of uploads in one 8 step run) but overlaps it (60 ms idle), so the target is overlap, not fitting. Left: (a) uploads still wait in order where the prefetch chain (`strict_gpu_prefetch`, one spill ahead) breaks: prefetch two rows or a block ahead; (b) power of two size classes keep ~1.9 GB of H3's pool unused (7 blocks of 512 MB for 319 MB lists, 1 GB for ~600 MB); finer classes churned activation blocks through the driver, they need activations kept and weights evicted first, or blocks lent across classes; (c) without spilled rows the trim before an own block runs at every block (40 of 50 blocks: 440 driver allocations and 200 syncs per step, 9.5-12 s against 2.8 s with `%ownReserve` at 256 MB instead of 1 GB); (d) measured 2026-10-25, not taken: rows with one scale uploaded with that scale alone for strict_device_whole (372 instead of 417 MB per block, 44 of 50 blocks resident) with a reserve halved whenever a trimmed class came back ran 3.9-4.2 s per step (a 1 GB activation block and the re-uploaded weights pushed each other out, a 1 GB cuMemFree per block), with uploads taking over spilled rows until 1.25 GB are free 3.82-3.84 s against master's 3.70-3.77 s; (e) MossImage with ~0.9 GB used by other programs still has 1-8 full collections per step: a sub-allocating pool would end them.
7. **Loading big safetensors at file speed**: the 21 GB H3 DiT loads in 10-12 s (ComfyUI 4-7 s), mostly page faults of the copy into fresh memory (~5 GB/s on 48 threads), and its first step uploads all of it: 10.1-10.6 s instead of 3.7 (14.4-14.9 before tables up to 256 MB went through the pinned staging buffer), the rest is the gather of each table on one thread (~45 ms per 165 MB) before its synchronous copy. Next: gather on the pool threads into two pinned buffers while the other one copies, then 8 bit rows that stay in the mapped file and are gathered from it (no copy at load).
8. **Generated GPU loops: vector coverage and fused memory passes**: they are instruction bound on the RTX 3080 (120-330 instructions per number). Left: (a) format mixes without an AOT copy (`MlirFormats` has all f32, all bfloat16 and first bfloat16) run the generic kernel: H3's `Rope.Rotated` with 16 bit norm weights 192 against 80 ms per step, Gated f32/bf16/f32; (b) a loop reading a member of an object parameter (`layout.width` in ../StrictComfy `H3Final.Unpatched`) stays on the CPU: pass loop invariant members as numbers; (c) bounds, reduction and tail checks remain, extend the four wide loads (`MlirBatched`) where counters show headroom (H3) and fuse memory passes. Details: `../StrictComfy/Handoff.md`.
9. **Trees as pools with 32 bit backward offsets** (from [Goose](https://github.com/aardappel/goose)): an immutable value is built after its members, so a type holding instances of itself (`SyntaxNode.children`) can keep all of them in one grow-only block linked by u32 backward offsets, one free per tree. Measure SyntaxNode allocations and bytes per `strict build Strict.strict` first.
10. **Small parallel loops cost up to 0.8 ms once the workers sleep**: every collecting loop of 256+ elements goes to the pool (`MlirParallel`), `List.Slice` of 1024 rows takes 0.4-0.8 ms (serial ~20 us) since waking 47 sleeping workers costs a system call each. A minimum chunk size (or the body's cost) should keep such loops on one thread.
11. **MOSS generation to VAE transition**: warm generation 4.10-4.18 s against ComfyUI's 3.51 s with sampling at parity: VAE decode 0.63 against 0.27 s, PNG encoding 0.28 against 0.08 s, cold loading. Details: `../StrictComfy/Performance.md`.
12. **Large grouped loop index precision** (3080, 2026-10-24): inlining `let half = size / 2` as `size / 2` in StrictComfy `MossBlock.Rotated` passes the small native tests but the full size kernel (3740 x 3072) gets 2.8M of 11.5M elements wrong (max difference 39). Reproduce with StrictComfy/benchmark_elementwise.py (STRICT_BENCH_KERNEL=Rotated, STRICT_BENCH_BOUNDS=1); suspect index precision or guard lowering.
13. **Packed int8 matrices in a `List(List(Numbers))` built by a `for`** read wrong numbers natively in StrictComfy's H3Block (2026-10-25, worked around there); a stack of tinyint8 rows reads right. StrictComfy rechecks it once its workarounds for the other bugs met then (composite and list defaults, indexing another type's constant, foreign calls with 6 numbers, all fixed) are gone.
14. **GPU-only lists can't be spilled**: activations computed on the GPU have no host copy, so keeping them alive across H3's 50 streamed blocks (Spectrum feature anchors, 2 x 160-320 MB) takes every byte from the streamed weights (steps 3.6 -> 5-7 s). Spillable activations (or an explicit move to the host) would allow feature forecasting.
15. **Linker and inference gaps** (2026-10-25): (a) `strict test Compiler/MlirModule.strict` prints "Unsupported native call Strict/Bytecode/InstructionEntry.LoadBoolean" twice (four times before `TypeEntry.Invoked` scanned member initializers): constants of linked types compiled on demand (`MlirPurity.Clamped`, `GpuSamples.Absolute`) call methods the linker never saw; (b) a parameter without a type does not get the type of its constant default: `Combined(other = Short)` in Examples/Labeled reads `other.label` as `()`, `other Labeled = Short` works; `HeaderTokens.ValueType` takes the constant's name as the type and TypeCodegen, TestLines and CallTarget read `ParameterTypes` from the header alone, so the header needs the owner's constants.
16. **mlir-opt crashes once in a while** (2026-10-25, twice): an access violation in its parallel verifier (StorageUniquer, DenseArrayAttr getOrCreate in verifyOperandSizeAttr, LLVM 23 mlir-opt from MSYS2), the identical rebuild passes. When it shows up again, rerun that build with `--mlir-disable-threading` to confirm the race, then pass it in `NativeBuild` if it costs little.

## Game engine (DeltaEngine)
1. **Methods as values so one game loop serves all games**: `Games/*`, `RealTimeStrategy/RtsGame.strict` and `Frameworks/GameApplication.strict` repeat the same `Played(application)` loop (21 times) because it needs `current.Frame(handle, now)` returning the concrete game type. A `GameLoop` trait needs (a) a type instance passed where a trait is expected, (b) a method returning the trait type when the implementation returns its own type, (c) the loop keeping that value without knowing the concrete type.
2. **Networking for multiplayer**: a small transport trait (a mock plus real sockets) and a lobby/match message layer shared by the real time strategy games. Plan it here before implementing.
3. **Spine 2D skeletal animation** for Elemental, TinyBat and other 2D games: wrap a native Spine runtime once, the `.strict` side only plays animations and sets skins.
4. **Platform services as trait implementations**: Steam, Google Play Games and Apple Game Center implement the `Achievements`, `InAppPurchase` and login traits; a base login package (account id, name, avatar, sign in and out events) for all games.
5. **Native trait dispatch**: a call on a trait typed value compiles to a call of the trait's own symbol (`undefined symbol: Analytics_GameStarted`) and `Bytecode/Linker.strict` skips trait files, so traits work on the VM but break `strict build` as members or parameters. Resolve the call to the one implementation in the program, or specialize trait typed parameters like generic methods (`Bytecode/Specialization.strict`).
