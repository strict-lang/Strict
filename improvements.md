## Game engine (DeltaEngine)
1. **Methods as values (function pointers) so one game loop serves all games**: `Games/*` each repeat the same `Played(application)` loop (21 occurrences of `Played(application`, the method plus its loop body, across `Games/*`, `RealTimeStrategy/RtsGame.strict` and `Frameworks/GameApplication.strict`) and the frame preamble because the loop needs `current.Frame(handle, now)` returning the concrete game type and `current.Closes(next)`. Traits (a type with methods without implementation, `README.md` members) are the intended shape: a game type could be used as a `GameLoop` trait and the shared loop would call `Frame`/`Closes` through it and get a `GameLoop` back (value-based selection like `NeuralNetworks/Activation.strict` works only for constants of one type, not for a different type per game). This needs (a) passing a type instance with methods into a member or parameter where a trait is expected, (b) a method that returns the trait type when the implementation returns its own type, and (c) the loop keeping that returned value without knowing the concrete type. `Games/*/Plan.md` and the shared `Frameworks/GameApplication.strict` describe the duplication.
2. **Networking for multiplayer**: no engine package exists, each game would hand-roll sockets. Wanted: a small transport trait (a mock plus a real socket implementation) and a lobby/match message layer so real time strategy games (Arena Wars, WebWars, ArmiesOfSteel) share it. Put the plan here before implementing, it is a large task.
3. **Spine 2D skeletal animation**: wanted for character and menu animation in Elemental, TinyBat and other 2D games; native Spine runtimes exist for C/C++ and can be wrapped once, then the `.strict` side only plays animations and sets skins.
4. **Platform services as trait implementations**: `Achievements`, `InAppPurchase` and login are traits with mocks in DeltaEngine; Steam, Google Play Games and Apple Game Center implement them (Steamworks, `play-games-services`, `GameKit`). A base login package (account id, name, avatar, sign in and out events) is wanted so all games report the same events.
5. **Native trait dispatch**: a call on a value whose static type is a trait is compiled to a call to the trait's own symbol (`GameApplication.analytics Analytics` produced `undefined symbol: Analytics_GameStarted`), and `Bytecode/Linker.strict` skips trait files on purpose, so a bodyless trait method only links when a `native/<Trait>.c` provides it (`Compiler/MlirForeign.strict` says the same). Traits therefore work on the Strict VM (`strict test`) but break `strict build` as soon as one is a member or parameter. DeltaEngine binds the concrete mock (`has analytics MockAnalytics = MockAnalytics.Empty`) instead. Resolving the call to the one implementation in the program, or specializing trait-typed parameters the way generic methods already are in `Bytecode/Specialization.strict`, would let `GameApplication` and platform services keep the trait type.
