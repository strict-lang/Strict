# Improvements
What to fix next, one short line each, bugs first. Remove a line once it is attempted: if it is done it is gone, whatever is left or newly found goes in as a new line at the end. No numbering, no history and no measurements here (those go into commit messages and package READMEs). Long running topics keep their details in their own file; bugs always stay here.

## Bugs
- `strict test Compiler/MlirModule.strict` prints "Unsupported native call Strict/Bytecode/InstructionEntry.LoadBoolean" twice: constants of linked types compiled on demand (`MlirPurity.Clamped`, `GpuSamples.Absolute`) call methods the linker never saw.
- A parameter without a type ignores the type of its constant default: `Combined(other = Short)` in Examples/Labeled reads `other.label` as `()` (`HeaderTokens.ValueType` takes the constant's name as the type).
- Traits break `strict build` as members or parameters: the call goes to the trait's own symbol (`undefined symbol: Analytics_GameStarted`); resolve it to the one implementation or specialize like generic methods (`Bytecode/Specialization.strict`).
- Rare crashes under load: mlir-opt's parallel verifier (access violation in StorageUniquer, rerun with `--mlir-disable-threading` when it shows up again); `strict test Compiler/Toolchain.strict` exited 127 once among 16 parallel tests in `PartsCompiled` (`Process.RunTools` on pool threads).
- Ternary Bonsai 27B stalls on 10 GB cards (p95 315 ms per token against 31 with 24 GB), not from collections (5 full ones either way): check uploads of evicted weights.
- Native builds now and then leave an llvm-split part (`Name.test-3`, LLVM bitcode) next to the source: `NativeBuild.Removed` ignores a failed `File.Delete` (likely still open).
- Parallel `strict build`s after a compiler change all rebuild `Compiler/NativeCompiler` at once and fail linking (`NativeCompiler.res` missing): one build rebuilds, the others wait for it.
- A GPU loop calling a method that only wraps one summing call (`Normalization.Scale(Normalization.Squared(...))`) sums the whole group again per element (Moss sampling 4.0 -> 17.5 s): let `MlirGroups.Adding` look through such a callee, with a MlirGroups test.
- `Compiler/Bootstrap.mlir` predates the 11 attention arguments: MossGenerate built by the stage 0 compiler of `Bootstrap.cmd` sampled for over 100 s; regenerate it from a fixpoint build.
- A failed host allocation shows up as `AccessViolation` instead of an out of memory Error (H3 with 40 GB committed by other programs).
- `File.Length` on the VM returns the collection length, not the file's byte count (release verification uses `ReadBytes.Length` for now).

4. **Grouped sums one call deeper**: `MlirGroups.Adding` makes a call in a GPU loop a per group sum only when the callee itself is the summing loop (`MlirDeviceSums.IsSummed`). 206b3b3e made `Qwen3Block.HeadScale` call `Normalization.Scale(Normalization.Squared(...))`, every element of MossBlock.Modulated then summed its 3072 numbers again: Moss sampling 4.0 -> 17.5 s on the RTX 3080 (2026-10-25). MossBlock and Gpt2Block now call `Normalization.Squared` directly and HeadScale is gone. Next: let Adding look through a callee that only wraps one summing call, with a MlirGroups test. Also seen: MossGenerate built by the stage 0 compiler of Bootstrap.cmd with the runtime of ec0c55e4 sampled for over 100 s (the full build does not), Bootstrap.mlir predates the 11 attention arguments.
5. **INT8 attention like ComfyUI's comfy_kitchen** (../StrictComfy/Performance.md, 2026-10-25): ComfyUI's `int8_attention` (Q and K rotated by a Hadamard of 128 before int8, int8 V, uint8 shares) runs H3's step in 2.06 instead of 3.22 s, Sol-Attn on top (each 64 token block attends the key blocks whose pooled proxy score clears tau sigma exactly, one pooled term for every other block) in 1.57 s. `Attention.quantized` (H3 sets it) quantizes the keys once per launch with a scale per position and head and multiplies them with per row quantized queries in m16n8k32 (`strict_device_attention_scores_eights`): one H3 launch 40.8 -> 31.1 ms under ncu, steps 0.34-0.43 s faster, errors against ComfyUI unchanged (video 0.236, audio 0.084). Quantizing the keys in the kernel instead was slower (every block of a head quantized all its keys again). Next, from ncu: the tensor pipe is 53 % busy, 35 of that the f16 PV products, so uint8 shares times int8 values (sums converted on the FMA pipe, not I2F); tiles of 64 positions (the per tile fold, barrier and softmax bookkeeping are amortized over 32 keys); the Hadamard on Q and K; then Sol's routing.
6. **16 bit lists on the GPU**: the rule is explicit, a GPU loop of a method returning `BFloat16s` stores bfloat16 (MossBlock.Modulated and Activated, which only int8 products read), never by size alone (bfloat16 in every loop made Qwen3.8 prompts of 1366+ tokens decode NaN, `DeltaChunks` feeds a triangular inverse). Open: (a) bf16 QK attention beyond the 128 wide QKV path; (b) attention, product and hadamard results are 32 bit; (c) joining lists of different formats goes through the host; (d) LLVM 23 PTX of strict_device_whole(s) is ~3 % slower than LLVM 22's.
7. **Ternary Bonsai 27B** (`C:/code/Models/Bonsai`, NeuralNetworks/README.md): 12.7-16.4 ms per token on the RTX 4090 (Prism's llama.cpp ~11); per token (ncu) the products take ~8.7 ms, the 257 `Sylvester` kernels ~1.4 ms, the quantize kernels ~0.6. Next: (a) a `Sylvester` kernel takes ~5.5 us for 50-170 blocks, latency bound by its 10 radix-2 stages with a barrier each: radix-4 or radix-8 stages in registers (fusing it into the quantize was slower); (b) on 10 GB cards steps stall (median 20, mean 313 ms): check StrictComfy's 256 MB own reserve (6c) there; (c) the dot products decode every PTQ1_0 block twice, the two lanes of a block should split the codes; (d) one kernel for 1 to 8 tokens (like Kindi's) so `LookupDecoding` verifies cheaper (2, 4, 8 tokens 27.7, 37.3, 47.2 ms against 16.8 for one) and keeps the tokens of plain decoding; (e) CPU loops unpack 3 bit rows to doubles (MlirWidths decodes only 4 and 6 bit blocks per use).
8. **Qwen3.8-Flash-Next** (qwen4exp, `C:/code/Models/FlashNext`, NeuralNetworks/README.md): ~280 ms per token, 325 with MTP drafts. Next: (a) the draft acceptance on a chat prompt with a longer answer and with 3 drafts (llama.cpp reports 89 %, here 7 and 12 of 24); (b) the 3 token `Steps` costs ~1.5 plain steps; (c) the QSA indexer past 2051 tokens.
9. **GPU memory at the edge of the WDDM budget**: H3 DiT steps (21.7 GB of weights, 37 of 50 blocks resident, the rest streamed) take 3.6-3.8 s against ComfyUI's 3.3 s, about 230 ms of that idle; ComfyUI streams too (47 GB of uploads in one 8 step run) but overlaps it (60 ms idle), so the target is overlap, not fitting. Left: (a) uploads still wait in order where the prefetch chain (`strict_gpu_prefetch`, one spill ahead) breaks: prefetch two rows or a block ahead; (b) power of two size classes keep ~1.9 GB of H3's pool unused (7 blocks of 512 MB for 319 MB lists, 1 GB for ~600 MB); finer classes churned activation blocks through the driver, they need activations kept and weights evicted first, or blocks lent across classes; (c) without spilled rows the trim before an own block runs at every block (40 of 50 blocks: 440 driver allocations and 200 syncs per step, 9.5-12 s against 2.8 s with `%ownReserve` at 256 MB instead of 1 GB); (d) measured 2026-10-25, not taken: rows with one scale uploaded with that scale alone for strict_device_whole (372 instead of 417 MB per block, 44 of 50 blocks resident) with a reserve halved whenever a trimmed class came back ran 3.9-4.2 s per step (a 1 GB activation block and the re-uploaded weights pushed each other out, a 1 GB cuMemFree per block), with uploads taking over spilled rows until 1.25 GB are free 3.82-3.84 s against master's 3.70-3.77 s; (e) MossImage with ~0.9 GB used by other programs still has 1-8 full collections per step: a sub-allocating pool would end them.
10. **Loading big safetensors at file speed**: the 21 GB H3 DiT loads in 10-12 s (ComfyUI 4-7 s), mostly page faults of the copy into fresh memory (~5 GB/s on 48 threads), and its first step uploads all of it: 10.1-10.6 s instead of 3.7 (14.4-14.9 before tables up to 256 MB went through the pinned staging buffer), the rest is the gather of each table on one thread (~45 ms per 165 MB) before its synchronous copy. The gather runs on the pool threads now (`strict_gpu_gathering`), big file matrices need none (item 20). Next: 8 bit rows that stay in the mapped file (no copy at load).
11. **Generated GPU loops: vector coverage and fused memory passes**: they are instruction bound on the RTX 3080 (120-330 instructions per number). Left: (a) format mixes without an AOT copy (`MlirFormats` has all f32, all bfloat16 and first bfloat16) run the generic kernel: H3's `Rope.Rotated` with 16 bit norm weights 192 against 80 ms per step, Gated f32/bf16/f32; (b) a loop reading a member of an object parameter (`layout.width` in ../StrictComfy `H3Final.Unpatched`) stays on the CPU: pass loop invariant members as numbers; (c) bounds, reduction and tail checks remain, extend the four wide loads (`MlirBatched`) where counters show headroom (H3) and fuse memory passes. Details: `../StrictComfy/Handoff.md`.
12. **Trees as pools with 32 bit backward offsets** (from [Goose](https://github.com/aardappel/goose)): an immutable value is built after its members, so a type holding instances of itself (`SyntaxNode.children`) can keep all of them in one grow-only block linked by u32 backward offsets, one free per tree. Measure SyntaxNode allocations and bytes per `strict build Strict.strict` first.
13. **Small parallel loops cost up to 0.8 ms once the workers sleep**: every collecting loop of 256+ elements goes to the pool (`MlirParallel`), `List.Slice` of 1024 rows takes 0.4-0.8 ms (serial ~20 us) since waking 47 sleeping workers costs a system call each. A minimum chunk size (or the body's cost) should keep such loops on one thread.
14. **MOSS generation to VAE transition**: warm generation 4.10-4.18 s against ComfyUI's 3.51 s with sampling at parity: VAE decode 0.63 against 0.27 s, PNG encoding 0.28 against 0.08 s, cold loading. Details: `../StrictComfy/Performance.md`.
15. **Large grouped loop index precision** (3080, 2026-10-24): inlining `let half = size / 2` as `size / 2` in StrictComfy `MossBlock.Rotated` passes the small native tests but the full size kernel (3740 x 3072) gets 2.8M of 11.5M elements wrong (max difference 39). Reproduce with StrictComfy/benchmark_elementwise.py (STRICT_BENCH_KERNEL=Rotated, STRICT_BENCH_BOUNDS=1); suspect index precision or guard lowering.
16. **Packed int8 matrices in a `List(List(Numbers))` built by a `for`** read wrong numbers natively in StrictComfy's H3Block (2026-10-25, worked around there); a stack of tinyint8 rows reads right. StrictComfy rechecks it once its workarounds for the other bugs met then (composite and list defaults, indexing another type's constant, foreign calls with 6 numbers, all fixed) are gone.
17. **GPU-only lists can't be spilled**: activations computed on the GPU have no host copy, so keeping them alive across H3's 50 streamed blocks (Spectrum feature anchors, 2 x 160-320 MB) takes every byte from the streamed weights (steps 3.6 -> 5-7 s). Spillable activations (or an explicit move to the host) would allow feature forecasting.
18. **Linker and inference gaps** (2026-10-25): (a) `strict test Compiler/MlirModule.strict` prints "Unsupported native call Strict/Bytecode/InstructionEntry.LoadBoolean" twice (four times before `TypeEntry.Invoked` scanned member initializers): constants of linked types compiled on demand (`MlirPurity.Clamped`, `GpuSamples.Absolute`) call methods the linker never saw; (b) a parameter without a type does not get the type of its constant default: `Combined(other = Short)` in Examples/Labeled reads `other.label` as `()`, `other Labeled = Short` works; `HeaderTokens.ValueType` takes the constant's name as the type and TypeCodegen, TestLines and CallTarget read `ParameterTypes` from the header alone, so the header needs the owner's constants.
19. **mlir-opt crashes once in a while** (2026-10-25, twice): an access violation in its parallel verifier (StorageUniquer, DenseArrayAttr getOrCreate in verifyOperandSizeAttr, LLVM 23 mlir-opt from MSYS2), the identical rebuild passes. When it shows up again, rerun that build with `--mlir-disable-threading` to confirm the race, then pass it in `NativeBuild` if it costs little.
20. **Weights pinned in place** (../StrictComfy/Performance.md, 2026-10-26, RTX 3080, 64 GB RAM): `strict_packed_rows` lays a matrix of 64 MB or more read from a file out like its rows table on the GPU (header, then the rows at the GPU stride), its first upload locks that block in place (`cuMemHostRegister`, at most half of `strict_host_memory`) and keeps it as its spill, so evicted rows come back asynchronously through the prefetch chain without a second pinned copy. H3 steps 1.8-2.0 s instead of 3.9-7.0 (ComfyUI 1.83 s), the first step 4.3 instead of 8-10 s, two 29 frame videos 54 instead of 103-168 s end to end, H3 commits its weights once (+26 GB), outputs bit identical. Left: (a) a failed host allocation is an `AccessViolation`, not an out of memory error (seen at the commit limit with a 32 GB pinned copy cap); (b) matrices below 64 MB (Moss) still go through the staging buffer, and spill slots are 1024; (c) no native test reaches the 64 MB path, only H3 against ComfyUI.
20. **File byte count on the VM**: `File.Length` does not return the file byte count (found while checking release copies). Route the existing member through file-size dispatch instead of collection length; release verification currently uses `ReadBytes.Length`.

## Game engine (DeltaEngine)
1. **iOS**: `strict build <file> ios` stages an arm64 iOS 15 static archive with `strict_main` and the content; linking against the SDK, UIKit, window, input and audio, signing and TestFlight need the MacMini ([Compiler/IOS.md](Compiler/IOS.md)).
2. **Android release path for SoulCraft**: `strict build <file> android` stages an API 26 arm64-v8a `libmain.so` and `assets/Content`; the APK/AAB, the Activity/JNI glue, window, input and audio backends and ASTC/ETC2 textures belong to DeltaEngine. The link stops at the `stb_image.h` include paths of `Content/native/ImageFile.c` and `Graphics3D/native/Gpu.c` (no Android native flags yet); keep the shipped app's identity (package `de.mobilebits.soulcraftdefault`, its signing and saves) when replacing it.
3. **Methods as values so one game loop serves all games**: `Games/*`, `RealTimeStrategy/RtsGame.strict` and `Frameworks/GameApplication.strict` repeat the same `Played(application)` loop (21 times) because it needs `current.Frame(handle, now)` returning the concrete game type. A `GameLoop` trait needs (a) a type instance passed where a trait is expected, (b) a method returning the trait type when the implementation returns its own type, (c) the loop keeping that value without knowing the concrete type.
4. **Networking for multiplayer**: a small transport trait (a mock plus real sockets) and a lobby/match message layer shared by the real time strategy games. Plan it here before implementing.
5. **Spine 2D skeletal animation** for Elemental, TinyBat and other 2D games: wrap a native Spine runtime once, the `.strict` side only plays animations and sets skins.
6. **Platform services as trait implementations**: Steam, Google Play Games and Apple Game Center implement the `Achievements`, `InAppPurchase` and login traits; a base login package (account id, name, avatar, sign in and out events) for all games.
7. **Native trait dispatch**: a call on a trait typed value compiles to a call of the trait's own symbol (`undefined symbol: Analytics_GameStarted`) and `Bytecode/Linker.strict` skips trait files, so traits work on the VM but break `strict build` as members or parameters. Resolve the call to the one implementation in the program, or specialize trait typed parameters like generic methods (`Bytecode/Specialization.strict`).
