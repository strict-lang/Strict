# Improvements
In priority order. Remove what is done, add what is found, keep each item to what is still open (results go into the README of the package). Every item gets done before the bigger image processing and neural network examples, parallel loops and GPU (decided 2026-10-12).

1. **Prompt speed** (Qwen3-8B Q4_K_M on the RTX 4090, what is done and measured is in `NeuralNetworks/README.md`): prefill takes 2.8 ms per token at 10 tokens, 1.3 ms at 100 and about 2 ms at 500 (llama.cpp 1.18, 0.175 and 0.10 ms). Open: attention over the prompt in FlashAttention style (`Scores` and `Merged` take half of a 500 token prompt and grow with its square, `Merged` computes each exponential again for every dimension), the tensor core tiles of `NativeRuntimeTokens.mlir` reach 5% of their peak (every lane loads its fragments from global memory, the token sums for the Q4_K minimums take a second mma, scales per 16 numbers), prompts below 32 tokens go row by row with dp4a; GPT-2 gets the same prefill (its prompt runs on the CPU, no loop reads 4M numbers before the logits).
2. **Batched decoding**: several sequences share the weights (batched multiplication, per sequence caches, positions and sampling, continuous batching), batch 1/2/4/8/16 benchmarks with peak VRAM and p95 latency, first target batch 8 x 4K.
3. **FP8 cache**: keys and values are 32 bit floats (295 KB per token for the 8B, 9.7 GB at 32K tokens), compare accuracy, speed and memory of 8 bit floats; with it attention that reads the cache coalesced at long contexts (700 tokens decode in 8.75 instead of 7.5 ms, `Merged` reads one position per lane), measured at 512 to 32K tokens.
4. **Language model leftovers**: sampling other than greedy (temperature, top-k, top-p) on the GPU; Qwen3-Coder-30B-A3B launches 1157 kernels per token, which keeps the CPU busy; GPT-2 spends 1.4 of its 2.1 ms per token in graph launches and waiting for the download; MXFP4 for gpt-oss, safetensors other than F32 (`OnlyFloat32TensorsAreSupported`); a program with a GPU loop carries the PTX of the whole device runtime (149 KB, `strict.exe` grew from 2.93 to 3.12 MB when two of its `Range` loops became kernels, the prompt kernels only come with `Batch.Sums`); per row `Summed` still checks its lists on the CPU, matrix rows are separate allocations (a full collection marks the 1.7M rows of the 8B, 140-216 ms); later for bigger models paged caches, prefix caching and moving inactive caches to the CPU. Each optimization stays switchable (`STRICT_GPU=0` for the CPU, `STRICT_GRAPHS=0`, `STRICT_YOUNG=0`, `STRICT_DP4A=0`) and gets measured before the next.
5. **Neural networks** (the use case, results in `NeuralNetworks/README.md`): every training step still builds new lists for activations, deltas and weights (about 38% of 784-64-6 MNIST training is allocating and collecting), a call with loop-invariant arguments runs on every iteration natively (could be hoisted), loops with calls (`activation.Output(...)`, `Row(...)`) take the checked path. Next: bigger networks to measure parallel `for` on all cores, SIMD and the GPU against the C# version; swish (its derivative needs the weighted sums, which `Network` does not keep). Only small inline data, bigger samples get their own repository like `../Mnist`.

## Language and compiler
- **`value` parameter of a one-member type** (found 2026-10-16): in compiled code a parameter named `value` of a method of a type with one member is that member (`MlirTyped.Shuffled` printed its value as the type), the Strict VM keeps them apart, `strict check` could reject the name.
- **Same-named types in one build**: a build needing `WebWars/Scene` and `LogoApp/Scene` at once is not supported (types and native symbols are keyed by the plain name).
- **Tests returning an Error are slow** (found by the VS Code client 2026-10-16): in `strict test` of each `Expressions/*.strict` the 25 tests involving an error (`Unknown`, `Unresolved`, `…Mismatch`, `…Must…`) took 1.36 ms on average, the other 619 0.29 ms; with all cores busy (SCrunch) most of the 273 tests over 10 ms in the repository return an Error. Probably building the Error (its Stacktrace) per call.
- **`Runtime/Execute.strict` test of `Completed` takes 40 s** (`Completed(Anything, ".", AnyFiles, ...)` in the repository root, the other tests of the file 0.01-0.6 ms): with all cores busy SCrunch stops it after 60 s, so it is never cached; needs a small folder or inline files.
- **`File.Override` writes nothing** (found by DeltaEngine 2026-10-16): it only keeps the text in memory for later reads of that path (`strict test <file> -`), the name suggests writing; rename it or make it write (`File.Write(texts)` writes).
- **Keyed reads of own types**: `json("bones")` only calls `get` for a Dictionary (`IndexCodegen.Indexed`), any other type indexes its first member, so `Json` and `Xml` use `Field(key)` and `Child(name)`; a `get(key)` method of any type could be called the same way (asked 2026-10-16, needs a decision).
- **Stack overflows show no Strict stack** and the other tests of the file do not run (a depth counter in the VM needs room in `Frame` and `Machine`, both at 15 members and methods).
- **`Code` of a Dictionary natively** calls a missing `@Dictionary(Number, Text)_Code_foreign` (Dictionary.strict has no `Code`, the VM gives the `Code` of its pairs, `((1, "a"), (2, "b"))`), `got:` uses `to Text` for dictionaries; needs `strict_pairs_text` with the `Code` of key and value as converters (`Text.Code` packaged as a used method).
- **Arc tangent of any number**: `Vector2(x, y).Atan` (atan2, degrees from +Y towards +X, `Vector2(1, 0).Atan is 90`) and `Ratio.Asin`, `Acos`, `Atan` are native on both backends, but `Ratio` is constrained to -1..1, so the arc tangent of a larger number needs `Vector2(value, 1).Atan`; the `Degrees(0)` body of `Vector2.Atan` is only the spec placeholder.

## Rebalancing: exact values and C# integration (../Rebalancing)
Stepped decimals (README "Rules worth knowing", `Examples/Prices.strict`) keep 12345678.12345678 at Step 0.00000001 and values up to 2^51 steps exactly (the rounding tolerance was over half a step above 2^49 steps), libraries for Number, Text, Boolean, records of numbers as C structs and lists of numbers or records (`strict build X.strict library`, README "Command line"); Rebalancing uses the generated C# binding behind one host lock, policy coefficients cross as decimal text. A stepped Number parameter or result is `decimal` in the generated C# (C# rounds an argument to its step and rounding mode like a Strict caller does, a result to whole steps, outside 2^51 steps the call throws an OverflowException `DecimalOverflow`). Still open: stepped record fields and lists as decimal, exact int64 step counts instead of doubles (needed for anything beyond 2^51 steps). Then: lists of stepped values (`has prices Numbers with Step 0.01`), `let`/`mutable` locals with a step, lists of texts, Boolean record fields as C# bool, Strict calling C# host services. Acceptance: the ASP.NET host sends a candle/portfolio/settings snapshot, Strict returns proposed trades and reasons with decimal values unchanged, errors produce no orders, historical fixtures match the C# reference before its logic is removed.
