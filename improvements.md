# Improvements
In priority order. Remove what is done, add what is found, keep each item to what is still open (results go into the README of the package). Every item gets done before the bigger image processing and neural network examples, parallel loops and GPU (decided 2026-10-12).

1. **Decode speed** (Qwen3-8B Q4_K_M on the RTX 4090 at 6.6-6.7 ms per token, 150 tokens/s, results in `NeuralNetworks/README.md`): a step is now its kernels (6.55 ms), the GPU hardly idles. Open: fewer of the 19 launches per layer (about 1 ms of small kernels per token): `Softmax.Shares` as one kernel instead of `Largests`, `Totals` and itself (`MlirGroups` takes one summing group call per loop, a maximum is no group call yet), the query and key rotations in one kernel with keys and values appended as one contiguous part, the 145 quantize kernels (1 us each) done by the kernels that produce their inputs; the matrix products reach 885 GB/s for gate and up but 775-790 for the output projection, QKV and the 4 bit down projections (2-4 us of each kernel are ramp-up and tail).
2. **Prompt speed** (Qwen3-8B Q4_K_M on the RTX 4090, what is done and measured is in `NeuralNetworks/README.md`): prefill takes 1.6 ms per token at 10 tokens, 0.52 ms at 100 and 0.58 ms at 500 (attention is 130 of 299 ms at 500 tokens, the matrix products 130 ms) (llama.cpp 1.18, 0.175 and 0.10 ms). Open: attention over the prompt in FlashAttention style on the tensor cores, `Scores` and `Merged` are matrix products of queries with keys and of shares with values done one dot product per warp or thread (`Scores` takes 94 of 299 ms at 500 tokens, a warp per score of 128 numbers and half of the warps find their position hidden; the 32768 outputs from which a strided sum like `Merged` takes a thread per output are one threshold for all loops, measure it per loop when another kernel needs a different one), the matrix products take the tensor core blocks of several sequences (`strict_device_blocks`, 64 rows by up to 32 tokens for a prompt, so it reads every row once per 32 tokens; 128 registers leave 16 warps per SM, most of their time waits for loads; the sums of the token numbers are 4 of the 8 mma of a Q4_K part and the scaling after the mma costs as much as they do, token sums from the quantize kernel would save both; 64 tokens per block were not faster); GPT-2 gets the same prefill (its prompt runs on the CPU, no loop reads 4M numbers before the logits).
3. **Batched decoding** (done and measured in `NeuralNetworks/README.md`): batch 8 decodes 953 tokens/s (llama.cpp 727) and 32 sequences 2357 tokens/s on the tensor cores (`strict_device_blocks`, 128 registers because the row by row path for other rows is in the same kernel, so 2 blocks of 8 warps per SM, capped at 80 or 64 registers it spills and gets slower); the Q6_K rows reach 540 GB/s against 790 for Q4_K at batch 8. Open: sequences of different lengths and continuous batching (all sequences are at the same position now), peak VRAM and p95 latency in `Qwen3Benchmark`, first target batch 8 x 4K.
4. **Long context decoding** (8 bit cache done, `Float8`, results in `NeuralNetworks/README.md`): decoding takes 9.1 ms after 1000 and 10.6 ms after 2000 tokens (7.1 ms after 10), attention reads one position per lane (`Merged` with a warp per output, `Scores` a warp per position), so the 4 times smaller 8 bit cache is not faster yet (11.0 ms after 2000 tokens, every 8 bit number of `Merged` goes through the generic element read); split the positions over blocks like flash decoding and read keys and values coalesced, then measure at 4K to 32K tokens.
5. **Language model leftovers**: sampling other than greedy (temperature, top-k, top-p) on the GPU; Qwen3-Coder-30B-A3B launches 1157 kernels per token, which keeps the CPU busy, and `Qwen3CoderText` reports 430 ms per token because its 24 tokens include the first upload of the 18.6 GB of experts (283 synchronous copies at 2.3 GB/s from pageable memory); GPT-2 spends 1.4 of its 2.1 ms per token in graph launches and waiting for the download; MXFP4 for gpt-oss, safetensors other than F32 (`OnlyFloat32TensorsAreSupported`); a program with a GPU loop carries the PTX of the whole device runtime (149 KB, `strict.exe` grew from 2.93 to 3.12 MB when two of its `Range` loops became kernels, the prompt kernels only come with `Batch.Sums`); per row `Summed` still checks its lists on the CPU, matrix rows are separate allocations (a full collection marks the 1.7M rows of the 8B, 140-216 ms); later for bigger models paged caches, prefix caching and moving inactive caches to the CPU. Each optimization stays switchable (`STRICT_GPU=0` for the CPU, `STRICT_GRAPHS=0`, `STRICT_YOUNG=0`, `STRICT_DP4A=0`) and gets measured before the next.
6. **Neural networks** (the use case, results in `NeuralNetworks/README.md`): every training step still builds new lists for activations, deltas and weights (about 38% of 784-64-6 MNIST training is allocating and collecting), a call with loop-invariant arguments runs on every iteration natively (could be hoisted), loops with calls (`activation.Output(...)`, `Row(...)`) take the checked path. Next: bigger networks to measure parallel `for` on all cores, SIMD and the GPU against the C# version; swish (its derivative needs the weighted sums, which `Network` does not keep). Only small inline data, bigger samples get their own repository like `../Mnist`.
7. **DeltaEngine performance**: on the Strict VM `+`, `Lerp` and constructors are full calls (300000 `position + Vector2(1, 2)` and 300000 `Lerp` take 5.8 s, a native method like `numbers.X` goes through the name comparisons of `Natives.Result` every time, `Bound` fills every member slot, `Constructed` checks `IsStruct` by name every time), assigning a replacement or `position + offset` back to the same mutable variable could write in place, types made only of numbers (Vector2, Size, ColorValue) could be stored flat (a `List(Vector2)` as one array of doubles).
8. **Tooling**: not reported yet: a method whose tests a method of a used type passes (exactly one way), a dropped call result of a method that can never return an Error (dropped operators, literals and variables are `UnusedValueMustBeRemoved`). `strict suggest <file> <method>` in Strict for the VS Code client (all candidates verified in one process). `strict test <folder> lines` builds all files in one executable (Bytecode: 44 files in 50 s, about 40 s of it clang), but one file that does not compile natively stops the whole folder and the whole repository takes longer than 4.5 minutes. `strict test <file> values` (README "Command line") runs the tests traced in a second `strict` process (`Runtime/TracedFrame` logs every line start and assignment, `ValueTrace` counts them, a few MB of output for a compiler file) and prints each line with its substituted expression and value or the values of its hits (VS Code client formats, 2026-10-16), records show their changed members first by name; later the Debug Adapter Protocol in the VM. Bytecode: copies of types from other packages and base types are still inlined into `.strictbinary` files (22% of WebWars, names differ by package). A method that can never return an Error could skip the `CheckError` of its results (they made `strict.exe` 7% bigger, VM tests 10% slower). The LanguageServer waits until after the parallel loops and GPU (decided 2026-10-13).
9. **Reflection** (only as use cases need it): `to Type` of a Text that is not a literal (needs type names at runtime), natively a `Variable` value is a `Generic` without its type, a `Stacktrace`'s `Method` is `Type.Method` text (a `Method` value needs the methods at runtime).
10. **Research** (when all other work is done): pruning (attention heads, MLP neurons, structured, low rank, skipping layers) and speculative decoding with a small draft model, start with GPT-2, judged by perplexity, coding tests and measured speed.

## Language and compiler
- **Positions in 32 bit kernels** (found 2026-10-17): a 32 bit GPU kernel computes `index` and positions like `row * positions + index` in floats, exact only up to 2^24, so a loop of more elements or reading a longer list now runs as the double kernel and its result comes back to the host (a 750 token prompt in one piece took 138 ms per token, before it failed with "a loop on the GPU read outside of a list", a loop over the 24576 gate and up rows times about 683 tokens already has more positions); integer positions in 32 bit kernels would keep them fast.

## Rebalancing: native runner and C# integration (../Rebalancing)
Updated 2026-10-17: the user accepts final-digit floating-point rounding, including
`12345678.12345678m` returning as `12345678.1234568m`. Exact 28-place identity and decimal record/list
bindings are useful future features, but no longer block this migration. The financial core and
standalone Binance runner now execute in Strict; only generic Windows platform I/O is C.
The website consumes four native libraries through generated bindings under one host lock.
Captured comparisons: 1,500 allocation decisions with zero notional difference, 3,380 indicator
values with maximum relative error 2.89485e-12 and identical regime decisions, 1,280 spike prices
with zero difference. Revisions still cross as text to preserve adjacent 64-bit ticks.

Step-aware decimal fields/lists, exact int64 step counts, text lists and C# callbacks remain useful
interop extensions. The running application currently does not need host callbacks: its native
runner owns HTTP, settings files, journaling and logging, and ASP.NET invokes native calculations.
