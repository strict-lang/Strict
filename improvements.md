# Improvements
In priority order. Remove what is done, add what is found. Every item gets done before the bigger image processing and neural network examples, parallel loops and GPU (decided 2026-10-12).

1. **Packages**: a type (declared or only used in a method body like `Vector2(1, 2)`) is looked up in the current folder (a project folder without base types also includes all its sub folders), then next to `strict.exe` (also plain names in its packages, `Vector2` finds `Math/Vector2.strict`), then in the GitHub repositories linked in the project's `README.md` and the repositories of github.com/strict-lang: the folder holding `Type.strict` is copied from a local clone in `C:/code/GitHub` or downloaded with `curl` into the current folder (`Repositories.strict`, GitHub is never asked when `C:/code/GitHub/strict-lang` exists), a type found nowhere is a `TypeNotFound` error with file, line and tips. Still open:
   - Without a token the GitHub API allows 60 requests per hour, each missing type costs the organization listing and one request per repository.
   - Only the `.strict` files directly in the package folder are downloaded (no sub packages), a newer version needs the folder deleted first.
2. **`.strictbinary` cache**: `strict <file>`, `test` and `build` write `Name.strictbinary` next to `Name.strict` once all its tests passed: a zip with a `sources` entry (format version, every source file the compiler read with its modification time) and one entry per used type (`TypeEntry.Bytes`, read back by `EntryDecoder`). While no source file has a different modification time the tests count as passed and its bytecode is used instead of compiling again (`strict test Strict.strict` 3.1 s, cached 0.07 s). A new `strict.exe` does not invalidate it: after compiler changes delete the `.strictbinary` files. A text literal in the tested file that names an existing file (`"ImageProcessing/4x4.png"`, `root + "/Compiler/NativeRuntime.mlir"`) is tracked the same way (`BinaryFile.Data`), a literal naming a data folder (relative, without `.strict` files, like `"NeuralNetworks/mnist"`) tracks every file below it. Still open: a path built only from other values (not a literal) is not tracked.
3. **Neural networks** (the use case): `NeuralNetworks/` has a multilayer perceptron (`Layer` fully connected with sigmoid and one weight row per neuron, `Network` with backpropagation over any number of layers) `Xor.strict` learns XOR with 2-3-1 neurons in 20000 steps, `Csv` reads a CSV (a header line, the class in the last column) and scales every feature to 0..1, `Dataset.Images` reads PNG images from one folder per class, both one-hot encode the class and keep every fifth sample for testing: `Iris.strict` reaches 97% test accuracy with 4-8-3 neurons after 200 epochs, `Diabetes.strict` 72% on `diabetes.csv` (UCI Diabetic Retinopathy Debrecen, 1151 rows, 19 features) with 19-10-2 neurons after 200 epochs. They log their training time measured with `Process.Elapsed` (seconds since the process started): Xor trains in 7 ms natively (Strict VM 1.5 s), Iris in 17 ms (VM 4.4 s), Diabetes in 240 ms (was 670 ms: `%` of whole numbers uses integer remainder instead of `fmod`, for-expression results grow their list in place instead of allocating a view per element and start with the capacity of the loop, a loop over a list reads its items directly, a list parameter the method never changes is read through its items pointer fetched when the method starts, `Layer` keeps one weight row per neuron instead of dividing the weight index), that is 1.3 µs per sample for 210 weights, every step still builds new lists for the activations, deltas and weights. A method call with loop-invariant arguments runs on every iteration natively, the compiler could hoist it. `Digits.strict` classifies the 16x16 handwritten digits 0 to 3 of AiInvest (160 PNG images in `mnist/`, read with `ImageProcessing/Png` and `Compression/Inflate`): 100% test accuracy on the 32 held out images with 256-32-4 neurons after 100 epochs in 0.38 s natively (1.5 s before the result lists started with the loop's capacity and the rows), 3.3 ns per weight and sample for the forward and backward pass. Next: softmax with cross entropy, momentum, the 28x28 digits and bigger networks to measure parallel speedups. The neural network is written in Strict, the old C# code in `C:\code\AiInvest\AiInvest.NeuralNetworks` (and the `AiInvest.NeuralNetworks.*` folders next to it) is only a guide, it has bugs (MatrixNetwork backprop drops the hidden gradient, the Tanh, Swish and Logistic derivatives, CrossEntropy ignores the target). Steps: XOR (`AiInvest.NeuralNetworks.Tests\LogicTests.cs`), a simple MNIST investigation (the digit images in `AiInvest.NeuralNetworks.Tests\Optimized16x16`, `SimpleMnistTraining` uses 256-64-1), then the usual samples (`iris.csv` and `diabetes.csv` in `AiInvest.Classifiers.RandomForest.Tests`), then bigger projects built on that. Number has `Exponential`, `Logarithm`, `SquareRoot`, `Random` (uniform below the value, seeded per run), `IsFinite`, `Round(decimals)`, bitwise `and`/`or`/`xor` and the constants `E`, `Pi`, `Phi`, lists have `Sum`, `Maximum` and `Minimum`. Still needed: image loading natively (see Native gaps). The goal is to find the performance bottlenecks and measure how much parallel `for` on all CPU cores, SIMD, GPU and CUDA through MLIR speed it up, compared with the C# version. Long term a more abstract language uses Strict like DNA: long chains of simple instructions that are easy to copy, change, merge and test, which the higher level rewrites, tests and evolves to reach its goals (trying different things, using what LLMs and other projects do).
4. **Dictionary generics**: `Dictionary(K, V)` works natively and on the Strict VM. It is built from type arguments or pairs, and its methods are runtime natives over the list of pairs (`Dictionary.strict` is the specification): Length, `in`, get (also `prices("apple")`), Add with DuplicateKey, Remove, and `is` between different type arguments. `for` over a dictionary gives its pairs (`value.Key`, `value.Value`), typed `List(K, V)` when key and value types differ, and such pairs compare and print natively too. Still open: natively only Text and Number keys and values compare and print (a pair with a Boolean or a struct value compares its slots as numbers); generic types other than List and Dictionary are not instantiated.
5. **HashCode**: `HashCode.strict` hashes a number to itself, texts and lists by combining their elements (times 31, modulo 2^32, `"abc"` is 96354), anything else through its text. Native Dictionary lookups use an open addressing index kept in the list holder, built on the first lookup and extended after appends (20000 Adds and lookups: 550 ms before, 85 ms now). Still open: the Strict VM's Dictionary natives still scan all pairs, and hashing an instance through its text is slow (a member wise hash needs reflection).
6. **Operator overloads by parameter type**: list `-`, `*`, `/` (with a list or a number), `3 + (4)`, Reverse, out of range indexes and the downcast Error work natively and on the Strict VM, `List.strict` passes on both. Overloads with the same argument count are chosen by the argument types (`Expressions/Overloads`, `Vector2 * Vector2` is the dot product, `Vector2 * 3` scales) on both backends: an exact fit first, then one an argument only converts to (Number to Byte or back through a one-member type, anything to Generic). A method call is typed with the return type of the overload its arguments choose (`a.Scaled(3, 1)`). Still open: a `to` or `from` conversion (ColorValue to Color) does not count when choosing an overload, the first one with that argument count is used.
7. **Errors instead of crashes**: the VM crashes are gone, failing tests print their value, a line that does not parse (`number + + other`, an unclosed bracket) in any file of the project is a `ParsingFailed` error and an unknown name or method in the compiled file or in any type it uses is a `NameNotFound` (`number + othr`) or `MethodNotFound` (`number.Unknown(other)`) error, all with file and line (the used files are checked after linking, 0.4 ms each). At runtime an Error prints as `Error: Name` and one `at Type.Method in file:line N` line per method it came through (where it was created and every call it was returned from), the same on the Strict VM and natively: instructions keep their source line (bytecode format 3), `Frame.Traced` adds a `Stacktrace` on the VM, natively a check after every call of a Strict method and the out of range branch of a list read append to the error block (`strict_trace`, `strict_index_error`, 2977 calls in `strict.exe`, which grew 16%). Still open: the `Method` of a VM `Stacktrace` is its `Type.Method` text and natively the stack traces are texts (Strict code reading `error.Stacktraces(0).Line` only works on the VM), errors that only pass through arithmetic (`1 + error`) keep their trace but get no new line, a test that compares `Error("x") to Text` sees its own frame.
8. **Native gaps**:
   - Logging a one-member instance prints its member natively but `(member)` on the Strict VM and in C# (`Examples/ProcessProbe.strict`: `Process.Find("nasm")`), decided: brackets everywhere like `(5)` for a one element list.
   - Images: `ImageLoader(path).Loaded` reads a PNG into an `Image` (`Colors` are `ColorValue`s 0..1, gray, palette, RGB and alpha up to 8 bits), `ImageSaver(path).Save(image)` writes an RGBA PNG with stored deflate blocks (`Compression/Deflate`, no compression yet), `Image.Blank(size)` is a black image, `ProcessImage` and `AdjustBrightness` run on both backends. An element write into a member list of a variable that is not owned (`adjusted.Colors(index) = ...` after `mutable adjusted = image`) copies the list and the instance first natively (`strict_instance_with`), before a loop once. Still open: JPG reading, compressed saving, a type with one stored member is that member natively so such a member list write is not supported, the C# version filled an empty list member with a `Length is` constraint automatically (now `Image.Blank`).
9. **Tooling**: LanguageServer in Strict (the C# one is on the `dotnet` branch), CI with the native toolchain.
10. **Reflection** (later, only as use cases need it): `"Number" to Type` builds `Type("Number", "Strict")` and `value is Number` is decided at compile time from the static type, on both backends. Not supported yet: `to Type` of other values (`Any.strict`, `5 to Type` would be the static type) and of a Text that is not a literal (needs the type names at runtime).
11. **Strict VM speed**: 255 ms for 1M iterations, about 6x slower than native (40 ms), but numeric code with method calls and lists is far slower: training `NeuralNetworks/Xor.strict` takes 1.1 s against 7 ms natively, `Iris.strict` 3.9 s against 17 ms (in the morning of 2026-10-12: 3.5 s and 25 s with process start). Constant lists are built once natively, `Resolver` finds the target of every call once when the types are loaded, the native loop improvements (for-expression lists grown in place with the loop's capacity, items read directly) help the VM as well. An element write to a list that is used elsewhere too (`Frame.Replaced`, `Looping.Counted`) no longer copies it: `strict_list_write` writes in place and turns the old header into a record of the replaced value, hoisted item pointers compare a global write counter that LLVM moves out of loops which never write. The records point from older to newer versions, so a stale reference to an old version (conservative stack scan) kept every later record alive (Iris used 1 GB): a list whose items live in its first block gets its own items array on the first versioned write and a new array after max(64, capacity) versioned writes, which bounds what one stale reference keeps (Iris 15 MB). Locals are slots: `Resolver` numbers the locals of every method when the types are loaded (`#this`, `value`, `#result`, `#flag`, `#loop`, `index`, then members, parameters and variables) and writes the slot into the instructions, `Frame` keeps them in one list, no local is found by name anymore and a call builds its locals in one allocation: Iris trains in 3.9 s (5.5 s before). Profile of Iris now: the collector about 26% and `Machine.Step` 9%, every step allocates a new `Frame` and every register or local write a 48 byte version record because the previous frame still points to the list. Next: the compiler updates a value in place when its previous version is never used again (`current = Step(current)`), constants decoded once (`PayloadDecoder.Value` decodes every number literal on every run), `Natives.TypeOf` by index instead of comparing type names.
12. **`name = expression`** (decided 2026-10-12, from the 2023 blog post "mutable"): shorthand for a single-expression method with an inferred return type, locally and on types, parameters may have defaults. Every use reads the current values it depends on, assigning to the name is an error, `let` keeps a calculated value and `mutable` a reassignable one. Effectful expressions run on every use, caching is only allowed when it keeps that behavior. Only for very simple, obvious things (square root, length, sin, cos of local values), one expression is not a tested method:
   ```
   mutable position = 3
   next(add = 1) = position + add
   next is 4
   position = 10
   next is 11
   next(2) is 12
   ```
