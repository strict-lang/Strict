# Improvements
In priority order. Remove what is done, add what is found. Every item gets done before the bigger image processing and neural network examples, parallel loops and GPU (decided 2026-10-12).

1. **Neural networks** (the use case): `NeuralNetworks/` has a multilayer perceptron written in Strict (see its README): `Layer` (fully connected, sigmoid, one weight row per neuron), `Network` (backpropagation over any number of layers, softmax with cross entropy for several outputs, momentum 0.5, weights start in plus minus 1 / square root of the inputs), `Csv` and `Dataset` (features scaled to 0..1, one-hot classes, every fifth sample held out, a new random order every epoch). Natively XOR (2-3-1) trains in 11 ms, Iris (4-8-3) in 25 ms with 97% test accuracy, Diabetes (19-10-2 on a quarter of the UCI Diabetic Retinopathy Debrecen data, 288 rows) in 80 ms with 60-64%. The MNIST digits moved into their own repository (github.com/strict-lang/Mnist, `../Mnist`): 256-32-4 neurons reach 100% on 32 held out 16x16 images in 0.49 s natively (58 s on the Strict VM), 784-64-6 neurons 68-82% on 28x28 images in 2.8 s. Every step still builds new lists for the activations, deltas and weights, and a method call with loop-invariant arguments runs on every iteration natively (the compiler could hoist it). Next: bigger networks to measure parallel `for` on all CPU cores, SIMD, GPU and CUDA through MLIR, compared with the C# version. Data over 1 MB is downloaded when needed instead of being checked in. The old C# code in `C:\code\AiInvest\AiInvest.NeuralNetworks` is only a guide, it has bugs (MatrixNetwork backprop drops the hidden gradient, the Tanh, Swish and Logistic derivatives, CrossEntropy ignores the target). Long term a more abstract language uses Strict like DNA: long chains of simple instructions that are easy to copy, change, merge and test, which the higher level rewrites, tests and evolves to reach its goals.
2. **Evolutionary algorithms and more neural networks** (asked 2026-10-13): `NeuralNetworks/Weasel.strict` evolves a random text into "METHINKS IT IS LIKE A WEASEL" by mutation and selection (45-95 generations of 100 children, 2-5 ms natively), `Neuroevolution.strict` evolves the weights of the 2-3-1 XOR network instead of backpropagating them (tournament selection, uniform mutation, the best network survives: error 1e-13 after 300 generations of 50 networks in 46 ms). `LogicGates.strict` learns Or, And, Nor and Nand with single neurons (`Perceptron`, from AiInvest's LogicTests) and builds Xor from three, `Activation` adds Tanh, Relu, LeakyRelu and Softplus with correct derivatives (`ActivationComparison.strict` on Iris: all 97-100% except plain Relu). Next, simplest first, from AiInvest (`X:\AiInvest`, deleted projects are in its history) and BrightWire (github.com/jdermody/brightwire, 18 samples in `ExampleCode/Program.cs`): swish (its derivative needs the sums, AiInvest's Tanh, Logistic and Swish derivatives and its CrossEntropy are wrong), RMSprop and Adam on XOR, linear regression by gradient descent, k-means on Iris (AiInvest's normalization divides by the variance), k nearest neighbors and Gaussian naive Bayes on Iris, a Gini decision tree and a random forest (bootstrap samples and random features, the AiInvest version has neither), an order 3 Markov text generator, inverse kinematics for the 6 joints of the Franka arm (`RobotEvolution.cs`, `ArmEvolution.strict` does it for a planar arm with 2 links), a simple recurrent network adding binary numbers (backpropagation through time), then Reber grammar prediction with a GRU or LSTM. Only small inline data, bigger samples get their own repository like Mnist.
3. **Tooling**: `.github/workflows/ci.yml` bootstraps from the seed on Linux with the LLVM 22 release archive, self builds until the fixpoint and runs every test on the Strict VM and natively (validated in a fresh WSL clone). A Windows job builds the same way with `mlir-opt` and `mlir-translate` from MSYS2 and clang from the LLVM 22.1.0 release (validated with a fresh clone and the local tools). The LanguageServer in Strict (the C# one is on the `dotnet` branch) waits until after the parallel loops and GPU (decided 2026-10-13, it needs console input and a JSON package), the VS Code client calls `strict` meanwhile: it reads the method headers itself for completion, hover, go to definition and signature help, suggests implementations from the tests of a method and reports methods that already exist (`MethodAlreadyExists`), both by running `strict test` on a temporary copy per candidate call (40 ms each). Found while doing that: a method with only test lines is no error, with one test line `strict test` says `All tests passed` without running a test (the line is taken as the implementation), with two it exits with 127 without any output, it should be an error with file and line (writing the tests first always starts like this). `strict test` of one file parses every `.strict` file of its folder, one file that does not parse fails the tests of all others. `strict check` should report a method that copies an existing method or whose tests a method of a type it uses passes (exactly one way to solve each problem), the client finds these in the repository: `CallTarget.TypeName` is `Natives.Short`, `Linker.Targets` is `TypeEntry.Invoked`, the `JoinElements`/`JoinArguments`/`JoinItems` loops of `DictionaryExpression`, `Instance`, `ListExpression`, `MethodCall` and `ValueListInstance` are the same, `Examples/Parsing` has `ExtractAfterKeyword` twice, `NumberSummer.Total` is `numbers.Sum`, `Vector2.X` and `Y` are `numbers.X` and `numbers.Y`, `ConstantCollapser.Inner` passes its test as `literal.Unquoted`. Later the search for implementations belongs into Strict too (`strict suggest <file> <method>` with real type inference, all candidates verified in one process instead of one each).
4. **Reflection** (later, only as use cases need it): `"Number" to Type` builds `Type("Number", "Strict")`, `5 to Type` (any other value) is its static type and `value is Number` is decided at compile time from the static type, on both backends. `value.Members` lists the stored members of an instance as `Variable`s (name, static type, value) and `HashCode` of an instance combines the hashes of its members: the compiler writes `Members` and `to HashCode` for every type that uses them (`Bytecode/Automatic`). Not supported yet: `to Type` of a Text that is not a literal (needs the type names at runtime), natively the value of such a `Variable` is a `Generic` without its type, it can not be printed or compared yet, the `Method` of a `Stacktrace` is its `Type.Method` text on both backends (a `Method` value needs the methods at runtime).
