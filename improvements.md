## Next
1. **CI complete and fast**: `.github/workflows/ci.yml` bootstraps from the seed (Linux ~6, Windows ~5 minutes), tests the quick folders on the VM and builds a few natively. Check the job times after the next push and add `Compiler` and `NeuralNetworks` (natively) while each job stays under 10 minutes.
2. **16 bit lists on the GPU**: bfloat16 lists (format 17) are read everywhere, but generated loops store 32 bits: storing bfloat16 in all of them made Qwen3.8 prompts of 1366+ tokens decode NaN (`DeltaChunks` pair matrices feed the triangular inverse). Next: a rule for which loops may store 16 bits (activations only 16 bit or int8 tensor core kernels read, no sums or inverses), measured on MossImage mix720 (bfloat16 3-4 % faster and closer to ComfyUI, PSNR 32.5 against 29.6 dB). Open: bf16 QK attention beyond the 128 wide QKV path; attention, product and hadamard results are 32 bit; joining lists of different formats goes through the host; LLVM 23 PTX of strict_device_whole(s) is ~3 % slower than LLVM 22's.
3. **Ternary Bonsai 27B** (`C:/code/Models/Bonsai`, NeuralNetworks/README.md): 15.1-16.4 ms per token on the RTX 4090 (Prism's llama.cpp ~11), 11.6 without the rotation. Next: (a) profile the ~3.5 ms of rotation (257 `Sylvester` kernels, 48 grouping loops, the rate products), fusing it into the products' quantize was slower; (b) on 10 GB cards steps stall (median 20, mean 313 ms): check StrictComfy's 256 MB own reserve (5c) there; (c) the dot products decode every PTQ1_0 block twice, the two lanes of a block should split the codes; (d) one kernel for 1 to 8 tokens (like Kindi's) so `LookupDecoding` verifies cheaper (2, 4, 8 tokens 27.7, 37.3, 47.2 ms against 16.8 for one) and keeps the tokens of plain decoding; (e) CPU loops unpack 3 bit rows to doubles (MlirWidths decodes only 4 and 6 bit blocks per use).
4. **Qwen3.8-Flash-Next** (qwen4exp, `C:/code/Models/FlashNext`, NeuralNetworks/README.md): ~280 ms per token, 325 with MTP drafts. Next: (a) the draft acceptance on a chat prompt with a longer answer and with 3 drafts (llama.cpp reports 89 %, here 7 and 12 of 24); (b) the 3 token `Steps` costs ~1.5 plain steps; (c) the QSA indexer past 2051 tokens.
5. **GPU memory at the edge of the WDDM budget**: H3 DiT steps (21.7 GB of weights, 5.3 GB streamed per step) take 3.5-3.9 s against ComfyUI's 3.2 s. Left: (a) uploads still wait in order where the prefetch chain (`strict_gpu_prefetch`, one spill ahead) breaks, about half of 6.5 GB per step: prefetch two rows or a block ahead; (b) power of two size classes keep 1.5 GB unused; finer classes churned activation blocks through the driver, they need activations kept and weights evicted first, or blocks lent across classes; (c) without spilled rows the trim before an own block runs at every block (H3 fully resident: 440 driver allocations and 200 syncs per step, 9.5-12 s against 2.8 s with `%ownReserve` at 256 MB instead of 1 GB in strict_gpu_device_alloc): trim only blocks not used again within a step, or validate 256 MB on 8-10 GB cards; (d) 8 bit rows with one scale keep a scale per 32 numbers on the GPU (2.4 GB of H3's 21.8 GB): one scale per row (bit 31 set: every 8 bit kernel reads scale 0) lets H3 nearly fit; (e) MossImage with ~0.9 GB used by other programs still has 1-8 full collections per step: a sub-allocating pool would end them.
6. **Loading big safetensors at file speed**: the 21 GB H3 DiT loads in 11-12 s (ComfyUI 5-7 s), mostly page faults of the copy into fresh memory (~5 GB/s on 48 threads). Next: 8 bit rows with one scale per row stay in the mapped file (no copy, also 5d).
7. **Generated GPU loops: vector coverage and fused memory passes**: they are instruction bound on the RTX 3080 (120-330 instructions per number). Left: (a) format mixes without an AOT copy (`MlirFormats` has all f32, all bfloat16 and first bfloat16) run the generic kernel: H3's `Rope.Rotated` with 16 bit norm weights 192 against 80 ms per step, Gated f32/bf16/f32; (b) a loop reading a member of an object parameter (`layout.width` in ../StrictComfy `H3Final.Unpatched`) stays on the CPU: pass loop invariant members as numbers; (c) bounds, reduction and tail checks remain, extend the four wide loads (`MlirBatched`) where counters show headroom (H3) and fuse memory passes. Details: `../StrictComfy/Handoff.md`.
8. **Trees as pools with 32 bit backward offsets** (from [Goose](https://github.com/aardappel/goose)): an immutable value is built after its members, so a type holding instances of itself (`SyntaxNode.children`) can keep all of them in one grow-only block linked by u32 backward offsets, one free per tree. Measure SyntaxNode allocations and bytes per `strict build Strict.strict` first.
9. **Small parallel loops cost up to 0.8 ms once the workers sleep**: every collecting loop of 256+ elements goes to the pool (`MlirParallel`), `List.Slice` of 1024 rows takes 0.4-0.8 ms (serial ~20 us) since waking 47 sleeping workers costs a system call each. A minimum chunk size (or the body's cost) should keep such loops on one thread.
10. **MOSS generation to VAE transition**: warm generation 4.10-4.18 s against ComfyUI's 3.51 s with sampling at parity: VAE decode 0.63 against 0.27 s, PNG encoding 0.28 against 0.08 s, cold loading. Details: `../StrictComfy/Performance.md`.
11. **A list literal as a call argument fails in the VM code generation**: `Joined(number, (Two,))` (`Joined(first Number, rest Numbers)`, `constant Two = 2`) dies with IndexOutOfRange in OperatorCodegen.Operation via ListCodegen.Argument (seen as `Network.Sent(client, (UnitCommand.MoveRight,))` in DeltaEngine), a `let` list works. Pass a list literal in an argument position as one list.
12. **Large grouped loop index precision** (3080, 2026-10-24): inlining `let half = size / 2` as `size / 2` in StrictComfy `MossBlock.Rotated` passes the small native tests but the full size kernel (3740 x 3072) gets 2.8M of 11.5M elements wrong (max difference 39). Reproduce with StrictComfy/benchmark_elementwise.py (STRICT_BENCH_KERNEL=Rotated, STRICT_BENCH_BOUNDS=1); suspect index precision or guard lowering.
13. **Native code generation bugs met in StrictComfy's H3 work** (2026-10-25, worked around there, the VM is right in a, b and d): (a) a member whose default is a composite type is not initialized (`has history SpectralHistory = SpectralHistory`, AccessViolation); (b) a parameter default `= List(MossLora)` compiles as `List(Generic)`; (c) indexing another type's constant `Texts` (`H3Lora.Linears(0)`) gives a list of characters on the VM and crashes natively, `for H3Lora.Linears` works; (d) a `List(List(Numbers))` of packed int8 matrices built by a `for` reads wrong numbers natively; (e) VM foreign calls take at most 5 numbers (with 6 the call crashed instead of failing). `NamedArguments` has two rules for which defaults a caller fills in: `IsComputed` for constructors (a member access like `Curve.Flat`) and `Computed` for methods (anything ConstantFolding can't make a literal); one rule for both may fix a and b.
14. **GPU-only lists can't be spilled**: activations computed on the GPU have no host copy, so keeping them alive across H3's 50 streamed blocks (Spectrum feature anchors, 2 x 160-320 MB) takes every byte from the streamed weights (steps 3.6 -> 5-7 s). Spillable activations (or an explicit move to the host) would allow feature forecasting.
15. **Linker and inference gaps** (2026-10-25): (a) constant initializers of linked types are not scanned for calls: `strict test Compiler/MlirModule.strict` prints "Unsupported native call Strict/Bytecode/InstructionEntry.LoadBoolean" four times; (b) a parameter without a type does not get the type of its constant default: `Combined(other = Short)` in Examples/Labeled reads `other.label` as `()`, `other Labeled = Short` works.

## Game engine (DeltaEngine)
iOS compiler foundation: `strict build <file> ios` stages an arm64/iOS 15 static archive with `strict_main` and content; Windows Mach-O/archive checks pass, native packages require full Xcode. MacMini SDK linking, device runtime/memory checks, UIKit/window/input/audio integration, app identity/signing and TestFlight remain. See [Compiler/IOS.md](Compiler/IOS.md) for the concrete handoff and old SoulCraft/iOS references.
1. **Android release path for SoulCraft**: Strict now stages an API 26 arm64-v8a `libmain.so` and `assets/Content` with `strict build <file> android`; APK/AAB creation, Activity/JNI lifecycle glue, Android window/input/audio backends and ASTC/ETC2 encoding/loading remain in DeltaEngine. Reference shipped app: `C:/code/_obs/DeltaAndroid/SoulCraft/Properties/AndroidManifest.xml`, package `de.mobilebits.soulcraftdefault`, version code `301000113`, target SDK 36. Preserve app identity, signing continuity and saves when replacing it. SoulCraft host tests pass from DeltaEngine root; the Android link currently stops at missing `stb_image.h` include paths in `Content/native/ImageFile.c` and `Graphics3D/native/Gpu.c` (missing Android native flags). Compiler ELF alignment is 16 KB; execution on a connected Android device still needs checking.
2. **Methods as values (function pointers) so one game loop serves all games**: `Games/*` each repeat the same `Played(application)` loop (21 occurrences of `Played(application`, the method plus its loop body, across `Games/*`, `RealTimeStrategy/RtsGame.strict` and `Frameworks/GameApplication.strict`) and the frame preamble because the loop needs `current.Frame(handle, now)` returning the concrete game type and `current.Closes(next)`. Traits (a type with methods without implementation, `README.md` members) are the intended shape: a game type could be used as a `GameLoop` trait and the shared loop would call `Frame`/`Closes` through it and get a `GameLoop` back (value-based selection like `NeuralNetworks/Activation.strict` works only for constants of one type, not for a different type per game). This needs (a) passing a type instance with methods into a member or parameter where a trait is expected, (b) a method that returns the trait type when the implementation returns its own type, and (c) the loop keeping that returned value without knowing the concrete type. `Games/*/Plan.md` and the shared `Frameworks/GameApplication.strict` describe the duplication.
3. **Networking for multiplayer**: no engine package exists, each game would hand-roll sockets. Wanted: a small transport trait (a mock plus a real socket implementation) and a lobby/match message layer so real time strategy games (Arena Wars, WebWars, ArmiesOfSteel) share it. Put the plan here before implementing, it is a large task.
4. **Spine 2D skeletal animation**: wanted for character and menu animation in Elemental, TinyBat and other 2D games; native Spine runtimes exist for C/C++ and can be wrapped once, then the `.strict` side only plays animations and sets skins.
5. **Platform services as trait implementations**: `Achievements`, `InAppPurchase` and login are traits with mocks in DeltaEngine; Steam, Google Play Games and Apple Game Center implement them (Steamworks, `play-games-services`, `GameKit`). A base login package (account id, name, avatar, sign in and out events) is wanted so all games report the same events.
6. **Native trait dispatch**: a call on a value whose static type is a trait is compiled to a call to the trait's own symbol (`GameApplication.analytics Analytics` produced `undefined symbol: Analytics_GameStarted`), and `Bytecode/Linker.strict` skips trait files on purpose, so a bodyless trait method only links when a `native/<Trait>.c` provides it (`Compiler/MlirForeign.strict` says the same). Traits therefore work on the Strict VM (`strict test`) but break `strict build` as soon as one is a member or parameter. DeltaEngine binds the concrete mock (`has analytics MockAnalytics = MockAnalytics.Empty`) instead. Resolving the call to the one implementation in the program, or specializing trait-typed parameters the way generic methods already are in `Bytecode/Specialization.strict`, would let `GameApplication` and platform services keep the trait type.
