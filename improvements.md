## Next

Add `Validators`, `Runtime`, `Expressions` and native builds back while it stays under 10 minutes; a failing native build prints the file and exit code. CI, `Toolchain.LinuxRelease`, `bootstrap.sh` and `MacOSTools` still use LLVM 22, move them to 23.1.3 like Windows (msys2 LLVM 23 needs cc-libs and gcc-libs 16, clang 23 too: LLVM 23 writes float literals as `f0x...`, which clang 22 can not read).
2. **Faster builds**: a gated program builds twice (`Name.test.exe`, then `Name.exe`, each compiling the bytecode from source), one bytecode load for both would save the second generation; native gates write no `.strictbinary`; generation is single threaded (10.8 s of `MlirModule.Declared` for `strict.exe`); the host build waits for the PTX; `--mlir-disable-threading` was needed for a threading race in 21.1.7, with 23.1.3 threaded runs give identical output (mlir-opt of `strict.exe` 4.2-4.7 -> 3.55 s, mlir-translate 2.5 -> 2.3 s): drop it once every platform uses 23.
3. **16 bit lists on the GPU**: lists of 2^20 numbers or more from generated loops and strict_device_whole are stored as bfloat16 (format 17, strict_gpu_stored; Moss residuals reach 41472, f16 could overflow), smaller ones stay 32 bit floats; every reader converts. MossImage mix720 steps are 3-4 % faster than with 32 bit lists (489-538 against 511-538 ms) and peak at 9.6 instead of 8.8 GB: (a) the attention prompt with bfloat16 keys and values only matches 32 bit (2.75 against 2.71 ms per call, synchronized) although it loads half the bytes; (b) the power of two block classes of the GPU pool keep more memory with mixed 16 and 32 bit lists (exact sizes from 16 MB on); (c) attention, products and hadamard results are still 32 bit (attention results in bfloat16 raised the step errors, 0.0080 -> 0.0086 at step 0, and slowed the VAE attention consumers); (d) lists joined with another format go through the host (KV caches growing past 2^20 numbers).
4. **Qwen3.8 for the robot arm**: MTP drafting 15.3-15.6 ms per token over 150 tokens (3 drafts, 2.78 tokens per step, Ollama's text), Ollama 13.3; plain decode 22 ms, prefill 1.83 ms per token at 460 tokens. A step is about 43 ms, the GPU busy 62 % of it (about 1800 launches per step, 59000 in 1.5 s): the host feeds 15-20 us per launch, so the DeltaNet replay of `Truncated` (per token `Updated` and `Read`) and the first segment after every download run the GPU dry (gaps of 1.7-2.9 ms each, `cuGraphExecUpdate` 0.15-0.5 ms and `cuGraphLaunch` 0.4-0.9 ms per segment under WDDM, 31 % of the busy host samples); restarting segments at 8 after host waits moved the gaps instead of removing them. Collections are 9 % (162 young and 6 full of 24 ms per 150 tokens), a live tokenizer makes a full one 107 ms (its million objects: keep the vocabulary in one text with offsets). Next: fewer launches per layer (quantize 185 and Scales 185 per step: Scales fused into Normalized, 8 bit inputs written by the producing kernels), one kernel per DeltaNet layer for the replay (a thread per state column loops over the kept tokens, the columns are independent), cheaper segments; speech to text, a small Strict endpoint the arm calls, the time from question to first sound. A loop calling `Length(start)` in `Corrected` stays on the CPU (find the rule in `MlirGpuCheck`).

## Bugs
- Qwen3.8 prompts of 911 tokens and more stop with `a loop on the GPU read outside of a list` in `DeltaChunks.Corrected` (`STRICT_GPU_CHECK=1` names the loop): it runs over 4 * 48 * 128 * tokens elements and its fourth part starts past 2^24 from 911 tokens on (910 prefills). A probe with the same `DeltaChunks` sizes, GPU computed inputs and the identical kernel passes at 950 tokens, so the Qwen3 run takes the generic 32 bit body (a failed guard), whose f32 index math is wrong past 2^24: find the failing guard, and make the generic body exact for loops of more than 2^24 elements.
- `Number to Text` writes numbers from 8 digits on with an exponent (`1.39002525e9`, even `9.002525e7`): whole numbers should print all their digits (DeviceBuild.Referenced takes its hash mod 9999991 to stay below it).
- `Text.Combine` of a list of numbers crashes natively with an access violation (the VM is fine).
