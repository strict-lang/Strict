# Improvements
In priority order. Remove what is done, add what is found, keep each item to what is still open (results go into the README of the package). Every item gets done before the bigger image processing and neural network examples, parallel loops and GPU (decided 2026-10-12).

1. **Prompt speed** (Qwen3-8B Q4_K_M on the RTX 4090, what is done and measured is in `NeuralNetworks/README.md`): prefill takes 1.8-2.0 ms per token at 10 tokens, 0.65 ms at 100 and 0.71-0.82 ms at 500 (attention is 170 of 357 ms at 500 tokens) (llama.cpp 1.18, 0.175 and 0.10 ms). Open: attention over the prompt in FlashAttention style (`Scores` takes 142 of 357 ms at 500 tokens, a warp per score of 128 numbers and half of the warps find their position hidden; the 32768 outputs from which a strided sum like `Merged` takes a thread per output are one threshold for all loops, measure it per loop when another kernel needs a different one), the tensor core tiles of `NativeRuntimeTokens.mlir` reach 6% of their peak (32 rows by 32 tokens per warp, every lane loads its fragments from global memory, no shared memory, the output and down projections of 4096 rows have too few tiles for all SMs at 100 tokens and splitting their columns over a block was slower), prompts below 32 tokens go row by row with dp4a; GPT-2 gets the same prefill (its prompt runs on the CPU, no loop reads 4M numbers before the logits).
2. **Batched decoding** (done and measured in `NeuralNetworks/README.md`): batch 8 decodes 725 tokens/s (llama.cpp 727), its matrix products take 9.0 of 11.0 ms per step (8 tokens per warp with dp4a, the tensor core tiles start at 32 tokens): the kernel waits on memory with 16 warps per SM (124 registers, 8 tokens of inputs in flight), sums of 16 input numbers from the quantize kernel instead of dp4a with ones did not help (135 registers halved the warps, capped at 128 the same speed, the tiles got slower than with their second mma), 3 or 4 blocks per SM spill; a step still idles 0.4-0.7 ms after downloading its tokens. Open: sequences of different lengths and continuous batching (all sequences are at the same position now), peak VRAM and p95 latency in `Qwen3Benchmark`, first target batch 8 x 4K.
3. **Long context decoding** (8 bit cache done, `Float8`, results in `NeuralNetworks/README.md`): decoding takes 9.1 ms after 1000 and 10.6 ms after 2000 tokens (7.1 ms after 10), attention reads one position per lane (`Merged` with a warp per output, `Scores` a warp per position), so the 4 times smaller 8 bit cache is not faster yet (11.0 ms after 2000 tokens, every 8 bit number of `Merged` goes through the generic element read); split the positions over blocks like flash decoding and read keys and values coalesced, then measure at 4K to 32K tokens.
4. **Language model leftovers**: sampling other than greedy (temperature, top-k, top-p) on the GPU; Qwen3-Coder-30B-A3B launches 1157 kernels per token, which keeps the CPU busy; GPT-2 spends 1.4 of its 2.1 ms per token in graph launches and waiting for the download; MXFP4 for gpt-oss, safetensors other than F32 (`OnlyFloat32TensorsAreSupported`); a program with a GPU loop carries the PTX of the whole device runtime (149 KB, `strict.exe` grew from 2.93 to 3.12 MB when two of its `Range` loops became kernels, the prompt kernels only come with `Batch.Sums`); per row `Summed` still checks its lists on the CPU, matrix rows are separate allocations (a full collection marks the 1.7M rows of the 8B, 140-216 ms); later for bigger models paged caches, prefix caching and moving inactive caches to the CPU. Each optimization stays switchable (`STRICT_GPU=0` for the CPU, `STRICT_GRAPHS=0`, `STRICT_YOUNG=0`, `STRICT_DP4A=0`) and gets measured before the next.
5. **Neural networks** (the use case, results in `NeuralNetworks/README.md`): every training step still builds new lists for activations, deltas and weights (about 38% of 784-64-6 MNIST training is allocating and collecting), a call with loop-invariant arguments runs on every iteration natively (could be hoisted), loops with calls (`activation.Output(...)`, `Row(...)`) take the checked path. Next: bigger networks to measure parallel `for` on all cores, SIMD and the GPU against the C# version; swish (its derivative needs the weighted sums, which `Network` does not keep). Only small inline data, bigger samples get their own repository like `../Mnist`.
6. **DeltaEngine performance**: on the Strict VM `+`, `Lerp` and constructors are full calls (`Bound` fills every member slot, `Constructed` checks `IsStruct` by name every time), assigning a replacement or `position + offset` back to the same mutable variable could write in place, types made only of numbers (Vector2, Size, ColorValue) could be stored flat (a `List(Vector2)` as one array of doubles). Every call without arguments looks up whether it reads a computed type constant (`Accessor.Constant`, 2% of Iris training), the Resolver could mark those calls once.

## Language and compiler
- **Positions in 32 bit kernels** (found 2026-10-17): a 32 bit GPU kernel computes `index` and positions like `row * positions + index` in floats, exact only up to 2^24, so a loop of more elements or reading a longer list now runs as the double kernel and its result comes back to the host (a 750 token prompt in one piece took 138 ms per token, before it failed with "a loop on the GPU read outside of a list", a loop over the 24576 gate and up rows times about 683 tokens already has more positions); integer positions in 32 bit kernels would keep them fast.
- **`value` parameter of a one-member type** (found 2026-10-16): in compiled code a parameter named `value` of a method of a type with one member is that member (`MlirTyped.Shuffled` printed its value as the type), the Strict VM keeps them apart, `strict check` could reject the name.
- **Natively a stack overflow ends the test executable** with the runtime message (`Error: StackOverflow, ...`, exit 127): no Strict stack and the other tests of the file do not run (the Strict VM returns a `StackOverflow` Error after 20000 nested calls, `Invocation.MaxDepth`).

## Rebalancing: native runner and C# integration (../Rebalancing)
Updated 2026-10-17: the user accepts final-digit floating-point rounding, including
`12345678.12345678m` returning as `12345678.1234568m`. Exact 28-place identity and decimal record/list
bindings are useful future features, but no longer block this migration. The financial core and
standalone Binance runner now execute in Strict; only generic Windows platform I/O is C.
The website consumes four native libraries through generated bindings under one host lock.
Captured comparisons: 1,500 allocation decisions with zero notional difference, 3,380 indicator
values with maximum relative error 2.89485e-12 and identical regime decisions, 1,280 spike prices
with zero difference. Revisions still cross as text to preserve adjacent 64-bit ticks.

Step-aware decimal fields/lists, exact int64 step counts, text lists and C# callbacks remain useful
interop extensions. The running application currently does not need host callbacks: its native
runner owns HTTP, settings files, journaling and logging, and ASP.NET invokes native calculations.
