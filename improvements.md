# Improvements
In priority order. Remove what is done, add what is found, keep each item to what is still open (results go into the README of the package). Every item gets done before the bigger image processing and neural network examples, parallel loops and GPU (decided 2026-10-12).

1. **Language models on the GPU** (asked 2026-10-15, RTX 4090 24 GB, Threadripper 3990X, 128 GB, what is done and measured is in `NeuralNetworks/README.md`): pass llama.cpp with the same GGUF weights and greedy sampling, Qwen3-8B Q4_K_M at batch 1 first (decode 7.0-7.1 ms per token against 7.25 ms, prefill 2.9 ms per prompt token against 1.1 ms at 10 tokens where llama.cpp batches 512 at 9413 tokens/s), then batch 8 x 4K. Open, in order: prefill that reads every weight once for all prompt tokens (`Batch.Sums` is one loop over rows times tokens, every element a dot of its row, on the CPU each token decodes the row again: 18 ms per token for the 0.6B, 190 ms for the 8B) and FlashAttention style attention over the prompt; attention that reads the cache coalesced at long contexts (700 tokens decode in 8.75 instead of 7.5 ms, `Merged` reads one position per lane); batched decoding (shared weights, per sequence caches, positions and sampling, continuous batching, paged and FP8 caches, prefix caching, CPU offloading of inactive caches) with batch 1/2/4/8/16 benchmarks; Qwen3-Coder-30B-A3B decodes in 5.0 ms (llama.cpp 4.78 ms, 209 tokens/s), its 1157 launches per token keep the CPU busy (a graph launch takes about 90 us there); pruning and speculative decoding experiments (start with GPT-2); GPT-2 runs its prompt on the CPU (no loop reads 4M numbers before the logits) and spends 1.4 of its 2.1 ms per token in graph launches and waiting for the download; a program with a GPU loop carries the PTX of the whole device runtime (134 KB, `strict.exe` grew from 2.93 to 3.08 MB when two of its `Range` loops became kernels); MXFP4 for gpt-oss, safetensors other than F32 (`OnlyFloat32TensorsAreSupported`); per row `Summed` still checks its lists on the CPU, matrix rows are separate allocations (a full collection marks the 1.7M rows of the 8B, 140-216 ms). Each optimization stays switchable (`STRICT_GPU=0` for the CPU, `STRICT_GRAPHS=0`, `STRICT_YOUNG=0`, `STRICT_DP4A=0`) and gets measured before the next. Found on the way: a parameter named `value` of a method of a type with one member is that member in compiled code (`MlirTyped.Shuffled` printed its value as the type), the Strict VM keeps them apart, `strict check` could reject the name.
2. **Neural networks** (the use case, results in `NeuralNetworks/README.md`): every training step still builds new lists for activations, deltas and weights (about 38% of 784-64-6 MNIST training is allocating and collecting), a call with loop-invariant arguments runs on every iteration natively (could be hoisted), loops with calls (`activation.Output(...)`, `Row(...)`) take the checked path. Next: bigger networks to measure parallel `for` on all cores, SIMD and the GPU against the C# version; swish (its derivative needs the weighted sums, which `Network` does not keep). Only small inline data, bigger samples get their own repository like `../Mnist`.
3. **DeltaEngine performance**: on the Strict VM `+`, `Lerp` and constructors are full calls (`Bound` fills every member slot, `Constructed` checks `IsStruct` by name every time), assigning a replacement or `position + offset` back to the same mutable variable could write in place, types made only of numbers (Vector2, Size, ColorValue) could be stored flat (a `List(Vector2)` as one array of doubles). Every call without arguments looks up whether it reads a computed type constant (`Accessor.Constant`, 2% of Iris training), the Resolver could mark those calls once.
4. **Tooling**: not reported yet: a method whose tests a method of a used type passes (exactly one way), a dropped call result of a method that can never return an Error (dropped operators, literals and variables are `UnusedValueMustBeRemoved`). `strict suggest <file> <method>` in Strict for the VS Code client (all candidates verified in one process). `strict test <folder> lines` builds all files in one executable (Bytecode: 44 files in 50 s, about 40 s of it clang), but one file that does not compile natively stops the whole folder and the whole repository takes longer than 4.5 minutes. `strict test <file> values` (README "Command line") runs the tests traced in a second `strict` process (`Runtime/TracedFrame` logs every line start and assignment, `ValueTrace` counts them, a few MB of output for a compiler file) and prints each line with its substituted expression and value or the values of its hits (VS Code client formats, 2026-10-16), records show their changed members first by name; later the Debug Adapter Protocol in the VM. Bytecode: copies of types from other packages and base types are still inlined into `.strictbinary` files (22% of WebWars, names differ by package), the `sources` entry repeats all paths (10 KB per file). A method that can never return an Error could skip the `CheckError` of its results (they made `strict.exe` 7% bigger, VM tests 10% slower). The LanguageServer waits until after the parallel loops and GPU (decided 2026-10-13).
5. **Reflection** (only as use cases need it): `to Type` of a Text that is not a literal (needs type names at runtime), natively a `Variable` value is a `Generic` without its type, a `Stacktrace`'s `Method` is `Type.Method` text (a `Method` value needs the methods at runtime).

## Rebalancing: native runner and C# integration (../Rebalancing)
Updated 2026-10-17: the user accepts final-digit floating-point rounding, including
`12345678.12345678m` returning as `12345678.1234568m`. Exact 28-place identity and decimal record/list
bindings are useful future features, but no longer block this migration. The financial core and
standalone Binance runner now execute in Strict; only generic Windows platform I/O is C.
The website consumes four native libraries through generated bindings under one host lock.
Captured comparisons: 1,500 allocation decisions with zero notional difference, 3,380 indicator
values with maximum relative error 2.89485e-12 and identical regime decisions, 1,280 spike prices
with zero difference. Revisions still cross as text to preserve adjacent 64-bit ticks.

Step-aware decimal fields/lists, exact int64 step counts, text lists and C# callbacks remain useful
interop extensions. The running application currently does not need host callbacks: its native
runner owns HTTP, settings files, journaling and logging, and ASP.NET invokes native calculations.
