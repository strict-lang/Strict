# Improvements
In priority order. Remove what is done, add what is found. Every item gets done before the bigger image processing and neural network examples, parallel loops and GPU (decided 2026-10-12).

1. **Neural networks** (the use case): `NeuralNetworks/` has a multilayer perceptron (`Layer` fully connected with sigmoid and one weight row per neuron, `Network` with backpropagation over any number of layers) `Xor.strict` learns XOR with 2-3-1 neurons in 20000 steps, `Csv` reads a CSV (a header line, the class in the last column) and scales every feature to 0..1, `Dataset.Images` reads PNG images from one folder per class, both one-hot encode the class and keep every fifth sample for testing: `Iris.strict` reaches 97% test accuracy with 4-8-3 neurons after 200 epochs, `Diabetes.strict` 72% on `diabetes.csv` (UCI Diabetic Retinopathy Debrecen, 1151 rows, 19 features) with 19-10-2 neurons after 200 epochs. They log their training time measured with `Process.Elapsed` (seconds since the process started): Xor trains in 7 ms natively (Strict VM 1.5 s), Iris in 17 ms (VM 4.4 s), Diabetes in 240 ms (was 670 ms: `%` of whole numbers uses integer remainder instead of `fmod`, for-expression results grow their list in place instead of allocating a view per element and start with the capacity of the loop, a loop over a list reads its items directly, a list parameter the method never changes is read through its items pointer fetched when the method starts, `Layer` keeps one weight row per neuron instead of dividing the weight index), that is 1.3 µs per sample for 210 weights, every step still builds new lists for the activations, deltas and weights. A method call with loop-invariant arguments runs on every iteration natively, the compiler could hoist it. `Digits.strict` classifies the 16x16 handwritten digits 0 to 3 of AiInvest (160 PNG images in `mnist/`, read with `ImageProcessing/Png` and `Compression/Inflate`): 100% test accuracy on the 32 held out images with 256-32-4 neurons after 100 epochs in 0.38 s natively (1.5 s before the result lists started with the loop's capacity and the rows), 3.3 ns per weight and sample for the forward and backward pass. The output layer is a softmax for several outputs (sigmoid for one) trained with cross entropy (output delta is output minus target), weights move with momentum 0.5 (heavy ball: the previous weights are the old list, one pass per row like plain gradient descent): Iris 22 ms, Diabetes 0.30 s, Digits 0.47 s with the same accuracy (Digits reaches it after 20 epochs already), XOR error 2.5e-5. Weights start in plus minus 1 / square root of the inputs and every epoch visits the samples in a new random order (`Dataset.Shuffled`, before all samples of one class came in a row): `Digits28.strict` learns the 28x28 JPG digits 4 to 9 of AiInvest (280 images in `mnist28/`) with 784-64-6 neurons, 82-88% test accuracy after 50 epochs in 2.6 s natively. Next: bigger networks to measure parallel speedups. The neural network is written in Strict, the old C# code in `C:\code\AiInvest\AiInvest.NeuralNetworks` (and the `AiInvest.NeuralNetworks.*` folders next to it) is only a guide, it has bugs (MatrixNetwork backprop drops the hidden gradient, the Tanh, Swish and Logistic derivatives, CrossEntropy ignores the target). Steps: XOR (`AiInvest.NeuralNetworks.Tests\LogicTests.cs`), a simple MNIST investigation (the digit images in `AiInvest.NeuralNetworks.Tests\Optimized16x16`, `SimpleMnistTraining` uses 256-64-1), then the usual samples (`iris.csv` and `diabetes.csv` in `AiInvest.Classifiers.RandomForest.Tests`), then bigger projects built on that. Number has `Exponential`, `Logarithm`, `SquareRoot`, `Random` (uniform below the value, seeded per run), `IsFinite`, `Round(decimals)`, bitwise `and`/`or`/`xor` and the constants `E`, `Pi`, `Phi`, lists have `Sum`, `Maximum` and `Minimum`. The goal is to find the performance bottlenecks and measure how much parallel `for` on all CPU cores, SIMD, GPU and CUDA through MLIR speed it up, compared with the C# version. Long term a more abstract language uses Strict like DNA: long chains of simple instructions that are easy to copy, change, merge and test, which the higher level rewrites, tests and evolves to reach its goals (trying different things, using what LLMs and other projects do).
2. **Tooling**: `.github/workflows/ci.yml` bootstraps from the seed on Linux with the LLVM 22 release archive, self builds until the fixpoint and runs every test on the Strict VM and natively (validated in a fresh WSL clone). Still open: a Windows job (msys2 mlir and LLVM 22). The LanguageServer in Strict (the C# one is on the `dotnet` branch) waits until after the parallel loops and GPU (decided 2026-10-13, it needs console input and a JSON package), the VS Code client calls `strict` meanwhile.
3. **Reflection** (later, only as use cases need it): `"Number" to Type` builds `Type("Number", "Strict")` and `value is Number` is decided at compile time from the static type, on both backends. Not supported yet: `to Type` of other values (`Any.strict`, `5 to Type` would be the static type) and of a Text that is not a literal (needs the type names at runtime), the members of an instance (`HashCode` hashes an instance through its text, member wise would be faster), the `Method` of a `Stacktrace` is its `Type.Method` text on both backends (a `Method` value needs the methods at runtime).
4. **Strict VM speed**: 255 ms for 1M iterations, about 6x slower than native (40 ms), but numeric code with method calls and lists is far slower: training `NeuralNetworks/Xor.strict` takes 1.1 s against 7 ms natively, `Iris.strict` 3.9 s against 17 ms (in the morning of 2026-10-12: 3.5 s and 25 s with process start), `ProcessImage` of the 400x300 progressive `test_image.jpg` 82 s against 250 ms. Constant lists are built once natively, `Resolver` finds the target of every call once when the types are loaded, the native loop improvements (for-expression lists grown in place with the loop's capacity, items read directly) help the VM as well. An element write to a list that is used elsewhere too no longer copies it: `strict_list_write` writes in place and turns the old header into a record of the replaced value, hoisted item pointers compare a global write counter that LLVM moves out of loops which never write. The records point from older to newer versions, so a stale reference to an old version (conservative stack scan) kept every later record alive (Iris used 1 GB): a list whose items live in its first block gets its own items array on the first versioned write and a new array after max(64, capacity) versioned writes, which bounds what one stale reference keeps (Iris 15 MB). Locals are slots: `Resolver` numbers the locals of every method when the types are loaded (`#this`, `value`, `#result`, `#flag`, `#loop`, `index`, then members, parameters and variables) and writes the slot into the instructions, `Frame` keeps them in one list, no local is found by name anymore and a call builds its locals in one allocation: Iris trains in 3.9 s (5.5 s before). A collection marks everything still alive (the loaded bytecode, the data), after at least 16 MB instead of 4 MB that costs less: Iris trains in 3.7 s instead of 4.5 s (8 MB 4.0 s, 32 MB 3.8 s), 1M loop iterations use 22 MB instead of 9 MB, native programs are unaffected. Number constants are decoded once when the types are loaded and `true` and `false` are shared values (no measurable change). The VM's Dictionary natives still scan all pairs (`Natives.Keyed`, natively an open addressing index in the list holder: 20000 Adds and lookups in 85 ms). An element write is versioned (`strict_list_write`, a 56 byte block per write) once the list was passed to a method that may keep it: a list passed to a method of the same type that neither stores nor returns it (`Borrowing` checks the callee's body, recursion assumed borrowing) stays owned and is written in place with `strict_list_set`. A returned list only escapes for that check, the method itself never writes it again. The VM loop (`Frame.Finished`) keeps locals and registers in one owned list written in place instead of a new `Frame` per instruction: `Resolver` puts the registers after the locals, sizes the list (`MethodEntry.Slots`) and appends to every instruction the slot its result goes to, the jump target and the loop begin, a loop keeps index and value in its state instead of three locals: Iris trains in 3.1 s instead of 4.0 s (64.7M steps). A call builds its slots in one list (`Machine.Bound`, the instance type is compared once instead of per member, a constant comes from the instance instead of being decoded again), `Looping` has no members (no helper instance per loop instruction), number constants are loaded without a `PayloadDecoder`: 2.8 s. Natively an instance constructed only from constants (`VmValue.None`, `true` and `false` values) is built once per place and pinned like a constant list instead of on every use (39 places in `strict.exe`): 2.55 s. A resolved instruction keeps its result slot in `InstructionEntry.Target` instead of the end of its payload, `Frame.Finished` reads the instruction list once and steps over plain instructions without calling `Next`: 2.3 s. Double constants of `StoreConstant` are decoded when loading too, a loop record keeps the kind of what it iterates as a number instead of comparing kind texts every iteration, `Machine.Call` computes the resolution once without another `Invocation`, member slots of an instance of the same type are read directly, a variable load goes from `Frame.Value` straight to `Frame.Local` which reads loop index and value without `Looping.Current`: 2.2 s (1.8x faster than 4.0 s). `Machine.Prepared` decodes the member values of every type once (one `Natives.Fresh` per type), a call takes its constants from there instead of decoding them again (`ProcessImage` decoded table constants 9.2M times because type qualified calls pass another type's instance), constructors start from that instance, `Natives.TypeOf` compares exact names first: Iris 2.1 s, `ProcessImage` 26.8 s instead of 82 s. Profile now: `Frame.Finished` 22% (pointer chasing through method, instruction list, entry and payload with bounds checks on every read), allocations about 15% (`Looping.Iterated`, `Machine.Bound` copies every member into the slots of each call), `Natives.Short` 3.4% (`Machine.MemberValue` compares type names). Next: a flat number encoding of the resolved instructions, members read from the instance instead of copied per call, `Natives.TypeOf` by index.
