# Improvements
In priority order. Remove what is done, add what is found, keep each item to what is still open (results go into the README of the package). Every item gets done before the bigger image processing and neural network examples, parallel loops and GPU (decided 2026-10-12).

1. **Decode speed** (Qwen3-8B Q4_K_M on the RTX 4090 at 6.6-6.7 ms per token, 150 tokens/s, results in `NeuralNetworks/README.md`): a step is now its kernels (6.55 ms), the GPU hardly idles. Open: fewer of the 15 launches per layer (attention is one kernel now): the query and key rotations in one kernel with keys and values appended as one contiguous part, the 145 quantize kernels (1 us each) done by the kernels that produce their inputs; the matrix products reach 885 GB/s for gate and up but 775-790 for the output projection, QKV and the 4 bit down projections (2-4 us of each kernel are ramp-up and tail).
2. **Prompt speed** (Qwen3-8B Q4_K_M on the RTX 4090, what is done and measured is in `NeuralNetworks/README.md`): prefill takes 1.6 ms per token at 10 tokens, 0.47 ms at 100, 0.21 ms at 460, 0.19 ms at 1820 and 0.20 ms at 3720 (the matrix products of a prompt are tiles of 64 rows by 64 tokens, `strict_device_tiles`, 62 of the 81 ms of kernels at 460 tokens, `Qwen3.Prefilled` sends up to 2048 tokens at once) (llama.cpp 1.18, 0.175 and 0.10 ms). Open: the GPU idles between the 689 launches of a 460 token prompt and when a full collection lands in the prefill (81 ms of kernels in 200 to 280 ms); the generated kernels reading exact positions take 10-25% longer than with float positions (`Rotated` 55 instead of 45 us, `Experts.Gated` 53 instead of 43, `Batch.Sums` 34 instead of 28 at 460 tokens: integer divisions for `Floor` and `%`, and a read falls back to the float position when the exact one is unknown, so both are computed); the tiles load the next 256 columns into registers while computing (3 barriers per 256 columns); ncu: 12 instructions per mma, 1.8 shared loads per mma, short scoreboard and MIO stalls at 16 warps per SM, padding the scales to 9 and 17 floats per row removed most bank conflicts (57M of 154M wavefronts) without making it faster, the float scaling after every 32 numbers is most of the work: accumulating the products of a block of 256 in integers (one token scale per 256 like Q8_K) and m16n8k32 (sm_80, 4 times the products per instruction, needs a second PTX module) are next, then 64 by 128 tiles, 8 bit rows still take `strict_device_blocks`; prefill times jump when a full collection lands in them (910 tokens 0.41-0.49 ms); the 32768 outputs from which a strided sum like `Merged` takes a thread per output are one threshold for all loops, measure it per loop when another kernel needs a different one; GPT-2 gets the same prefill (its prompt runs on the CPU, no loop reads 4M numbers before the logits).
3. **Batched decoding** (done and measured in `NeuralNetworks/README.md`): batch 8 decodes 953 tokens/s (llama.cpp 727) and 32 sequences 2357 tokens/s on the tensor cores (`strict_device_blocks`, 128 registers because the row by row path for other rows is in the same kernel, so 2 blocks of 8 warps per SM, capped at 80 or 64 registers it spills and gets slower); the Q6_K rows reach 540 GB/s against 790 for Q4_K at batch 8. Open: sequences of different lengths and continuous batching (all sequences are at the same position now), peak VRAM in `Qwen3Benchmark` (p95 is reported; batch 8 decodes 525 tokens/s after 3720 tokens with the 8 bit cache, median 15.2 ms per step, p95 51 ms because the first steps are slower).
4. **Long context decoding** (8 bit cache and flash decoding done, results in `NeuralNetworks/README.md`): decoding takes 7.6 ms after 1820 and 8.3 ms after 3720 tokens, 8.6 ms after 7450, 9.7 ms after 14900 and 12.8 ms after 29700 tokens with the 8 bit cache (prefill 0.24 and 0.29 ms per token). Open: the attention kernel uses 255 registers, so a block of 8 warps per SM and batch 32 runs its 256 blocks in two waves (13.8 ms per step).
5. **Language model leftovers**: Qwen3-Coder-30B-A3B launches 1157 kernels per token, which keeps the CPU busy, and `Qwen3CoderText` reports 430 ms per token because its 24 tokens include the first upload of the 18.6 GB of experts (283 synchronous copies at 2.3 GB/s from pageable memory); GPT-2 spends 1.4 of its 2.1 ms per token in graph launches and waiting for the download; MXFP4 for gpt-oss, safetensors other than F32 (`OnlyFloat32TensorsAreSupported`); a program with a GPU loop carries the PTX of the whole device runtime (149 KB, `strict.exe` grew from 2.93 to 3.12 MB when two of its `Range` loops became kernels, the prompt kernels only come with `Batch.Sums`); per row `Summed` still checks its lists on the CPU, matrix rows are separate allocations (a full collection marks the 1.7M rows of the 8B, 140-216 ms); later for bigger models paged caches, prefix caching and moving inactive caches to the CPU. Each optimization stays switchable (`STRICT_GPU=0` for the CPU, `STRICT_GRAPHS=0`, `STRICT_YOUNG=0`, `STRICT_DP4A=0`) and gets measured before the next.
6. **Neural networks** (the use case, results in `NeuralNetworks/README.md`): about half of 784-64-6 MNIST training (`../Mnist/Digits28`, 50 epochs in 0.78 s) is allocating, sweeping and zeroing, 12% is the math of `Layer.Row`; every step builds new lists for activations, deltas and weights. Reuse the memory of obvious cases instead (decided 2026-10-18): when an outer loop runs the next batch or step, the lists the previous one allocated and dropped can be filled again in place of allocating, sweeping and zeroing the same sizes again, no whole-program analysis needed for that (`previousWeights` keeps one older version alive for momentum). Loops with calls (`activation.Output(...)`, `Row(...)`) take the checked path. Next: bigger networks to measure parallel `for` on all cores, SIMD and the GPU against the C# version. Only small inline data, bigger samples get their own repository like `../Mnist`.
7. **Flat number types** (decided 2026-10-18): every type made only of numbers is stored as tightly packed 32 bit floats natively and, where possible, on the Strict VM: Degree, Radians, Ratio one float, Vector2 and Size two (PseudoRandom could simply be one number), Vector3 three, Quaternion and Rectangle four, Ray six, Matrix 16, and a `List(Vector2)` is one array of 8 bytes per element. Calls like `position.X` (`numbers.X`, then `List.X` returning `elements(0)`) must not survive Validators and Bytecode: they become direct reads of the float at its offset (element 3 `.Y` of a `List(Vector2)` is at 3 * 8 + 4 bytes), results stay 32 bit floats for physics, graphics, UI, matrices, math and neural networks. Today on the VM 300000 `position + Vector2(1, 2)` and 300000 `Lerp` take 5.8 s (`numbers.X` goes through the name comparisons of `Natives.Result` every time, `Bound` fills every member slot, `Constructed` checks `IsStruct` by name every time); assigning a replacement or `position + offset` back to the same mutable variable could write in place.
8. **Tooling**: not reported yet: a dropped call result of a method that can never return an Error (dropped operators, literals and variables are `UnusedValueMustBeRemoved`). `strict test <folder> lines` builds all files in one executable (Bytecode: 44 files in 50 s, about 40 s of it clang), the whole repository takes longer than 4.5 minutes. Rebuild and retest only what a change reaches (decided 2026-10-18): a changed file, its `.strictbinary` and the files and packages using it, the full rebuild of every bytecode file and test only once a day or before a big commit. `strict test <file> values` (README "Command line") runs the tests traced in a second `strict` process (`Runtime/TracedFrame` logs every line start and assignment, `ValueTrace` counts them, a few MB of output for a compiler file) and prints each line with its substituted expression and value or the values of its hits (VS Code client formats, 2026-10-16), records show their changed members first by name; later the Debug Adapter Protocol in the VM. Bytecode: copies of types from other packages and base types are still inlined into `.strictbinary` files (22% of WebWars, names differ by package), reference their binaries instead unless loading gets more than 25% slower (decided 2026-10-18: speed wins only above 25%, otherwise smaller files). The LanguageServer waits until after the parallel loops and GPU (decided 2026-10-13).
9. **Reflection** (only as use cases need it): `to Type` of a Text that is not a literal (needs type names at runtime), natively a `Variable` value is a `Generic` without its type, a `Stacktrace`'s `Method` is `Type.Method` text (a `Method` value needs the methods at runtime).
10. **Research** (when all other work is done): pruning (attention heads, MLP neurons, structured, low rank, skipping layers) and speculative decoding with a small draft model, start with GPT-2, judged by perplexity, coding tests and measured speed.

## Language and compiler
- **GPU kernels beyond NVIDIA** (found 2026-10-17): the device runtime and the tensor core kernels (`NativeRuntimeTokens.mlir`, `NativeRuntimeAttention.mlir`) call NVVM intrinsics directly. MLIR 22 lowers `gpu.subgroup_mma_*` to NVVM (wmma) but not to ROCDL ("failed to legalize gpu.subgroup_mma_load_matrix"), SPIR-V needs `spirv.entry_point_abi`. Before writing the next kernel by hand, check what MLIR already provides (`linalg` with the transform dialect's tensor core tiling, `nvgpu`/`amdgpu` mma ops), then port the existing kernels to it so AMD (ROCDL) and Vulkan (SPIR-V) get them too.
- **`()` crashes the bytecode generator** (found 2026-10-18): `Empty(1).None is ()` stops `strict test` with `Error: IndexOutOfRange at OperatorCodegen.Operation` (a node without children reaches `Negative(node.children(0))`) instead of a `ParsingFailed` error with file and line (an empty list is `List(Number)`).
- **Deep recursion** (decided 2026-10-18): `strict check` should reject recursion that obviously goes very deep (more than 1000 to 1M calls), unless it is tail recursion, which becomes a loop and may run as long as it wants (then natively no stack check is needed for it either).

## Rebalancing: native runner and C# integration (../Rebalancing)
Updated 2026-10-17: the user accepts final-digit floating-point rounding, including
`12345678.12345678m` returning as `12345678.1234568m`. Exact 28-place identity and decimal record/list
bindings are useful future features, but no longer block this migration. The financial core and
standalone Binance runner now execute in Strict; only generic Windows platform I/O is C.
The website consumes four native libraries through generated bindings under one host lock.
Captured comparisons: 1,500 allocation decisions with zero notional difference, 3,380 indicator
values with maximum relative error 2.89485e-12 and identical regime decisions, 1,280 spike prices
with zero difference. Revisions still cross as text to preserve adjacent 64-bit ticks.

Step-aware decimal fields/lists, exact int64 step counts, text lists and C# callbacks remain useful
interop extensions. The running application currently does not need host callbacks: its native
runner owns HTTP, settings files, journaling and logging, and ASP.NET invokes native calculations.
