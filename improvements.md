5. **GPU memory at the edge of the WDDM budget**: lists on the GPU are freed by their counts at a missing block (strict_rc_reclaim, device flag 64), so MossImage at 720x1280 runs without full collections per step (95 % GPU busy, 470 ms); with ~0.9 GB used by other programs the pool sits at its 256 MB headroom and still has 1-8 full collections, 2-5 cuMemAlloc/cuMemFree/cuCtxSynchronize and ~100 young collections per step (462-499 ms, was 1.5 s): a sub-allocating pool (any free block serves any size) would end that; measured on C:/StrictDumps/moss720 (8 GB peak, 240 ms steps) with another process holding 15.8 GB: steps take 320-485 ms with one 7 MB allocation and one young collection per step (printf probe in strict_gpu_alloc/free/strict_gc_run), so there it is WDDM paging at the edge of the budget, not the pool; the VAE decode after the steps allocates 5.7 GB in 68 blocks and frees 214 (446 ms), 6.4 instead of 1.2 s (14.5 GB held: no slowdown); the arena wrap synchronizes every second step; MossImage's per-step reference list (7 MB) is only freed by a later collection.
6. **Generated 32 bit GPU loops still cost 2-3x hand written kernels**: MossBlock_Rotated takes 279 us (exact kernel, 3740x3072 bfloat16) against 121 us for the same math in CUDA with checked loads (kb harness: the real PTX launched on synthetic data, scratchpad of the 2026-10-22 session). Measured by removing pieces of its PTX: the uniform format branch of every read (strict_device_floats, 32 or 16 bit) costs 69 us, the 64 bit and missing magic fallbacks of the three divisions 36 us; doing the format without a branch (both loads, one aligned load, predicated loads) or the bounds checks with selects measured slower. Both need the uniform launch values known when the kernel is compiled: a launch-time specialization (formats, exact parameters, magic numbers written into the PTX of a kernel at its first launch with them, cached per signature) would remove both. Divisions: positions are never negative, so a range analysis (loop index in [0, count), list positions in [0, length), the parameter values the host knows at the launch) that proves a numerator in [0, 2^32) can use the 32 bit magic number without the sign, size and divisor checks and their slow path: assuming that unchecked measured Rotated 279 -> 226 us, Gated 148 -> 144 us; a sign safe 64 bit magic number for every numerator instead measured slower (348 and 166 us, the 64 bit high multiply).
