2. **16 bit lists on the GPU**: bfloat16 lists (format 17: the high half of a float, same range, 8 bits of precision; Moss residuals reach 41472, f16 could overflow) are read everywhere (strict_device_elements, host unpacking, the guarded body, the int8 products epilogue, attention, quantize, hadamard, products and convolution); strict_device_whole writes them when strict_gpu_tokens asks for format 17, generated loops no longer do (format 0 by default): when every generated loop of 2^20 numbers and more stored bfloat16, Qwen3.8 prompts of 1366 tokens and more decoded NaN (the pair matrices of `DeltaChunks`, even elementwise ones like `Unit`, feed the triangular inverse, which amplifies their rounding). MossImage mix720 steps were 3-4 % faster with bfloat16 generated loops than with 32 bit lists (489-538 against 511-538 ms) and peak at 9.6 instead of 8.8 GB; on C:/StrictDumps/moss720 with STRICT_GPU=all bfloat16 lists give latent error 0.210 and PSNR 32.53 dB against ComfyUI's dumps, 32 bit lists 0.260 and 29.59 dB (ComfyUI computes in bfloat16 itself), steps 237-260 ms either way. Next: a rule for which loops may store 16 bits (activations that only 16 bit or int8 tensor core kernels read, not inputs of sums or inverses), measured on MossImage mix720 for speed and error. Open: (a) the attention prompt with bfloat16 keys and values only matches 32 bit (2.75 against 2.71 ms per call, synchronized) although it loads half the bytes; (b) the power of two block classes of the GPU pool keep more memory with mixed 16 and 32 bit lists (exact sizes from 16 MB on); (c) attention, products and hadamard results are still 32 bit (attention results in bfloat16 raised the step errors, 0.0080 -> 0.0086 at step 0, and slowed the VAE attention consumers); (d) lists joined with another format go through the host (KV caches growing past 2^20 numbers). (e) LLVM 23 PTX of strict_device_whole and strict_device_wholes is still slower than LLVM 22's (32 bit steps 476-492 ms with LLVM 22 PTX of these two kernels): the zero filled copies past the last stage took the branch out of the main loop (bfloat16 steps 492-508 -> 477-497 ms, 32 bit 511-525 -> 491-514), ptxas still drops the LTC128B L2 prefetch hint LLVM 22 PTX gets (an explicit .L2::128B measured no faster), the main loops are the same size (133-137 against 130 instructions), the rest of the difference is not found yet (nsys and ncu counters do not work on this machine).

4. **GPU memory at the edge of the WDDM budget**: lists on the GPU are freed by their counts at a missing block (strict_rc_reclaim, device flag 64), so MossImage at 720x1280 runs without full collections per step (95 % GPU busy, 470 ms); with ~0.9 GB used by other programs the pool sits at its 256 MB headroom and still has 1-8 full collections, 2-5 cuMemAlloc/cuMemFree/cuCtxSynchronize and ~100 young collections per step (462-499 ms, was 1.5 s): a sub-allocating pool (any free block serves any size) would end that; measured on C:/StrictDumps/moss720 (8 GB peak, 240 ms steps) with another process holding 15.8 GB: steps take 320-485 ms with one 7 MB allocation and one young collection per step (printf probe in strict_gpu_alloc/free/strict_gc_run), so there it is WDDM paging at the edge of the budget, not the pool; the VAE decode after the steps allocates 5.7 GB in 68 blocks and frees 214 (446 ms), 6.4 instead of 1.2 s (14.5 GB held: no slowdown); the arena wrap synchronizes every second step; MossImage's per-step reference list (7 MB) is only freed by a later collection.
5. **Generated 32 bit GPU loops still cost 2-3x hand written kernels**: MossBlock_Rotated takes 279 us (exact kernel, 3740x3072 bfloat16) against 121 us for the same math in CUDA with checked loads (kb harness: the real PTX launched on synthetic data, scratchpad of the 2026-10-22 session). Measured by removing pieces of its PTX: the uniform format branch of every read (strict_device_floats, 32 or 16 bit) costs 69 us, the 64 bit and missing magic fallbacks of the three divisions 36 us; doing the format without a branch (both loads, one aligned load, predicated loads) or the bounds checks with selects measured slower. Both need the uniform launch values known when the kernel is compiled: a launch-time specialization (formats, exact parameters, magic numbers written into the PTX of a kernel at its first launch with them, cached per signature) would remove both. Divisions: positions are never negative, so a range analysis (loop index in [0, count), list positions in [0, length), the parameter values the host knows at the launch) that proves a numerator in [0, 2^32) can use the 32 bit magic number without the sign, size and divisor checks and their slow path: assuming that unchecked measured Rotated 279 -> 226 us, Gated 148 -> 144 us; a sign safe 64 bit magic number for every numerator instead measured slower (348 and 166 us, the 64 bit high multiply).
