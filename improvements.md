# Improvements
What to fix next, one short line each, bugs first. Remove a line once it is done, add what is found at the end. No history or measurements (those go into commit messages). Speed work: [performance.md](performance.md).

## Bugs
- The compiler makes 3.7 million small objects (up to 16 KB) a second and its full collections visit up to 728 thousand of them (STRICT_GC_LOG prints both, its own build of NativeCompiler: 20 million in 5.5 s); reduce that first, then add the runtime rule: 10 thousand small objects collected every second for 5 seconds, or more than 100 thousand small live objects at once, end tests and plain builds and warn in release builds (H3Video's per-row LoRA lists, 4.9 million live, were found that way).
- Native Safetensors test `Nibbles.Tuned(...)` (line 21, in Entry) exceeds the 100 ms test budget every run (also before the rank above 512 GPU merge), passes on the VM.
- Routed attention (routing > 0) with strided values (valueOffset/valueStride) runs unrouted: `strict_gpu_attention` takes the routed 8 bit path only for packed values, so H3Block.Heads with V read from the combined list attends densely (6 s slower, 12.9 dB from the routed result), routing 0 is bit-identical; the per-token value quantization (`strict_device_quantize_rows_run`) and the pooled value means need strided rows, H3 keeps the copy until then.
- `"abc".Reverse` (a List method returning the list, called on a Text) gives `(", c, b, a, ")` on the VM and `undefined symbol: Text_Reverse` natively (Ben). `Text(text.characters.Reverse)` works on the VM, natively a Text's `characters` is the Text handle itself: `Length` works on it, Reverse, First and `Text.Combine` of it see an empty list. Decide one native List(Character) representation, then forward such calls to `characters` in ValueCodegen and convert back with `Text(...)`.
- Native `to Text` of a Float32 fails to compile ("unsupported: text of Float32"), every type should get Any's `to Text`.
- `ImageCodec.SaveJpeg` only works on Windows and the web (`JpegRequiresWindowsOrWeb` on Linux, macOS, Android, iOS): a baseline JPEG encoder in Strict next to ImageSaver's PNG would cover every platform.
- GPU memory grows while generating on the Qwen3.8 models (Bonsai 6.9 to 15.3 GB, Brilliance 17.2 to 22 GB), Qwen3-8B stays flat (Ben, not investigated).
- On the web dead values can stay roots: Asyncify saves every local that is live at any unwind point of a function with whatever it held last, and the collector scans them (strict_registers_spilled). The old value of an owned local is freed when it is replaced (strict_rc_dead), so `moss = Loaded(model)` releases the old Moss; a value that is not provably owned (passed to a method returning it, aliased) can still be kept by such a copy until the local is reused. Precise roots (reference locals in a shadow stack frame the collector scans instead of the Asyncify locals) would cover all of them.
- Lists of numbers made by generic list paths (`strict_list_add` growing `raw = raw + ...` in MersenneTwister.Uints, `strict_list_new` of other loops) are scanned by the collector: on wasm the halves of their numbers look like references and keep dead big lists alive while they live; they should be scanned only up to their items like `strict_numbers_new` lists.
- Two greedy runs of Qwen3-Coder-30B-A3B on the same prompt give different outputs (Ben, not investigated: atomics or reduction order in the expert path?).
- A GLSL shader that fails to compile in `Gpu.Program` is silently ignored: TorinsTowers with a broken WaterPlane fragment shader ran with exit 0 and no message; compile and link errors should stop with the info log and the .strict line.
- A named argument that skips parameters with defaults fails in bytecode codegen with `UnsupportedOperator` (OperatorCodegen line 157 via ListCodegen.Argument): `Release.Packaged(program, 0, isReleased = true)` and `Bytes.Hosted("a", picked = (2))`, positional arguments work.
- `Directory.Change` only works natively (strict.exe uses it to work from the project folder), on the VM it gives the Error DirectoryChangeNeedsNative: Runtime/Hosted calling it needs a stage A build and a regenerated Compiler/Bootstrap.mlir.
- `Error: OutOfMemory` has no .strict stack yet (it names the failed allocation and the heap since the commit retry).
- A failed GPU or driver allocation crashes with AccessViolation instead of OutOfMemory: a program making GPU lists under a 2 GB commit limit (Windows job object) ends with AccessViolation at a 0 MB heap.
- H3Video on the 4090: the full collection that frees the 27 GB text encoder takes 1.4-1.8 s (21 GB marked, 509 objects visited) and trips GarbageCollectionExceedsTenth; probably strict_gpu_sweep unlocking or freeing its pinned host memory (cuMemHostUnregister, cuMemFreeHost), not marking. Measure it there, then keep driver release time out of the collection time or release on another thread.
- `strict test Compiler/NativeBuild.strict` and `Compiler/DeviceBuild.strict` stop with GarbageCollectionExceedsTenth (NativeBuild in the Mlir tests, DeviceBuild after Built line 57; each method alone passes): the VM collects too often while combining the runtime texts.
- Qwen3Benchmark stops with GarbageCollectionExceedsTenth on long prompts (Qwen3-Coder 30B, repeats 137 or 200) in a plain build, release builds only warn.
- MossImage: the same seed gives a different image than the build of 2026-11-04 11:41 and loading Moss with its LoRAs got slower (7.2 to about 9 s); not from the C loop changes of 31ed107f (reverting them gives the same image and time), find the commit and check it is intended.
- Native tests of `Graphics3D/BillboardBatch.strict` (line 7) and `Skybox.strict` (line 8) stop with `Error: WindowNotOpen`: the inlined `Created` returns its Error from the test method instead of comparing it with `is Error` (the VM passes, also before 2026-11-05).
- `strict test Compiler native` and `strict test NeuralNetworks native --no-recursive` (sometimes also `Expressions`, DeltaEngine's `RealTimeStrategy`) stop with GarbageCollectionExceedsTenth in their frontend or emission (the plain built NativeCompiler, also before 2026-11-05); single files build and pass. The heap reaches 4-20 GB with under 300 MB live before the first big collection: the parallel emission allocates without collecting.

## Next
- GPU speed and memory: [improvements-gpu.md](improvements-gpu.md); Ternary Bonsai and Qwen3.8-Flash-Next: [improvements-models.md](improvements-models.md).
- Game engine (iOS, Android, one game loop, Spine, platform services): [improvements-engine.md](improvements-engine.md).
- Nightly CI: build and run every program's Run once a day (games and long running apps for a few frames); work too slow for a Slow test (rebuilding all content, big models) belongs in a Run, not in tests.
- Networking: `Http.Send`, `Http.Started`/`Received` and `Hmac.Sha256` are in (Windows, Linux and the web checked, macOS untested), DeltaEngine's Google sign-in and sheet downloads use them: switch Rebalancing's `NativeIO.Http`/`Hmac` (with the user, it trades live); client certificates when a program needs them, TLS for multiplayer sockets later.
- GPU sidecars: every program still keeps obj/Name.kernels.mlir (the PTX cache key) and its PTX in obj/ next to the source, move them into Tools/PtxCache once it evicts old entries (up to 25 MB each, never cleaned today).
- Realtime frames: a full collection at a frame end that takes longer than a few ms marks over several frame ends (incremental, the cards record what changed meanwhile).
- f32 kernels: a GPU loop reading a `value.Bits is 32` member computes in f32 (WGSL on WebGPU, the 32 bit CUDA kernel natively); WGSL lacks Float8 `from` calls, Bytes results and rows.
- MossImage in the browser (prompt in, encoder, Moss and VAE cached in OPFS, WebGPU like FractalZoomer): the VAE decode runs as WGSL kernels (Compiler/NativeRuntimeWgsl.js) with kept 16 bit maps; next Moss (an int8 GEMM with dot4I8Packed), the encoder, OPFS for the big models.
- Release builds: platform builds into Release/<Platform> are optimized without debug checks, logging or per-call checks (the web runtime already is), plain `strict build`, test executables and the VM keep them; native needs a release flag on `strict build` for local benchmarks.
- Native symbols, register kinds and helpers use the short type name, so one executable cannot hold two packages' types of the same name: qualify the symbols of a type whose short name is taken.
- Named iterators over counts (`for row, column in rows, width`) as one flat loop of rows * width with the names from the index (parallel, GPU kernel), then the `(index / n).Floor` and `index % n` loops of NeuralNetworks, Math/Matrix and the image decoders can name their iterators without losing their kernels.
- Parallel dedup by key (Ben): a `for` that keeps the first element per computed key (Dictionary or distinct by key) in parallel; Ben's program search keeps 2 of 128 cores busy because its observational equivalence dedup is a sequential loop over a mutable Dictionary.
- NeuralNetworks on the GPU (Ben): a program using NeuralNetworks (models, image and video generation) should get GPU kernels for every loop that can run there, also those the size heuristics keep on the CPU today.
- Loop conditions in the compiler (Ben): split loops on conditions that do not change in them (`range is 0` guards, mode flags like `isGray`) the way LoopPeeling splits first and last iterations; `strict check` only reports guards in inner loops.
- Branch probing in `strict check` (Ben): for a branch in an inner loop run the method's tests with only the then side and only the else side (SuggestionTests on the changed body); when one passes the branch is not needed or not tested, the issue says which side and how to fix it.
- Mutation testing (Ben): `strict test <file or folder> mutations` runs each method's mutants (comparison always true or false, default return, dropped reassignment or call, + and - or * and / swapped) on the VM and fails for every one that still passes; Math has 131 survivors, the base types 218, Validators 476, ImageProcessing 261, Compression 63 (mostly real: tests with 1 as a factor, no case below a bound). Fix them folder by folder, then make it the default; Json.strict takes over 2 minutes (each mutant inlines and resolves all types and computes all constants again, profile it), files whose tests take over 100 ms (Expressions, Bytecode, Runtime) are skipped.
- 32 bit loops (Ben): a vectorizable CPU loop (+ - * / over lists, not on the GPU, not a small constant count) over f64 Numbers fails the build with `VectorLoopMustUse32BitNumbers` (MlirNarrowing) until its lists say `with value.Bits is 32` (or 64 to keep them exact, a hard stop for narrowing); packed lists (Float32s, BFloat16s) compute in f32 with f64 sums (MlirSums: a 10 million dot takes 3.6 ms, 2.7 with f32 sums, 5.5 in f64); `value.Bits is 32` list members are stored packed natively (`strict_list_single`, format 32, 10 million sum of squares 4.3 -> 3.55 ms). A parallel CPU loop over a list of number-only structs fails the same way until each Number member (on the member, its one-number type or the iterated list) says `value.Bits is 32` or 64 (MlirWideMembers; DeltaEngine marked Particle, Lifetime, Torque2D, SceneryObject, AddDamageMessage, GhostTree). Next: inline structs still store such members in 8 bytes (only two marked numbers without defaults become one 8 byte pair, Lifetime's `age = 0` keeps it 16 bytes): store them as 4 byte floats (byte offsets in MlirEmbedded, f32 loads and stores), then ParticleStress drops from 72 to about 44 bytes per particle; a `value.Bits is 32` parameter reads whatever its caller passes (f64 unless the caller's list is packed).
