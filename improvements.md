# Improvements
In priority order. Remove what is done, add what is found.

1. **Packages**: a type is looked up in the current folder (a project folder without base types also includes all its sub folders), then next to `strict.exe` (also plain names in its packages, `Vector2` finds `Math/Vector2.strict`), then in the GitHub repositories linked in the project's `README.md` and the repositories of github.com/strict-lang: the folder holding `Type.strict` is downloaded with `curl` into the current folder (`Repositories.strict`), a type found nowhere is a `TypeNotFound` error with file, line and tips. Still open:
   - Only declared types (members, parameters, return types) are checked, a type only used in a method body (`Vector2(1, 2)`) still fails later instead of being looked up.
   - Without a token the GitHub API allows 60 requests per hour, each missing type costs the organization listing and one request per repository.
   - Only the `.strict` files directly in the package folder are downloaded (no sub packages), a newer version needs the folder deleted first.
2. **`.strictbinary` cache**: `strict <file>`, `test` and `build` write `Name.strictbinary` next to `Name.strict` once all its tests passed: a zip with a `sources` entry (format version, build time of `strict`, every source file the compiler reads with its hash) and one entry per used type (`TypeEntry.Bytes`, read back by `EntryDecoder`). While it is up to date the tests count as passed and its bytecode is used instead of compiling again (`strict test Strict.strict` 3.3 s, cached 0.15 s, a self-build 27 s before, 15 s now). Still open:
   - The zip CRC is computed without bitwise operators (`Floor` and `%` per nibble): about 300 ms of the 446 KB `Strict.strictbinary`. Bitwise operators on Number (ask first) or a native would take about 1 ms.
   - The stamp is the modification time of the running `strict` executable, so two copies (the VS Code one, a self-build copy) invalidate each other's caches, a hash of the executable would not.
   - An up to date check still reads and hashes every source file the compiler would read (60-150 ms).
   - Tests that read other files (`NativeRuntime.mlir`, images) are not rerun when only those files change.
3. **Neural networks** (the use case): a multilayer perceptron written in Strict, the old C# code in `C:\code\AiInvest\AiInvest.NeuralNetworks` (and the `AiInvest.NeuralNetworks.*` folders next to it) is only a guide, it has bugs (MatrixNetwork backprop drops the hidden gradient, the Tanh, Swish and Logistic derivatives, CrossEntropy ignores the target). Steps: XOR (`AiInvest.NeuralNetworks.Tests\LogicTests.cs`), a simple MNIST investigation (the digit images in `AiInvest.NeuralNetworks.Tests\Optimized16x16`, `SimpleMnistTraining` uses 256-64-1), then the usual samples (`iris.csv` and `diabetes.csv` in `AiInvest.Classifiers.RandomForest.Tests`), then bigger projects built on that. Needs Exp, Log, SquareRoot and Random (new Number methods, ask first) and image loading natively (see Native gaps). The goal is to find the performance bottlenecks and measure how much parallel `for` on all CPU cores, SIMD, GPU and CUDA through MLIR speed it up, compared with the C# version. Long term a more abstract language uses Strict like DNA: long chains of simple instructions that are easy to copy, change, merge and test, which the higher level rewrites, tests and evolves to reach its goals (trying different things, using what LLMs and other projects do).
4. **Dictionary generics**: `Dictionary(K, V)` works natively and on the Strict VM. It is built from type arguments or pairs, and its methods are runtime natives over the list of pairs (`Dictionary.strict` is the specification): Length, `in`, get (also `prices("apple")`), Add with DuplicateKey, Remove, and `is` between different type arguments. `for` over a dictionary gives its pairs (`value.Key`, `value.Value`), typed `List(K, V)` when key and value types differ, and such pairs compare and print natively too. Still open: natively only Text and Number keys and values compare and print (a pair with a Boolean or a struct value compares its slots as numbers); generic types other than List and Dictionary are not instantiated.
5. **HashCode**: `HashCode.strict` hashes a number to itself, texts and lists by combining their elements (times 31, modulo 2^32, `"abc"` is 96354), anything else through its text. Native Dictionary lookups use an open addressing index kept in the list holder, built on the first lookup and extended after appends (20000 Adds and lookups: 550 ms before, 85 ms now). Still open: the Strict VM's Dictionary natives still scan all pairs, and hashing an instance through its text is slow (a member wise hash needs reflection).
6. **Operator overloads by parameter type**: list `-`, `*`, `/` (with a list or a number), `3 + (4)`, Reverse, out of range indexes and the downcast Error work natively and on the Strict VM, `List.strict` passes on both. Overloads with the same argument count are chosen by the argument types (`Vector2 * Vector2` is the dot product, `Vector2 * 3` scales) on both backends. Still open: a method call overload (`a.Scaled(3)`) whose return type differs from the other overloads is typed with the last one (only operators use the chosen overload's return type), and an argument that only converts to the parameter type (Number to Byte, anything to Generic) falls back to the first overload with that count. Indexing another type's constant list (`MlirLists.Steps(4)`) is unsupported natively.
7. **Errors instead of crashes**: the VM crashes are gone, failing tests print their value, but there is still no RuntimeError with a stack trace back to the `.strict` line.
   - A parse error (e.g. `number + + other` in a method body) crashes the same way (exit 139) instead of printing a ParsingFailed message with file and line.
8. **Output for VS Code**:
   - `test`: print one line per test (passed or failed, with its line number and duration) and a total. Then the client no longer guesses passes from missing failure lines, and a crash no longer marks passed tests as failed.
   - Add a folder mode for `test`: today every file starts its own process, which parses all files and infers all types again.
   - `strict test` answers from an up to date `.strictbinary` in about 100 ms (a changed type used by the file makes it outdated too), so the client can run it for every file instead of comparing modification times.
   - `check` issues need a line number: the client marks the first line containing the target for now. A folder outside root is printed with mixed separators (`C:/.../pkg\Unused.strict`).
9. **Native gaps**:
   - `Character("b").number` prints `b` instead of 98, the member load keeps the Character kind.
   - `Character.Tab` is `Character(7)` (the bell), a tab is 9, the test in `Character.strict` checks the wrong value.
   - Logging a one-member instance prints its member natively but `(member)` on the Strict VM and in C# (`Examples/ProcessProbe.strict`: `Process.Find("nasm")`).
   - ImageProcessing executables crash when run (Image and ColorValue members), `ProcessImage.strict` does not build (`ImageLoader.Width` is unsupported natively).
10. **Validators**: a `let` with only constant values must be `constant`. The check misses list literals.
11. **Tooling**: LanguageServer in Strict (the C# one is on the `dotnet` branch), CI with the native toolchain. A running `strict.exe` can't overwrite itself on Windows, building `Strict.strict` goes through a copy (linking to a new name and swapping it in would avoid that).
12. **Reflection** (later, only as use cases need it): `"Number" to Type` builds `Type("Number", "Strict")` and `value is Number` is decided at compile time from the static type, on both backends. Not supported yet: `to Type` of other values (`Any.strict`, `5 to Type` would be the static type) and of a Text that is not a literal (needs the type names at runtime).
13. **Strict VM speed**: 245 ms for 1M iterations, about 5x slower than native (45 ms). Fast enough for now. When needed, update frames and registers in place for values with only one reference.
14. **Mutable as signals** (design decision, from the 2023 blog post "mutable"): `mutable squareArea = length * length` would keep recomputing when `length` changes, while `constant` stays the first value. Today a `mutable` only changes when it is reassigned (README). Within one method the compiler could recompute the dependent mutables after each reassignment of their inputs; members would need dependency tracking across methods.
