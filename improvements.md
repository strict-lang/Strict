# Improvements
Bugs to fix, most harmful first, one short line each. Remove a line once it is done, add what is found. No history or measurements (those go into commit messages). Speed work: [performance.md](performance.md). Anything large or difficult, features and far fetched things: [ideas.md](ideas.md).

- Two greedy runs of Qwen3-Coder-30B-A3B on the same prompt give different outputs (Ben, not investigated: atomics or reduction order in the expert path?).
- Qwen3.8 27B decode on the 4090 sometimes runs at 20.5 ms per token until about token 70, then stalls once for 0.7 s and continues at 27-31 ms: GPU memory reaches 22.6 of 24 GB in 256 MB steps, the same binary was fast an hour before; find what grows and what the trim then evicts.
- Once in 8 Qwen3-Coder 30B runs, right after loading, a full collection followed another (19 in a row, about 40 ms each, nothing freed) until GarbageCollectionExceedsLimit: probably the own block path of strict_gpu_obtain, whose pause after a collection is skipped when it freed one reusable block.
- Two packages with a type of the same name (Left/Point and Right/Point, each used by a type of its package): the front end stops with AmbiguousType even inside each package's own Point (its own package should win), and natively the symbols, register kinds and helpers use the short type name, so one executable cannot hold both yet: qualify the symbols of a type whose short name is taken.
- On the web dead values can stay roots: Asyncify saves every local that is live at any unwind point of a function with whatever it held last, and the collector scans them (strict_registers_spilled). The old value of an owned local is freed when it is replaced (strict_rc_dead), so `moss = Loaded(model)` releases the old Moss; a value that is not provably owned (passed to a method returning it, aliased) can still be kept by such a copy until the local is reused. Precise roots (reference locals in a shadow stack frame the collector scans instead of the Asyncify locals) would cover all of them.
- Lists of numbers made by generic list paths (`strict_list_add` growing `raw = raw + ...` in MersenneTwister.Uints, `strict_list_new` of other loops) are scanned by the collector: on wasm the halves of their numbers look like references and keep dead big lists alive while they live; they should be scanned only up to their items like `strict_numbers_new` lists.
