# Improvements
In priority order. Remove what is done, add what is found, keep each item to what is still open (results go into the README of the package). Every item gets done before the bigger image processing and neural network examples, parallel loops and GPU (decided 2026-10-12).

1. **Decode speed** (Qwen3-8B Q4_K_M on the RTX 4090 at 6.6-6.7 ms per token, 150 tokens/s, results in `NeuralNetworks/README.md`): a step is now its kernels (6.55 ms), the GPU hardly idles. Open: fewer of the 15 launches per layer (attention is one kernel now): the query and key rotations in one kernel with keys and values appended as one contiguous part, the 145 quantize kernels (1 us each) done by the kernels that produce their inputs; the matrix products reach 885 GB/s for gate and up but 775-790 for the output projection, QKV and the 4 bit down projections (2-4 us of each kernel are ramp-up and tail).
2. **Prompt speed** (Qwen3-8B Q4_K_M on the RTX 4090, what is done and measured is in `NeuralNetworks/README.md`): prefill takes 1.0-1.2 ms per token at 10 tokens, 0.21 ms at 100, 0.15 ms at 460, 0.15 ms at 1820 and 0.17 ms at 3720 (the fastest of 3 prefills in `Qwen3Benchmark`; the matrix products of a prompt are tiles of 128 rows by 64 tokens, `strict_device_tiles`, which add the biases when they store (with fewer tiles than multiprocessors the blocks of a tile split its columns and the last adds up their sums, 70 and 100 tokens 16% faster), `Qwen3.Prefilled` sends up to 2048 tokens at once) (llama.cpp 1.18, 0.175 and 0.10 ms). Open: the GPU idles between the 545 launches of a 460 token prompt and when a full collection lands in the prefill (81 ms of kernels in 200 to 280 ms); the generated kernels reading exact positions (`Rotated`, `Normalized`, `Experts.Gated`, 38 of 291 ms at 1820 tokens) are mostly bound by memory: without the float fallback of a read they execute 14-20% fewer instructions but save only 2 ms (and a non-integral position would fail instead of being cut like on the Strict VM), exact fractions of floats (power of 2 denominators) instead of the fallback make the denominators of parameters unknown and cost more than they save, branching around the fallback did not move the float positions out of the way; the tiles take mma.m16n8k32 from sm_80 on and load the next 256 columns into registers while computing, ncu at 460 tokens (gate and up, base clocks, 746 instead of 1022 us; 128 instead of 64 rows per block 807 to 763 us, the token sums added up when the tokens are put 749): 32 instructions per m16n8k32 (16 of them the float scaling after every 32 numbers), its 8 steps of 32 numbers take 44% of the time, staging the next 256 columns 36% (setup and the first stage 10%, prepare 12%, put 9%, fetch 5%), the barriers 14%, the stores 6%; decoding the scales of the Q4_K headers in put instead of prepare only moved the work (more instructions, same time), blocks that go on to their next tile (one per SM, the first stage of a tile loaded during the last products of the one before) took 880 instead of 749 us (spills, more state per 256 columns). Next: tiles of 128 by 128 with 8 warps of up to 255 registers like llama.cpp (each warp 32 by 64, more products per staged byte and per scale load); accumulating a block of 256 in integers needs one token scale per 256 (like Q8_K) and 16 more registers; Q6_K rows are not unpacked yet (9.9 instead of 7.4 us per million weights), 8 bit rows still take `strict_device_blocks`; prefill times jump when a full collection lands in them (910 tokens 0.41-0.49 ms); the 32768 outputs from which a strided sum like `Merged` takes a thread per output are one threshold for all loops, measure it per loop when another kernel needs a different one; GPT-2 gets the same prefill (its prompt runs on the CPU, no loop reads 4M numbers before the logits).
3. **Batched decoding** (done and measured in `NeuralNetworks/README.md`): batch 8 decodes 953 tokens/s (llama.cpp 727) and 32 sequences 2357 tokens/s on the tensor cores (`strict_device_blocks`, 128 registers because the row by row path for other rows is in the same kernel, so 2 blocks of 8 warps per SM, capped at 80 or 64 registers it spills and gets slower); the Q6_K rows reach 540 GB/s against 790 for Q4_K at batch 8. Open: sequences of different lengths and continuous batching (all sequences are at the same position now), peak VRAM in `Qwen3Benchmark` (p95 is reported; batch 8 decodes 525 tokens/s after 3720 tokens with the 8 bit cache, median 15.2 ms per step, p95 51 ms because the first steps are slower).
4. **Long context decoding** (8 bit cache and flash decoding done, results in `NeuralNetworks/README.md`): decoding takes 7.6 ms after 1820 and 8.3 ms after 3720 tokens, 8.6 ms after 7450, 9.7 ms after 14900 and 12.8 ms after 29700 tokens with the 8 bit cache (prefill 0.19 and 0.25 ms per token). Open: the attention kernel uses 255 registers, so a block of 8 warps per SM and batch 32 runs its 256 blocks in two waves (13.8 ms per step).
5. **Language model leftovers**: Qwen3-Coder-30B-A3B launches 1157 kernels per token, which keeps the CPU busy, and `Qwen3CoderText` reports 430 ms per token because its 24 tokens include the first upload of the 18.6 GB of experts (283 synchronous copies at 2.3 GB/s from pageable memory); GPT-2 spends 1.4 of its 2.1 ms per token in graph launches and waiting for the download; MXFP4 for gpt-oss, safetensors other than F32 (`OnlyFloat32TensorsAreSupported`); a program with a GPU loop carries the PTX of the whole device runtime (149 KB, `strict.exe` grew from 2.93 to 3.12 MB when two of its `Range` loops became kernels, the prompt kernels only come with `Batch.Sums`); per row `Summed` still checks its lists on the CPU, matrix rows are separate allocations (a full collection marks the 1.7M rows of the 8B, 140-216 ms); later for bigger models paged caches, prefix caching and moving inactive caches to the CPU. Each optimization stays switchable (`STRICT_GPU=0` for the CPU, `STRICT_GRAPHS=0`, `STRICT_YOUNG=0`, `STRICT_DP4A=0`) and gets measured before the next.
6. **Neural networks** (the use case, results in `NeuralNetworks/README.md`): about half of 784-64-6 MNIST training (`../Mnist/Digits28`, 50 epochs in 0.78 s) is allocating, sweeping and zeroing, 12% is the math of `Layer.Row`; every step builds new lists for activations, deltas and weights. Reuse the memory of obvious cases instead (decided 2026-10-18): when an outer loop runs the next batch or step, the lists the previous one allocated and dropped can be filled again in place of allocating, sweeping and zeroing the same sizes again, no whole-program analysis needed for that (`previousWeights` keeps one older version alive for momentum). Measured 2026-10-18 (Digits28, 0.75 s): self time is 22% memset of reused spans, 16% marking, 8% sweeping, 30% math, but skipping the memset only saves 4% because it just touches the memory first: the cost is every step allocating fresh lists (weights rows, activations, deltas) that the collector frees only every 16 to 32 MB, so they always come from outside the cache. Reuse is deferred reference counting (decided 2026-10-18, general for every repeated loop: game engine, physics, neural networks): every object counts the references stored in other heap objects (list items, instance members, holders, error traces), locals stay uncounted; a new object starts at 0 in a zero count table, a reclaim pass scans only the stack and frees what has count 0 and is not on it, decrementing its children in cascade, so the next iteration allocates the same hot blocks without tracing survivors (the weights in use have counts). Done: (a) counts for every heap reference store of the runtime and the generated code (lists of numbers filled by loops skip it, 850 instead of 790 ms for Digits28 with the sweep now zeroing what it frees), (b) `STRICT_RC_CHECK=1`: 349 test programs and strict.exe itself report no count too low. Next: (c) the table, reclaim and freeing (one object back to its size class: clear its mark, only on swept pages, large objects unlinked), measured on MNIST and a game loop; (d) unique values (count 0, only one local) rewritten in place. The mark-sweep collector stays for cycles and missed decrements. Loops with calls (`activation.Output(...)`, `Row(...)`) take the checked path. Next: bigger networks to measure parallel `for` on all cores, SIMD and the GPU against the C# version. Only small inline data, bigger samples get their own repository like `../Mnist`.
7. **Flat number types** (decided 2026-10-18): every type made only of numbers is stored as tightly packed 32 bit floats natively and, where possible, on the Strict VM: Degree, Radians, Ratio one float, Vector2 and Size two (PseudoRandom could simply be one number), Vector3 three, Quaternion and Rectangle four, Ray six, Matrix 16, and a `List(Vector2)` is one array of 8 bytes per element; results stay 32 bit floats for physics, graphics, UI, matrices, math and neural networks. Done: the Strict VM inlines small methods (`Inliner`, `position.X` is one element read, the Vector2 loop of 300000 `position + Vector2(1, 2)` and 300000 `Lerp` 6.3 to 4.4 s); natively a type whose only member is two numbers (`has numbers with Length is 2`, Vector2) is one 64-bit slot of two 32 bit floats (`MlirPairs`, constructing packs, `X`/`Y`/`Length`/`Atan`/`to Text`/`is` work on the slot, the same loop 24-28 to 8-10 ms). Next natively (one type shape at a time, each measured, DeltaEngine and SoulCraft built against it at the end): (a) Size (two Number members) as such a slot too (written and tested 2026-10-18, not committed: the 32 bit rule needs to know a type's package, but types of the compiled package have no prefix, `Size` and `Vector2` in Math, `Strict/Number` for base types, so `Range` or a Bytecode type of two numbers would become 32 bit too; needs the package in `TypeEntry` or passed to the compiler; until then every `has numbers with Length is 2` type is 32 bit, not only Math), a pair passed where a list is expected (as Numbers, iterated) unpacked there, a list passed as a Vector2 argument packed; (b) types of 3 to 16 numbers (Vector3, Quaternion, Rectangle, Ray, Matrix) are one block of exactly their floats without a list header, a list of them one array of such elements; (c) the Strict VM keeps the same 32 bit values, so both backends round alike (tests comparing exact doubles of these types change). Also: assigning a replacement or `position + offset` back to the same mutable variable could write in place.

## Language and compiler
- **strict.exe embeds the PTX of the device runtime** (found 2026-10-18): since `f35234ff` the loops of `EntryDecoder.Payload` and `ZipReader.Content` become GPU kernels in `strict.exe` itself, its data grew from 0.6 to 1.8 MB (`strict.exe` 3.3 to 4.5 MB) for loops that never get enough data for the GPU. -> can we just split up what is needed at the bare minimum for strict.exe and extensions like GPU kernels support into an extra file that is loaded on demand (and can be left out for non-GPU programs, simple stuff just need simple things, bloating everything up with the fully powerful strict.exe containing everything is not a great solution). Maybe we could also have strict.tiny.exe (bare minimum, nothing optimized, just the base library will work) and strict.full.exe (everything included, GPU stuff, etc.) and the normal strict.exe something in between ..
- **GPU kernels beyond NVIDIA** (found 2026-10-17): the device runtime and the tensor core kernels (`NativeRuntimeTokens.mlir`, `NativeRuntimeAttention.mlir`) call NVVM intrinsics directly. MLIR 22 lowers `gpu.subgroup_mma_*` to NVVM (wmma) but not to ROCDL ("failed to legalize gpu.subgroup_mma_load_matrix"), SPIR-V needs `spirv.entry_point_abi`. Before writing the next kernel by hand, check what MLIR already provides (`linalg` with the transform dialect's tensor core tiling, `nvgpu`/`amdgpu` mma ops), then port the existing kernels to it so AMD (ROCDL) and Vulkan (SPIR-V) get them too.

## Rebalancing: native runner and C# integration (../Rebalancing)
Updated 2026-10-17: the user accepts final-digit floating-point rounding, including
`12345678.12345678m` returning as `12345678.1234568m`. Exact 28-place identity and decimal record/list
bindings are useful future features, but no longer block this migration. The financial core and
standalone Binance runner now execute in Strict; only generic Windows platform I/O is C.
The website consumes four native libraries through generated bindings under one host lock.
Captured comparisons: 1,500 allocation decisions with zero notional difference, 3,380 indicator
values with maximum relative error 2.89485e-12 and identical regime decisions, 1,280 spike prices
with zero difference. Revisions still cross as text to preserve adjacent 64-bit ticks.

Step-aware decimal fields/lists, exact int64 step counts, text lists and C# callbacks remain useful
interop extensions. The running application currently does not need host callbacks: its native
runner owns HTTP, settings files, journaling and logging, and ASP.NET invokes native calculations.
