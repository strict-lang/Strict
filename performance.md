# Performance
Measured speed work, compiler front end first. One item per finding, removed when done or no longer true.

## Front end, checks, tests and the server
- Cache loading: `EntryDecoder.Of` turns all bytes of a cached type into varints and names (`ByteEncoder.Integers`) also when only its method names are asked (`BinaryLinks.IsTested`, 100-170 ms of the 230 ms stale scan of Strict's 426 test files on one thread, reading and the head 65-130 ms more). Decode varints and names natively. An up to date `strict test` of Qwen3Benchmark takes 220 ms, scripts never take the cache.
- Compiler self-build after a one-line edit of a compiler file (BuildProfile 2026-11-26, 64.5-66.7 s): link 12.5-14.8 s; new executable checks 14.9-16 s, the critical path is `check Expressions` re-testing under the new exe (stamps include the exe on purpose, the four checks already run in parallel and need the linked exe); the test gate (Verified, 11-11.5 s) is the front end the build reuses (`gate.Types`): dependency linking 5.5 s in 29 link passes over a growing set of types (45 ... 610, 0.1-0.3 s each), saving homes 4 s (`LinkHomes.Saved` -> `BinaryLinks.Grown` reads and decodes each used home binary, the `EntryDecoder` cost of the cache loading line), inlining 2.9 s, source discovery 1.1 s; emission 9.8 s (bodies 5.0, GPU kernels 1.8). Timed inside the 29 passes (instrumented exe, 2026-11-26): `LinkFresh.Precompile` 2.7 s (reading and generating the types whose signature is new this pass), signatures 0.33, linkable 0.29, homing 0.19, trait links 0.13, base types 0.13, `Complete` 0.02, the rest (entries, forwarding, advancing) about 1.3 s. Pass time does not grow with the types linked (0.11 s at 45 and at 610), so a worklist saves little; counted: 2413 fresh signatures for 612 types (Text 16 times, CallTarget 12, Number 11). `Want` already generates only the added methods and `Fresh` merges them, so a repeat only re-reads and fuses the source (`LinkCompile.Prepare`) and builds a `TypeCodegen` over all its lines: at most 75 % of the 2.7 s, realistically 1-1.5 s of a 66 s self-build (under 3 %), dropped. The native decode is the other candidate.
- `strict check .` of DeltaEngine warm (copy, 2026-11-26): 5.5 s, validation 1.5-1.7 s (was 5-6 s, InputOutputs.Settle), dependency cycles and project rules stamped, tests 3.3-17 s from the random light mutant round of each folder. Warm `strict check .` of Strict is 3.4 s (was 6.5 s): validation 2.5 s is the per-folder keys, a fresh process tokenizes the mentions of every file once (~1 s, the server's Memo keeps them but its check is not faster), traversal ~0.7 s and 15000 `File.Modified` stamps ~0.4 s.
- `strict test RealTimeStrategy native` (DeltaEngine, 73 files) after one touched file (16.6-17.3 s): struct lanes 3.2-3.9 s (lane state is texts like "3 Pair" keyed by register numbers: keep laned registers as numbers), `CallGraph.Closure` in `EmissionCache.Keys` (`Marked` copies the dictionary parameter, rebuilding the index), dependency linking (`Completed`, `Forwarded`, `Linkable` and round lists), and name validation reading every linked source again per file.

## Native builds (emission, lowering, linking)
- Web rebuilds after a one-line edit (LogoApp, 2026-11-26, machine 50 % busy): `web edit` 9-12 s, all of it the emcc link with Asyncify (7.2-7.8 s) and the front end, no wasm-opt and no Closure now; release `web` 23-24 s (wasm-opt -O3 12 s, link with Closure 9.5 s).

## VM
- A VM call of a small Strict method costs about 6 us. nsys of 100000 `position + Vector2(1, 2) * 0.75` (2026-11-26): `Machine.Bound` 19 %, inside it `strict_list_push` 46 % (one push per frame slot: 6 header slots, X and Y, 8 constants and the parameters of Vector2), `Machine.Member` 10 % (2 % of the loop, so binding constants lazily alone is under 3 %). A per-method frame template was dropped (2026-11-26): the cost under the pushes is per-element reference counting, which a copy pays too, and indexed writes into this frame list measured no gain.
- VM calls dominate game logic (a member read through a method like `Vector2.X` is two calls): DeltaEngine's multi-tick simulation and content loading tests are Slow for it. `position + Vector2(1, 2) * 0.75` costs about 20 us (nsys 2026-11-26): `Rounding.Build` 21 % (its prototype copy pays the same per-item reference counting as building fresh, under 3 %; `Number.Rounded` is native now, `strict_number_rounded` keeps 24 significant bits by integer rounding, VM loop median 2.33 -> 1.94 s), `Machine.Bound` 19 % (dropped 2026-11-26: writing serial collecting loops by index passed the fixpoint, but `strict_list_filled` at the exit costs what the pushes did, `Machine.Bound` 18.8 % before and after in nsys).

## Compiled CPU loops, lists and texts
- Matrix and vector speed (native probe: 3M `Translation * Scaling`, `Inverse`, `Transform`, 2026-11-26): `Inverse` is 75 %, its list literals pushed element by element (25 %, now `strict_list_push_number` for lists of numbers, 8 % faster) and `rotation + (...)` joined by `strict_list_concat_host` (18 %) before `Matrix(...)` flattens it again (`strict_flat_from_list` 8 %); `Axis(n)` allocations are not visible. The VM still calculates in f64.
- Whole-number versions: LoopSpeed `twisted` (MersenneTwister.Uints, 28-32 ns per number) is not limited by f64 math: `Twist`/`Temper` made whole (2026-11-26: `Number.and`/`or`/`xor` as i64 ops plus `HasWholeParameters` ignoring unread members, the latter breaks `MlirWholeBody.Allocate` on `ProcessResult.HasFailed`) gave the same time and were reverted; `Uints` is mostly the growth and marking of its list.
- ParticleStress at 1 million particles (8.3-8.8 ms per tick with the machine 40 % busy after capping the young generation at 512 MB, was 9.7-13 ms, 2026-11-26; 4.8-5.5 ms quiet): every `Particle.Advanced` allocates a new 96 byte particle and the old one dies (`strict_gc_small` 12 %, `strict_rc_dead` 8 %). Reusing the old particle needs three steps: the caller passes a dying receiver (`current = current.Advanced(Tick)`), `EffectSystem(value, ...)` moves members of an owned `value` instead of sharing them, and the parallel `Living` loop frees or reuses elements of its owned list; today `strict_rc_dead` returns at once inside pool jobs (`strict_rc_busy`, counts are not atomic and `strict_rc_recycled` is global), so a tick's million dead particles wait for the young collection. 32 bit members (72 -> 44 bytes).

## Collector
- Realtime frames: mark incrementally over several frame ends when a full collection takes longer than a few ms (STRICT_GC_LOG of ParticleStress 1M, 2026-11-26: spawning has one full collection of 93 ms marking 86 MB and young ones up to 27 ms, the 100 ticks have 3 young ones of 7-9 ms marking 198 MB; the card barrier `strict_gc_written` and `strict_gc_framed` are the starting points). Lists of numbers grow into leaf blocks the collector does not scan, by `+` (`strict_list_concat_numbers`, `Uints(20000000)` 1.0 -> 0.63 s) and by appends (`strict_list_push_number`, 20M appends 0.50 -> 0.45 s).
