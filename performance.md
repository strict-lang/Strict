# Performance

From Ben's VM handoff of 2026-11-18 (a trial is a 20 line type with 20 to 30 tests, `strict test <file> shown` through the resident server).

- A file its own dependencies mention gets the full inference on every call: `Calculation.strict` in Ben 0.9 s for 520 files, most of Ben's 61 types 1.4 to 1.6 s outside their tests. `KeptInference` only keeps the others for a leaf. Next: one entry per file (write time, shape, raw scopes, typed scopes, mentions) instead of one per file list. A request takes the entries of its files, makes the raw scopes of new and changed files again and types again only those and the files that reach them through mentions (a changed `Datum` in Ben: about 60 files instead of 520; a leaf: itself). Everything again when the set of generic types changes or a type name now belongs to another file. This also serves a smaller file list from a bigger one, so the 8 kept lists of `InferenceCache` would go.
- A kept trial call is 0.33 to 0.45 s (522 files, was 1.3 to 1.5 s), a base type trial 0.17 to 0.2 s. Left: `SourceFiles.Reached` 0.1 to 0.15 s (`FolderIndex` lists every folder of every sibling project per round, `Matching` walks all indexed files per round), `FileCompiler.Resolved` loops over all files, `BinarySources.Stamped` runs twice (10 to 15 ms each), the process itself 60 to 70 ms.
- The same exe answers that trial in 0.33 s when the server was started from a console (`strict serve 2`) and in 0.44 s when the client started it (hidden PowerShell start), both with `STRICT_THREADS=47`. Cause not found, priority class and logs are the same.
- `strict build Ben.strict windows` 64 s, 37.9 s of it GPU preparation (PTX 11.2 s, cubins 9.1 s), 14 to 25 s on 2026-11-16. Ben has no GPU loop of its own, only `Advisor` through NeuralNetworks.
- A folder of 100 new trials takes 17 s the first time (170 ms a file), 4.4 to 4.9 s for the 24 failing ones afterwards.
- Ben's search on the VM was 115 to 264 times slower than native (`Planner.Planned(Evens)` 5 s against 43.5 ms). Since 2026-11-18 one line methods of up to 10 instructions are inlined inside a type and calls no longer parse type names: Evens 3.6 -> 3.2 s for each of the two, a call costs 4 to 5 us, an instruction about 0.7 us. Profile after that (nsys, a strict.exe relinked with a map, `Planner.Plain.Planned(Planner.Evens)` in a script): `Machine.Bound` 37 % (one list of `method.Slots` values per call, pushed one by one with a count each; a version joining ready lists was slower, 1.5-2.8 against 0.8-1.6 us for 32 slots), reference counts 16 % (`strict_rc_count`, `strict_rc_container`, `strict_rc_drop`), `Machine.Field` 10 % (since then `Resolver.Fielded` puts the place of the type and the member into the instruction: 400,000 reads in a loop 810 -> 710 ms median of 5, nothing measurable on Ben's search), `Frame.Finished` and `Value` 10 %. Still wanted: inlining a one line method of another type (`Datum.IsFailed`, `Skill.IsLearned`: the inliner only takes calls inside one type or on a type with one member), a text compared with a constant text by identity first (`kind is "Error"`, `Calculation.Applied`), `Floor` and its neighbours as VM natives, small values without an object each (`Datum.OfNumber`).
- A GPU result that only becomes a texture should never reach the CPU. FractalZoomer per image now: the kernel result is downloaded (1.0 ms for full HD, 6 ms for 4K), `Texture.Update` in ../DeltaEngine Frameworks/native/Render.c turns the numbers into bytes on the CPU (`pixelBytes`, one malloc per frame) and uploads them with `glTexSubImage2D`. To build: (1) a foreign call receives a list living on the GPU as its device address and count instead of a downloaded copy (`MlirForeign`, `strict_gpu_device`), (2) Render.c registers a pixel buffer of the texture with the CUDA context once (`cuGraphicsGLRegisterBuffer`), copies device to device per frame (`cuMemcpy`) and calls `glTexSubImage2D` from that buffer, (3) the kernel writes palette bytes (or the shader reads 32 bit numbers) so no conversion is left, (4) the download stays as the path without NVIDIA and for WebGPU, where the result is already a buffer of the page.
