# Performance
Open speed work, one short line each, measurements go into commit messages. GPU details: [improvements-gpu.md](improvements-gpu.md), models: [improvements-models.md](improvements-models.md).

- The VM is about 100 times slower than native on compiler code (boxed numbers, dispatch, allocation): the reason internal package tests count as Slow.
- Testing one file on the VM spends 0.7-4.3 s before its first test (Compiler/MlirLibrary 4.3 s, MlirCalls 2.7 s), all of it again every run: the link rounds themselves are cheap, compiling the used methods takes 10-30 ms per type, Changes(lines).Members and .Methods are recomputed per method body and call site (TypeShape.CallScope, MethodBodies, ChangedInstance) and source discovery tokenizes every file (SourceFiles.PackagesIn).
- Compiling Number.strict (instrumented `strict test Compiler/output/Probe/CodegenProbe.strict lines`, 596 ms) tokenizes 18k lines (36% of executed lines, 148k is the character count): BodyParser parses 1042 statements for ~250 lines, source discovery reads 185 files and tokenizes every line with a `/` (870, mostly strings and divisions, each candidate costs Directory.Exists calls), TypeShape.MemberScope is rebuilt 1191 times (scans all lines each time, CallTarget, Definitions) and TypeCodegen.Generator 1239 times; a per-line token memo or computing shape scopes once per TypeCodegen would cover most of it, stopping MemberScope at the first method needs a members-first rule (only Compiler/MlirBatched.strict has a constant after methods).
- VM calls dominate game logic (a member read through a method like `Vector2.X` is two calls): DeltaEngine's multi tick simulation and content loading tests are Slow for it.
- Build speed: under 10 s hard limit, 2-3 s target (LogoApp, Blocks and Breakout 3.6-4 s): a build with tests runs the frontend twice (test gate, then native), lowering and the thin LTO link are the largest phases left.
- Cold GPU builds spend most time on the shared runtime PTX for both sm_75 and sm_80.
- `MlirCost` sums expensive alternative call paths and overestimates tiny loops: a loop called again is probed on the caller once its last fork took under 1 ms, a loop run once still forks.
- Collector lane refill: a lane still takes the collector lock for every waiting page it pops and every fresh page (`strict_gc_refill_busy`), one shared lock for 64 lanes.
- Trees as pools with 32 bit backward offsets ([Goose](https://github.com/aardappel/goose)): count SyntaxNode allocations of `strict build Strict.strict` first.
- GPU preparation takes 0.5-0.6 s of every build with kernels also when nothing changed (`DeviceBuild.Built`: `PtxCache` reads the runtime PTX and hashes the kernel text with `HashCode` per character), `MlirSplit` still reads the just written module back.
- All native providers compile once any of them is needed.
- Reachability, safety and globals/text assembly of MLIR emission run serially.
- ParticleStress at 1 million particles (Unity's particle system 9.5 ms per tick): 5.5 ms per tick over 100 ticks, 4.8 at 600 ticks (7.8 and 5.9 before 2026-11-06, 14.2 at first) and no collections: dying locals free their old values (MlirDying), a long list whose last count goes is freed at the next large allocation unless a stack slot points into it, and the next list reuses its pages. Pool threads take their own pieces of a job first (strict_pool_run) and prefer one core each (SetThreadIdealProcessorEx), so every tick a thread writes and reads the same items in its own L3; before, the list two ticks old was still dirty in other CCXs' L3 and every line moved between them. Next: 32 bit members (72 -> 44 bytes per particle), writing in place over the list being read.
- A `for` that drops items collects objects in parallel, but numbers and flat elements stay on one thread (any bit pattern is a number, so no hole marker): keep a bitmap of the kept slots instead.
- `strict test RealTimeStrategy native` (DeltaEngine, 73 files) takes 47 s when anything changed: every file is linked again, 11 s of dependency linking (link rounds only scan new entries now, `Completed`, `Forwarded`, `Linkable` and the round lists remain), the thin LTO link takes 8 s (about 2 s on one thread at the end), name validation reads every linked source again per file. A run without changes of a .strict file takes 0.1 s.
- WebGPU submits every dispatch in its own command buffer (2300-2700 submits, ~9000 writeBuffer, a new bind group and result buffers per kernel): MossWeb at 480p takes 3.5-4.1 s a step in Chrome on an RTX 4090 against 0.23-0.28 s natively, Chrome's GPU process spends its time in single-threaded Dawn command handling (0.37 ms per batch, a dispatch inside one submit costs 0.01 ms). Batch whole runs of kernels into one command buffer and submit only before a read; the per-dispatch `work` values, pooled inputs and places must stop relying on writeBuffer landing before the next submit (one parameter buffer with offsets), cache bind groups and pool result buffers. The 1 GB queue throttle counts every byte a kernel reads (weights too) and waits ~750 times a step, count only new allocations.
- MossWeb at 1088x1920 takes 43 s per evaluated step on a 3080 (WebGPU): attention stores all scores of a head (8400² is 283 MB), a tiled online softmax would need far less memory and traffic at every size.
- MossWeb 480p after 720p images in the same page is 15-20 % slower than in a fresh page (fastest 5.1-5.7 instead of 4.3-4.5 s an image on a 3080): the WebGPU buffer pool probably keeps the 720p sized buffers, smaller sizes should reuse or shrink them.
- Decode attention (`strict_device_attention_decode`) is latency bound: about 8 us per call even for a few positions (4 blocks of 8 warps, 255 registers, warps waiting at the merge barriers) and 24 us after 2000 positions for Qwen3-Coder 30B, 48 calls a token.
- Generated CPU loops: parallel chunks whose checks are all on numbers run once without early exits (a failed check or index read gives 0 and a flag, the chunk then runs again with all checks) and vectorize when their reads are of hoisted parameter or member lists; still per element: reads of other lists (`strict_list_read`), checks on instances, chunks with inner loops (their fast path copies would be duplicated), serial loops, and f64 numbers and indices.
- Fast path loops (MlirFastLoop) below `MlirCost.Threshold` elements run on one thread, longer ones in parallel chunks (10 million numbers: 30 ms on one thread, 12 ms on 64, the rest is page faults of the fresh 80 MB result, pool big results); a chunk reads an iterated list of 32 or 16 bit floats (Float32s, BFloat16s, halves) in place (`MlirDeferred.Packed`), a chunk with inner loops reads each item where it is (`strict_steady_item`) instead of unpacking the list first.
- Reading a packed list through `strict_list_items` (chunks without inner loops over Float8, byte, lane or quantized lists, quantized formats read by index, Float8 and quantized arguments of native library calls) replaces it with an f64 copy for good (`strict_list_unpacked`), it then takes twice the memory and loses the f32 loop variants; serial loops, chunks with inner loops and index reads read 32, 16, 17 and 7 bit formats in place (`strict_steady_item`, `strict_list_get`).
- A call with whole number arguments dispatches per element between its i64 (`_whole`) and f64 versions: a vectorized loop computes both and blends, one thread over 10 million numbers takes 55 ms against 14 ms for the same math inline.
