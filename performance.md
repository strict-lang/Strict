# Performance
Measured speed work, compiler front end first. One item per finding, removed when done or no longer true.

## Front end, checks, tests and the server
- Native builds after a new strict.exe reuse 0 emitted functions (MossWeb: 613 emitted again, 51.6 s instead of 39.9 s): every emission key holds CodegenStamp, a hash of the modified times of all root *.strict, Compiler/, Bytecode/, Expressions/ and NativeRuntime*.mlir files, so any touch there (a Check* program, a git checkout) makes all keys new. The Check* programs are left out since 2026-11-23. Hashing file contents instead of modified times took over 5 s per stamp on the VM (HashCode over the 2+ MB of sources, CodegenStamp's test ran past 10 s): needs a native file hash first; validation-only files could go too; precise later: a stamp per file of what codegen reaches.
- Cache loading after today's fixes (a fresh `.strictbinary` is decoded once per test command: `test Sum unit` 43 -> 28 ms, `test Layer unit` 94 -> 54 ms, `test Strict.strict unit` 3.4 -> 1.7 s, 0.8 s with the Text change below): what is left is the full decode of all 391 linked types (3.2 MB of bytecode down to every instruction, about 2.3 million allocations, collections only 17 ms) although the links ask for 4024 methods: decode only the selected methods. A Text collected from Characters in a counted `for` is allocated once now (5.7-8.8 ns per character instead of 570-820 at 4096 characters; `test Strict.strict unit` 1.83 -> 0.81 s); the appending form `text = text + Character(value)` still allocates and copies per character (600-770 ns each at 4096, quadratic: texts have no stored length or capacity). Stamping the 6648 source names of the links again per link costs 0.14-0.24 s (no shared stamp dictionary). `strict <file>` recompiles its program on every run and never uses the cache (135 ms for Sum).
- Compiler self-build, where the front end time is (2026-11-12, 12.3-14 s with cached objects): the first build after a new strict.exe links in 4.4 s instead of 16.5-17.9 s since 2026-11-14 (every type compiles again then, `LinkFresh` reads the sources serially and runs `LinkCompile.Generated` in a parallel loop, one big type of 66-109 ms still ends some passes alone); dependency linking 1.7-2.1 s since 2026-11-14 (2.3-2.7 s: `Signature.Earlier` scanned every signature of the round several times per fresh signature, `LinkFresh` looks the type up in one dictionary per pass now). - `strict check .` of DeltaEngine (442 files, i9-13900KF): warm (nothing changed) 160 -> 11 s since 2026-11-14 (validation 105 -> 10 s: `ResolveCheck.Tree` skips Release, lowercase folders and Content/Tools folders without a .strict file and lists only folders with .strict files; tests 56 -> 1 s: `Folders.Pending` starts no test process for a file whose header stamps (sources, compiler) and test runner are unchanged). ## Native builds (emission, lowering, linking)
- With a usable GPU strict.exe's own loops ran on one thread or through GPU dispatch (2026-11-23): its parallel loops carried the GPU gate (strict_parallel_forkable, 36 of them, EmissionCache.Fresh/Pick and LinkFresh.Generating among them) and 9 of its loops were GPU kernels (List.Slice, MlirSafety.Spreading, ...) dispatched per call; a fresh build spent 32-36 s in body emission and 17 s in dependency linking (5.3 and 2.2 s with STRICT_GPU=0). Since ce184820 and 0ef1674b the compiler program (MlirCost.IsCompiler) has neither: self-build 175-183 -> 120 s, bodies 42-48 -> 3.8 s. Precise follow-up: MlirPurity.IsReachingGpu and kernel selection for every program should only gate or offload loops whose counts can reach the GPU threshold (IsDevice today counts any device-capable inner loop), checked on NeuralNetworks and StrictComfy.
- Every raw loop is emitted six times (one copy per packed format its lists may have at run time plus the plain one) next to its generic body: code size and lowering time grow with every loop that becomes raw, not measured yet (compare `strict build Strict.strict` and a NeuralNetworks program with the copies off).
- Measured 2026-11-12 (cold `build Strict.strict windows`, three runs, seconds summed over the parallel body emission): `MlirArguments.Constant` (through `MlirWholeBody.Parameter`) runs once, 0.002-0.004 s, left as it is; `MlirDefaults.ParameterName` runs at 57 call sites, 0.31, 1.68, 0.35 s (rebuilds `ParameterTexts` over all methods per call; since 2026-11-15 not for `""`, whose name is never used, not measured), next to try after `IsMatched`. Suspected from reading, to be measured: `MlirConstants.Escaped` computes `Hex(value, 2)` for every byte of 640 KB of text globals and `EscapedLength` encodes the text a second time.
- Host lowering with 0 parts changed takes 1.5 s per build of Strict.strict (2.6-3.9 s before the remembered text length survived reclaims: `ReadLines` of the 80 MB module 2.2 -> 0.39 s, 1000 lines of 80 KB 13 s -> 0.14 s). Left: `ReadLines` 0.39 s (the emitter's text could reach `MlirSplit` without the round trip through the file), `Owned` for 64 parts 0.34 s (`Body` appends line by line), `Text.Combine` of each key 0.20 s, `Written` (reads the 80 MB of stored `.owned` keys and compares) 0.08 s, `Starts`/`Shared`/`Placed` 0.13 s.
- `MlirWholeCall.IsMatched` (41-45) analyses the callee from scratch at every call site (`Kinds`, `IsWhole` with recursion to depth 3, the `Settled` fixpoint, `MlirWholeTypes.Called` inside it): 13397 calls per cold `build Strict.strict windows`, 5.4, 8.2, 6.2 s summed over the parallel body emission whose wall time is 2.6-3.1 s with that per-call logging and 0.72-0.95 s without it (measured 2026-11-12). - Test executables link without ThinLTO cross-module importing since 2026-11-21 (owner's choice: NeuralNetworks after a one-line edit 10.7 -> 0.3 s, test runs about 20 % slower); programs and releases still import. - A web rebuild is now mostly whole program work after the parts: emcc link with Closure 2.3 s and wasm-opt 1.6 s for Xor, also when only one string changed.
- Build speed: under 10 s hard limit, 2-3 s target (LogoApp, Blocks and Breakout 3.6-4 s): a build with tests runs the frontend twice (test gate, then native), lowering and the thin LTO link are the largest phases left.

## VM
- VM loops of small Number methods are about 20-50x slower than native (2026-11-14, `STRICT_SERVER=0`, 4608 steps per probe): a loop step with `sum = sum + index` costs 2 us (about 0.5 us per instruction), a call of a method of the own type 4 us more, a call of a Number method (`Floor`, `Absolute`) 11 us more: `Machine.Bound` 4 us (27 slots, 11 of them Number's members and constants, `Ownership` splits texts per call), `Execute` 3 us, routing 4 us. `Huffman.Entry` calls `Floor` per step, so `DynamicSample.Inflated` takes 149-157 ms on the VM (minimum of alternating runs, 159-277 before the frame fix below) against 5.6 natively and fails the 100 ms test limit; most of the whole `test Compression/Inflate.strict` (852 -> 554 ms) is the 512 entry `Huffman.From` tables of its constants. Fixed 2026-11-14: every slot write of `Frame.Finished` was a versioned `strict_list_write` (a new view per write, a full copy every 64) because the `return` inside its loop counted as handing the slots away, a loop now copies a shared list once before it also when a `return` passes the list on (ListCodegen.Disowned); `Bound` builds its slots in one `for` expression. Also done: `x is Error` compares with one shared Error (`strict_any_error`, was a new `Error("")` with a trace per check, 7.5 %), `Ownership` and `VmValue.Member` cut type names by `IndexOf` (`TypeEntry.Based`), neither measurable in the whole test, both tests now 94-98 ms when they pass and still over 100 ms in most runs. Fixed 2026-11-14: a loop whose whole run fit into the caller's 10 us probe of `strict_parallel_forked` is remembered with its count (`strict_pool_small`, up to 64 elements) and the compiled fork check (`MlirParallel.Enough`, `strict_parallel_worth`) takes its own serial branch from then on, so `Bound` no longer allocates a 400 byte context, rc-counts its result in `strict_list_finished` or touches the pool per call (a 46080 step `Floor` loop on the VM, pinned to one core: median 974 -> 903 ms, a hand-patched never-forking `Bound` 885). Left in a profile of that loop: `VmValue.OfNumber` allocations and `strict_rc_reclaim` freeing them (about 18 %). `DynamicSample.Inflated` is still around its 100 ms limit.
- VM calls dominate game logic (a member read through a method like `Vector2.X` is two calls): DeltaEngine's multi tick simulation and content loading tests are Slow for it.

## Compiled CPU loops, lists and texts
- Serial loops (below `MlirCost.Threshold`) run raw when they read lists at `index + offset` (parameters, members and checked local lists), calculate, use `and`/`or`/`xor` on Numbers and call pure Number methods that cannot fail (Examples/LoopSpeed and probes at 227 elements: offsets 23-27 -> 1.4-2.9 ns per element, local lists 45-65 -> 4-6, `xor` of two reads 25 -> 3, a `Twisted` call 31 -> 8.5, `MersenneTwister.Uints` 55 -> 32 ns per number at 10 million). Still generic (`strict_hoisted_read`/`strict_list_read`, `strict_is_failure`, `strict_list_push`): gathers `table(value)` 14-20 ns, calls that can fail or read lists (`MersenneTwister.Normals`), one thread of a parallel chunk (22 ns, its packed copies still read through `strict_hoisted_read`); a raw `Tempered` call stays at 31 ns, its f64 body has two remainders and no whole number version is used. Nothing reports a pure loop that stays generic.
- Appending in a loop (`Probe/AppendSpeed.strict`, 624 elements, 2026-11-14): 7.5-8.5 ns per element for a local list started empty, with one element or from a parameter (29.7 before `strict_list_add_seeded`). Still a new view per append (about 30 ns): a list started from a member (`MersenneTwister.Uints`, which concatenates `raw + Generation(...)`) and one handed to a constructor afterwards (`MersenneTwister.Seeded`, 240 ns per state, `Spread` has four remainders); a raw collecting `for` writes its result at 1.4-2.9 ns per element.
- Texts carry their byte length and character length in front of their bytes, appending to a local text writes into its block, and substrings of long texts and of spans are spans (one value: text window, start, length) since 2026-11-14 (plan.md: tokenizer folder 0.28 -> 0.24 s, self-build 16.3 -> 13 s, substring of a word 14.1 -> 10.9 ns, split part 41-45 -> 18 ns, 20000 appends 207 -> 0.25 ms). Left: `File.ReadLines` copies its lines in the runtime, `Trim`, case changes, `to Number` and sorting copy a span first, texts under 256 bytes copy their substrings.
- Short parallel loops: `Gpt2Block.Normalized` of one row of 768 numbers takes 37-61 us natively without GPU (85-138 before the pool cut the rest of a probed loop into pieces for its helpers only instead of about 500 pieces of one or two elements), one thread alone needs 37 us (48 ns per element in the generic body: memo check, two `index % size`, the `Scale` call), `Centered` 10-17 us. Left: the probe hands a loop over after 10 us although its rest takes less than the wake up, every piece starts with a memo miss (the row's `Squared` again), and the fork threshold (`MlirCost.Work` 50000, about 33 us of work) is below what a wake up costs on 128 threads. Measured 2026-11-14 with `Probe/ParallelSpeed.strict` (Threadripper 3990X, `STRICT_GPU=0`, a 40-65 ns body): 1000 elements 31-33 us (38-39 before every job copied the 0.1 MB lane table instead of the lane's own 1 KB row, 11 % of the caller's time), 3000 43 us (serial 100-200), 10000 41-50 us (serial 340-670), 30000 75-80 us (serial 1230-1990), 300000 0.5 ms (serial 12 ms). A forked loop never gets under about 40 us: each helper gets 50 us of work, and that share is right here. Tried and measured no better: WaitOnAddress instead of the condition variable, a wake tree (each woken worker wakes two, the caller two), 10x longer spinning (2000 `pause` are only 35 us on Zen 2, but 95 spinning threads lower the boost clock and slow their SMT siblings), counting spinning workers as 2 us helpers, pieces of at least 512 elements. With a 5 us share the caller woke about 80 sleepers one by one (0.3 ms, the tree brought it to 70 us, still above the 50 us share). Cheaper small loops need work that stays on fewer threads (a few hot workers per CCX like Go's limit on spinning threads) rather than faster wakes.
- `List.Sorted` of numbers is a sorted copy through the platform's `qsort` since 2026-11-13 (`strict_list_sorted`): 1187 numbers 1000 -> 195 us on Windows, 54 us on Linux (glibc), the web build about as slow as before (952 us, comparator calls through the wasm table). Left: MSVC's and wasm's `qsort` call the comparator per comparison, a sort with the comparison inlined (an introsort or radix sort in the runtime) would bring Windows and the web to the Linux time; other element types still run the merge passes of `List.Sorted` (1 us per element). `Sampling.Threshold` (2.7 ns per element in its raw passes) may now be slower than one sort, measure it.
- Matrix and vector speed (`Probe/MatrixSpeed.strict`, minimum of 40 alternating runs of 200000 calls, i9-13900KF, 2026-11-14): chained product 7.7 ns (14.1 before 32 bit values were calculated in f32, `MlirRounded`), `Transformed` 5.5 ns, `Axis(n).Y` 4.5 ns. Left: the VM calculates in f64 (plan.md, step 8), accessors (`point.X`) are not counted as 32 bit values, `Axis(n).Y` still allocates its Vector3, a block is only reused when the local is alone (not seeded from a parameter, not read through `.values(n)` or passed to a method that is not destined itself).
- Whole-number call guards give up (f64 version runs) when a variable read after an `if` or a loop that stores it is used in `+`, `-` or `*` (sound since 2026-11-12; a maximum over the possible stores would bring the i64 path back for those, nothing in LoopSpeed or the compiler's own guards changed).
- A struct with a stored member left to its default (`MachineUse.coordinator`: the call names a parameter past its arguments) is no longer rebuilt in place (`MlirOwned.IsArgued`, 2026-11-12): storing the default in the `^tNreuse` block (`MlirInstances.Default` with its own suffix, releasing an old reference member) would bring it back; not measured.
- ParticleStress at 1 million particles (Unity's particle system 9.5 ms per tick): 5.5 ms per tick over 100 ticks, 4.8 at 600 ticks (7.8 and 5.9 before 2026-11-06, 14.2 at first) and no collections: dying locals free their old values (MlirDying), a long list whose last count goes is freed at the next large allocation unless a stack slot points into it, and the next list reuses its pages. Pool threads take their own pieces of a job first (strict_pool_run) and prefer one core each (SetThreadIdealProcessorEx), so every tick a thread writes and reads the same items in its own L3; before, the list two ticks old was still dirty in other CCXs' L3 and every line moved between them. Next: 32 bit members (72 -> 44 bytes per particle), writing in place over the list being read.
- A `for` that drops items collects objects in parallel, but numbers and flat elements stay on one thread (any bit pattern is a number, so no hole marker): keep a bitmap of the kept slots instead.
- Generated CPU loops: parallel chunks whose checks are all on numbers run once without early exits (a failed check or index read gives 0 and a flag, the chunk then runs again with all checks) and vectorize when their reads are of hoisted parameter or member lists; still per element: reads of other lists (`strict_list_read`), checks on instances, chunks with inner loops (their fast path copies would be duplicated), serial loops, and f64 numbers and indices.
- Fast path loops (MlirFastLoop) below `MlirCost.Threshold` elements run on one thread, longer ones in parallel chunks (10 million numbers: 30 ms on one thread, 12 ms on 64, the rest is page faults of the fresh 80 MB result, pool big results); a chunk reads an iterated list of 32 or 16 bit floats (Float32s, BFloat16s, halves) in place (`MlirDeferred.Packed`), a chunk with inner loops reads each item where it is (`strict_steady_item`) instead of unpacking the list first.
- Reading a packed list through `strict_list_items` (chunks without inner loops over Float8, byte, lane or quantized lists, quantized formats read by index, Float8 and quantized arguments of native library calls) replaces it with an f64 copy for good (`strict_list_unpacked`), it then takes twice the memory and loses the f32 loop variants; serial loops, chunks with inner loops and index reads read 32, 16, 17 and 7 bit formats in place (`strict_steady_item`, `strict_list_get`).
- A call with whole number arguments dispatches per element between its i64 (`_whole`) and f64 versions: a vectorized loop computes both and blends, one thread over 10 million numbers takes 55 ms against 14 ms for the same math inline.

## Collector
- Lists of numbers made by generic list paths (`strict_list_add` growing `raw = raw + ...` in MersenneTwister.Uints, `strict_list_new` of other loops) are scanned by the collector: on wasm the halves of their numbers look like references and keep dead big lists alive while they live; they should be scanned only up to their items like `strict_numbers_new` lists.
- Realtime frames: a full collection at a frame end that takes longer than a few ms marks over several frame ends (incremental, the cards record what changed meanwhile).
- `GarbageCollectionExceedsLimit` and `GarbageCollectionAboveTarget` could also name the largest allocating call sites of the window.

## GPU
- Qwen3Benchmark 27B Q4 batch 1 decode (cacheBits 32, 20 tokens, RTX 4090, 2026-11-23): 20.47-20.75 ms median (48-49 tokens/s) with today's code, with 5010f8b6's sources and with 5010f8b6's own strict.exe alike, so no code regression; the 57-58 tokens/s were Ben's ask server (400 token essays, 8 bit KV), not this benchmark. Batching is the real target: 8 batched give 30 tokens/s in total.
- The first big numeric loop of a process takes ~330 ms extra, that is its first GPU use (STRICT_GPU=0 saved ~0.45 s of an 8 seed run, only cold runs pay it).
- Decode attention (`strict_device_attention_decode`) is latency bound: about 8 us per call even for a few positions (4 blocks of 8 warps, 255 registers, warps waiting at the merge barriers) and 24 us after 2000 positions for Qwen3-Coder 30B, 48 calls a token. Short-context decode (`positions <= 128`, `strict_device_attention_short`) now uses 4 warps (128 threads) with a single barrier and no prompt path: Qwen3-8B Q4 (100 tokens, cacheBits 8) improved from 7.43 ms (135 tok/s) to 7.03 ms (142 tok/s) at batch 1 and from 13.19 ms (607 tok/s) to 11.55 ms (693 tok/s) at batch 8.
- Attention: the routing planner reads all pooled keys of a head in every block: moments once per head, the scores as a small product kernel (2026-11-08: fusing the moments and score passes, or only storing the centroid before the moments loop, made the routed kernel run 2.25x the instructions and L2 bytes at 480x832, so plans got longer although the data flow reads as equivalent: dump plan lengths before trying again)
- 16 bit lists: compiled loops index in 64 bits: 32 bit index math where the counts fit
- GPU memory: without spilled rows the trim before an own block runs at every block
- GPU memory: GPU-only lists can't be spilled, activations kept across streamed blocks take every byte from the weights
- GPU memory: a reference in a local stays alive after its last use in a callee-saved register or spill slot (conservative stack scan)
- GPU memory: NVFP4 matrices (`TensorFile_Fours`) load as 8 bit rows (27 instead of 15.7 GB): e2m1 rows with their block scales on the GPU
- Loading with LoRAs: H3 with the LoRA of a preset loads in 11.3 to 12.4 s against 6.4 to 6.5 s without, since the next matrix of a block is read into its rows on 16 threads while the GPU merges the LoRA into the current one (`RowsAhead`, 12.7 to 13.6 s before). Left: the first matrix of each block is still read after the last merge of the block before it, and the merge itself sends every matrix to the GPU and back (22 GB each way, 10 to 36 ms a matrix)
- WebGPU: strict_convolution runs at ~6 TFLOPS on a 3080 (30 peak): not limited by workgroup bank conflicts, index divisions, register prefetch or the rolled inner loop (unrolled it was 6 % faster in a decode, products slower, shaders compiled longer)
