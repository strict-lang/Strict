# Texts with stored lengths, spans, growing lists, f32 members

Decided by the user on 2026-11-14. Internals only, the language does not change. Each step is committed when it is green, measured before and after (a gain counts from 5%).

## Text block
Every text in memory is `byteLength` (i64), `characterLength` (i64), then its UTF-8 bytes. Both lengths count the payload only. `characterLength is byteLength` means ASCII: indexing, iteration and substrings are byte offsets, nothing is decoded. A Text value points at the first byte (the two lengths sit in the 16 bytes before it) and a zero byte still follows the payload, so C calls (`fopen`, `getenv`, the web page) and code not converted yet keep reading it as a C string. That is what lets the change land in steps instead of one switch of 47000 lines of runtime.

## Steps
1. Writers: every place that makes a text writes the two lengths. `strict_alloc_text`, the 45 callers that fill it, `strict_text_new`/`strict_text_written`, the shared one character table, runtime constants that become Text values (error names), texts from C (`getenv`, arguments, files), the web page's inputs, and the constants the compiler emits (`MlirConstants.Global`, 16 bytes in front, references point behind them). Debug builds check in `strict_text_length` that the stored length is the `strlen` and stop with the text when it is not: the tests find every writer that was missed.
2. Rebuild `strict` twice and regenerate `Compiler/Bootstrap.mlir`, so every compiler that still runs writes the lengths. Only then:
3. Readers: `strict_text_length`, concat, substring, index, compare, hash, starts, split and the rest read the stored length (55 `strlen` calls, the measured text and joined text caches go). ASCII paths for `strict_text_at`, substring and iteration; the UTF-8 path counts characters.
4. Appending: a text that grows gets a block with room (doubling, +50% from 4 KB), the stored length moves, nothing is copied until the room is used up. Needs the text to be the only holder (ownership for Text like for lists, `MlirOwned.IsHeap`).
5. Spans: a substring, a line of a file or a split part is (text block, start, length) into the block it came from, ASCII only, read only. The Text value of a span has its bytes out of line (a flag in the `characterLength` word, the pointer where the bytes would be), a C call gets a copy with the zero byte. Tokenizer, `File.ReadLines`, `Split` and `Substring` use them.
6. Lists like a C# List: an append that fits writes in place, one that does not gets double the room. A list seeded from a parameter or from `List(Number) + first` appends as fast as an owned one (33 -> 8 ns per element): releasing a view must not free a holder another view uses.
7. Collector: number lists from generic paths are scanned only up to their items (`strict_list_add`, `strict_list_new`), a full collection at a frame end marks over several frames.
8. Members with `value.Bits is 32` are computed in f32 natively, the VM rounds every such result to f32, so a test shows where 32 bits are not enough (then the constraint goes).

## Measure with
`Probe/TextSpeed.strict` (20000 appends, 187-217 ms), `Probe/TokensSpeed.strict` (Qwen tokenizer folder, 0.28 s), `Probe/AppendSpeed.strict` (8.2 and 33 ns per element), `Probe/MatrixSpeed.strict` (product 14.2 ns), `strict build Strict.strict` (the compiler is the biggest text user).

## State
Steps 1 to 3 are in (2026-11-14). Every text carries the two lengths (constants of the compiler and the runtime, heap texts through `strict_text_room`, `strict_text_made`, `strict_text_sealed`, `strict_text_from`, `strict_text_taken`), `Compiler/Bootstrap.mlir` is regenerated from that fixpoint, and `strict_text_length`, concat, `StartsWith`, join, trim and the file line readers read the stored length; the measured text and joined text caches are gone. Measured: Qwen tokenizer folder 0.28 -> 0.256 s, self-build 16.3 -> 15.5 s, `strict check Compiler` 26 -> 22.8 s, root native tests 22 -> 16.8 s. Run on Windows and a Linux build in WSL; macOS, iOS, Android and web are converted the same way but not run.
Left from steps 1 to 3:
- `Text.Length` and indexing still count bytes. `characterLength` is stored and right for every maker except `strict_text_written` (it counts a byte as a character); nothing reads it yet. Open: should `Length` and `text(index)` count characters for texts that are not ASCII?
- Trace locations (`@w` tables of the emitter) are copied into texts per trace, they should carry lengths themselves.
- `strict_kept_text` (the folder of a thread) stays a C text, the GPU and trace code keeps `strlen` on its C names (30 calls in the main runtime), compare, index and hash still run to the zero byte.
Step 4 is in (2026-11-14): `text = text + piece` of a local that is the only holder of its text (`MlirAppended`: stored only from constants and concatenations, read only by `+`, comparisons, a return or calls returning a Number, Boolean or None) calls `strict_text_append`, which writes behind the text while its block has room and no heap object counts it, else moves both into a block with room for twice the bytes (half more from 4096 on). 20000 appends up to 280000 characters 207 -> 0.25 ms, tokenizer folder 0.256 -> 0.245 s, self-build unchanged at 15.5 s. `Examples/Growing.strict` checks that a text also held by a list keeps its value.
Left from step 4: a text seeded from a parameter or member, or read by a call returning a Text (`Trim`, `Substring`), still copies on every append.
Step 6 is in for the measured case (2026-11-14): lists already double their room (`strict_list_appended`, twice plus four), what cost 30 ns per element was a new view per append for a list that started as a parameter. `raw = raw + element` of such a local (`MlirAppended`, the same proof as for texts, a concatenation of two lists never counts since it may return one of them) calls `strict_list_add_seeded`: the parameter's view gets a new one, every later view takes the new length in place. 29.7 -> 7.7 ns per element (`Probe/AppendSpeed.strict`), `Examples/Growing.strict` checks that the caller's list stays as it was.
Left from step 6: a list started from a member (`MersenneTwister.Uints`, which also concatenates), and one handed to a constructor afterwards (`MersenneTwister.Seeded`).
Step 8 is in for native code (2026-11-14): `+`, `-`, `*` and `/` of two 32 bit values (an element of a flat type like `values(row)`, a local stored once from such a value, or such an operation) round their result to 32 bits (`MlirRounded`: truncf and extf behind the f64 operation, LLVM turns the chain into f32 operations). Chained matrix product 14.1 -> 7.7 ns, `Transformed` 6.3 -> 5.5 ns. Native tests of Math, Examples, ImageProcessing and of DeltaEngine Graphics3D and Physics3D pass unchanged.
Left from step 8: the VM still calculates in f64 and rounds when the value is stored, so a VM test and a native test can differ in the last bit of a 32 bit result. The rule is per method (a 32 bit value handed to a `Number` parameter is a 64 bit value in the called method), the VM needs the same rule per instruction, not a 32 bit tag on values: one analysis on the bytecode for both (`MlirRounded` reads `MlirCouples.IsFlatRead` today). Accessors (`point.X`) are not counted as 32 bit values yet.
Open questions for the user:
- Spans (step 5): a Text value is one 64 bit word, so a span (text, start, length) has to be a small heap block. It saves the copy of the bytes, not the allocation: a substring of a word costs 14 ns today, a split part 41-45 ns (`Probe/SpanSpeed.strict`, `Text.Split` is Strict code). Spans without an allocation need a two word value in compiled code (like the two numbers of a `Vector2` in one slot). Which one?
- `Text.Length` and `text(index)`: bytes as today, or characters for texts that are not ASCII?
